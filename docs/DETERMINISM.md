# Determinism in Lockstate

Lockstate strictly relies on fully deterministic logic within its simulation core. The game state must be capable of being perfectly recreated on any hardware given identical initial state and an identical command log.

Since [ADR 0009](./adr/0009-challenge-verification-strategy.md) this is a **product** guarantee, not only an engineering preference: challenge verification works by deterministic replay, so a simulation that is not bit-reproducible silently invalidates every piece of stored challenge evidence. A determinism regression does not look like a crash — it looks like a correct-seeming session whose replay disagrees.

## Kernel Pacing and Time
- The simulation advances on a strict **50ms tick interval** (20 Hz), owned by `FixedStepClock`, whose `stepMilliseconds = 50` default is at `src/simulation/clock/fixed-step-clock.ts:29`, and supplied explicitly by the worker, which writes it out as `new FixedStepClock(50, { mode: 'paused' })`. There are exactly two such sites and `grep -n "new FixedStepClock" src/simulation/worker/state-machine.ts` is the whole enumeration of them: the `_clock` field initialiser, and the reset near the end of `handleInitialize` (`:203` and `:724` as of `83d9616`). **The `Kernel` itself counts ticks and knows nothing about milliseconds** — `src/simulation/kernel/kernel.ts` contains no time value and `step()` takes no argument. This line attributed the interval to the `Kernel` until an earlier correction, four lines above the line that already assigned it correctly — and **the two anchors that correction left behind then drifted in the other direction**: `:165` had become a comment inside `COMMAND_REJECTION_FAULT_CODES` and `:583` a bare `*/`, while [ADR 0020](./adr/0020-deterministic-kernel.md) said `:203`/`:724` about the same two lines. Both directions are kept because the second is the more instructive: the repair is the grep above, not a third pair of bare numbers (#444).
- Systems and state mutations rely solely on integer `tick` increments, never on floating-point time deltas or elapsed milliseconds.
- Functions like `Date.now()`, `performance.now()`, or other ambient environment timers must NEVER be used in the simulation logic.

`FixedStepClock` is the one legitimate reader of real time, and only as *pacing*: it converts elapsed wall-clock milliseconds into a whole number of 50 ms ticks to run. The number of ticks is a scheduling decision; nothing about the value reaches a system, a command payload or any simulation state.

### The transport controls

Pause, play and fast-forward reach that same clock, over `simulation/set-clock`. They are the most obvious way for a player to break the guarantee above, so the rule is stated rather than assumed: **they change when ticks happen and never what a tick computes, nor the sequence of ticks.**

- Speed is a divisor on wall time inside `FixedStepClock` and nowhere else. `Kernel.step()` takes no argument and reads no clock, so a tick at ×4 is the same tick as at ×1.
- `setControl` pumps before it swaps, so wall time that passed under the *old* control is accounted for under that control. A paused clock accrues nothing: the milliseconds it was paused for are never converted into ticks, so a pause is not a way to store up simulation time. It does not, and must not, *discard* a backlog that already existed when the pause began — time that had elapsed but that the per-wake tick budget had not yet spent survives the pause and is spent after the resume, which is the same overload catch-up `FixedStepClock` performs without a pause. Either way the sequence of ticks is identical; only when they happen moves. `tests/unit/fixed-step-clock.test.ts` pins both halves.
- The worker's unsolicited `simulation/clock-state` publication is a read of `Kernel.tick` after the tick loop has finished stepping. Rate-limiting it changes how often the HUD is told the tick and nothing else.

`tests/determinism/clock-transport.test.ts` drives the real `SimulationWorkerStateMachine` twice from one snapshot — once straight through at ×1, once paused, idled and resumed at ×1, ×2 and ×4 — and requires a byte-identical session bundle at the same tick.

### Recovering from a rejected message

Since #187 the worker **keeps running** after a message it could not decode, rather than faulting permanently ([ADR 0024](./adr/0024-protocol-fault-recoverability.md)). That is a decision about session lifetime, and it puts a determinism obligation beside it: while the worker faulted, a bad message ended the run and there was nothing left to diverge; now the same session continues, and handling garbage must therefore compute nothing.

It does not, and the reasons are structural rather than incidental. The decoder returns its verdict as data and calls no simulation code ([ADR 0003](./adr/0003-simulation-worker-protocol.md)), so a rejected message reaches no system, no command queue and no RNG stream. The fault envelope's `messageId` is a correlation id and is never read by the kernel — the same exemption `crypto.randomUUID()` already holds in `tests/determinism/ambient-nondeterminism-contract.test.ts`'s allow-list — and the main thread's own locally raised fault numbers its ids from a counter rather than drawing randomness, so the simulation import closure gains no new ambient source.

`tests/determinism/protocol-fault-recovery.test.ts` is the executable form: sixty ticks of the standard scenario driven through the **real worker entry module**, with undecodable messages of every classification arriving between wakes, must end byte-identical to the same sixty ticks with none — and the heckled run is asserted to have actually been heckled, so the comparison cannot pass by both runs doing nothing.

## Command Ordering
- All external input is enqueued as a discrete `QueuedCommand` with a designated `executeAtTick` and a strict, contiguous `sequence` number.
- Commands are explicitly ordered and validated by the Kernel.
- Gaps and duplicates in the sequence are aggressively rejected by the Kernel to prevent desynchronization.
- The pending queue is sorted by `(executeAtTick, sequence)` — a total order — both on submission and on restore, so a restored queue dispatches identically to a live one.
- **The submitting side keeps `executeAtTick` non-decreasing.** `SimulationCommandSender.projectExecuteTick` floors its estimate at the highest tick this session's stream is already known to carry — what the sender has submitted, and what a restored save's pending queue brought with it ([ADR 0056](./adr/0056-keeping-a-players-orders-in-the-order-they-gave-them.md), #437). Without it a pause taken inside the twenty-tick command lead makes the projection collapse backwards, so a later gesture carries a *lower* tick, and the comparator above — correctly — dispatches it first. Twelve of the thirteen gestures commute and cannot see that; `Undo` and `Redo` count positions in the stream (ADR 0009) and reverse the wrong order. This is a property of the **input**, not of execution: the kernel's behaviour for a *given* stream is unchanged, which is why no fingerprint moves and why the guard is a behavioural test rather than a hash.

## System Ordering
- Every system declares an explicit integer `order` and a stable string `id`; the kernel sorts by `order`, then by `id`. Both keys together are a total order, so registration order can never influence execution order.
- `Kernel.systemExecutionOrder` exposes the resolved order read-only, and `tests/determinism/kernel-system-order.test.ts` pins the declared order of a real session. Adding, removing or renumbering a system changes what a recorded command stream produces, so that pin must be updated deliberately — and, per ADR 0009, accompanied by retiring incompatible challenge submissions through the definition allow-lists.
- Declared `order` values in a real session are kept **distinct**. The id tie-break makes a collision deterministic, not obvious: two systems sharing an order would silently swap places the day one of them was renamed.

## RNG Ownership
- The simulation forbids the use of `Math.random()`.
- Instead, Lockstate uses isolated, named RNG streams powered by `Xoshiro128**` algorithms, which are explicitly seeded and fully serializable.
- Systems must claim specific named RNG streams (e.g. `prisoners.classification`, `contraband.detection`) to ensure that generating a random number in one system does not perturb the sequence of random numbers in an unrelated system. A session registers **six**, all in one array literal in `createNewSimulationRuntime`, and the enumeration is a grep rather than a list of line numbers: `grep -n "RNG_STREAM, state: deriveXoshiroState" src/simulation/runtime/new-session.ts` returns the registrations, `grep -rn "^export const .*RNG_STREAM = " src/` returns the literals. The six are `prisoners.classification` (`PRISONER_CLASSIFICATION_RNG_STREAM`, declared in `src/simulation/runtime/new-session.ts`), `prisoners.sentence` (`PRISONER_SENTENCE_RNG_STREAM`, `src/simulation/prisoners/sentence.ts`), `contraband.detection` (`CONTRABAND_DETECTION_RNG_STREAM`), `contraband.intelligence` (`CONTRABAND_INTELLIGENCE_RNG_STREAM`) and `contraband.introduction` (`CONTRABAND_INTRODUCTION_RNG_STREAM`, all three in `new-session.ts`) and `identity.actor-name` (`ACTOR_IDENTITY_RNG_STREAM`, `src/simulation/identity/actor-identity.ts`). `tests/determinism/save-rng-stream-compatibility.test.ts` writes the set and its derived words out longhand, so adding a seventh has to fail there before it can ship.

  **This bullet read *"A session registers five: `contraband.detection`, `contraband.intelligence`, `contraband.introduction`, `identity.actor-name` and `prisoners.classification` … so that adding a sixth has to fail there before it can ship"*, and it was true for one day.** It was written on 2026-08-28 in `5b99b869` and `89da98f4` (2026-08-29, *"Draw a sentence at admission instead of hard-coding one (ADR 0069) (#541)"*) registered `prisoners.sentence` as the sixth. Kept rather than overwritten, because **the interval is the finding and so is which half of the mechanism worked.** The longhand set was doing exactly what the sentence promised of it: `89da98f4` had to edit `save-rng-stream-compatibility.test.ts` to land — 18 lines of it — and that test lists all six today. What no gate covers is the count in *this* file, so the tally rotted beside a guard that had already fired. `docs/AGENT_WORKFLOW.md` §4 names the shape: *"A sentence asserting an absence or a count rots first"*. The count is unavoidable in a sentence whose subject is isolation between a known set of streams, so it was rewritten to carry a `file:line` per registration instead of standing on its own — *"a wrong number is then one `grep` from being caught rather than one reading"*. **That repair is itself corrected here rather than overwritten, because it failed in exactly the way §4 predicts and the count it was protecting never moved.** Checked 2026-09-15: the count is still **six**, and **ten of the twelve `file:line` anchors it added had drifted** — the six registrations were cited at `:441` and `:478`–`:482` and are at `:446` and `:483`–`:487`; five of the six literal declarations had moved too, with only `sentence.ts:47` and `actor-identity.ts:188` still landing on the line they name. A line number into a file under active edit is the least durable citation in this repository (§4 again), so the anchors are replaced by the two greps above and by the exported constant names, which are what `grep` actually checks.
- Streams are never created on demand: `NamedRngStreams.get` throws for an unknown name, so a typo is an error rather than an unseeded, unsnapshotted stream.
- Every stream's seed is a pure function of `(masterSeed, streamName)` via `deriveXoshiroState`, and `snapshot()` emits streams sorted by name, so the order streams were registered in cannot change a save.
- **Adding a named stream is not a save-format change.** A restore *merges* the bundle's streams over the ones the freshly built runtime holds rather than replacing the instance ([ADR 0038](./adr/0038-what-makes-a-save-compatible.md), #415): a stream the save carries wins, a stream this build registers and the save omits keeps the state `deriveXoshiroState(masterSeed, name)` gave it, and a stream the save carries that this build does not register is kept rather than dropped. Before that, `Kernel.restoreState` replaced the instance, so adding a stream bricked every existing save — silently at the load, and then as an irrecoverable worker fault at the first draw, 5 to 600 ticks later.
- `masterSeed` is therefore load-bearing at restore and not only at creation, which is why the save carries it (#412). It is optional in the payload and absent means 0; see `docs/PERSISTENCE.md`.

## Canonical iteration order

Deriving simulation state by iterating a `Map` or `Set` is the most common way this guarantee breaks, and the hardest to notice. Insertion order is a property of *how a session happened to be built*, not of its state — and almost every `getSnapshot()` in this codebase emits sorted entries, so a snapshot-restored session re-inserts in a different order than the live one it came from. The two then diverge with no visible cause.

Rules:

- Anything that feeds simulation state must iterate in a **canonical order derived from state** — ascending id, ascending entity id, ascending tile index — never `Map`/`Set` insertion order and never `Object.keys()` of a runtime-built object.
- `EntityQuery.execute()` walks indices `0..maxActiveIndex`, which is why it is the only supported way to iterate entities ([ADR 0005](./adr/0005-entity-storage-model.md)).
- **Never `localeCompare`.** Collation depends on the runtime's default locale and on the ICU data the engine was built with, so the same ids can sort differently on two clients. Compare strings with `(a < b ? -1 : a > b ? 1 : 0)` — code-unit ordering is spec-defined and identical everywhere.
- A tie-break must be *total*. A comparator that leaves two elements equal falls back to whatever order the input array happened to be in.
- A registry-shaped `all()` sorts, and so does a keyed membership accessor. `ContentRegistry`, `SecuritySectorRegistry`, `GangRegistry` (including its per-gang `membersOf`) and — since #132 — `DoorRegistry` all do; an accessor that hands out registration history is a trap for its next caller even where today's only caller sorts what it gets. `RoomInstanceRegistry.occupantsOf` was the one stated exception and is no longer one: it sorted nothing, said so at the accessor, and closed by admitting that the sort was the consumer's job and "nothing will remind it". It sorts ascending by entity id now, for the reason the rest of this list exists — insertion order there is assignment order live and ascending-id order after a restore, so the same prison answered two different lists on the two sides of a save. `RoomInstanceRegistry.findBestAvailable` still applies the same sort itself rather than routing through the accessor, deliberately: it is a per-tick scan and the accessor's other caller is a HUD projection, so keeping the two costs independent stops a future optimisation of one from being made blind to the other. `tests/determinism/room-occupant-ordering.test.ts` is the guard, and it is behavioural because the static scan below cannot see either expression.

`tests/determinism/canonical-iteration-contract.test.ts` is what stops this section from being advice. Every unordered enumeration in `src/simulation/`, `src/content/` and — since #177 — `src/persistence/` is either sorted or named in that test's allow-list with the reason insertion order is safe there, so reverting a canonical sort means editing a reviewable list rather than one method body. Persistence is in scope because that is where such a walk stops being theoretical: a walk that feeds an array in the payload puts insertion history *into* the save, and `computeSaveChecksum` hashes array order (it is insensitive to object key order, not to element order), so the failure surfaces as a `checksum-mismatch` on a later load with nothing pointing at the walk. None of the three walks the scan found in that tree feeds a payload today — the guard is what keeps a future one from doing so unnoticed.

## Floating point

JavaScript numbers are IEEE-754 doubles and are deterministic **for a fixed sequence of operations**. The risk is therefore never the arithmetic itself; it is accumulation whose *order* can vary. Wherever simulation state sums floats over a collection (needs effects, risk sampling, utility scoring), the collection must be iterated in canonical order for the same reason as above.

### Quantised state and multi-rate schedules

There is a second, quieter failure of the same family: a rate below the resolution of the integer it is applied to. A system scheduled every `intervalTicks` that rounds its result to storage each call does not merely lose precision — if the per-interval step rounds to zero the value is a **fixed point** and never moves again, and *which* values are fixed points is decided by the schedule rather than by the state. That is a scheduling cadence silently deciding what a tick computes, which is the same line the transport controls above must not cross.

`NeedsDecaySystem` did exactly this until #259: five of six needs never decayed at any level, because their per-interval step was at most half a level and `Math.round(n - d) === n` for such a `d`. The rule the fix follows, and the one to apply to any future quantised rate: **store at a resolution finer than the smallest step, and choose it so the step is a whole number of stored units per tick.** Decay is then exactly linear in ticks elapsed, the same total of ticks gives the same result however it is batched, and `intervalTicks` goes back to being a work-per-tick decision. `tests/unit/prisoners-needs.test.ts` pins both halves — that every rate is whole at the scale, and that batching cannot change the outcome.

## Snapshots and Overload
- By removing non-determinism, a full snapshot becomes a simple data dump of the RNG state, active systems, and kernel tick/sequence index.
- Heavy simulation lag must be handled by the worker queue preserving backlog, executing up to a tick budget without altering the 50ms semantic interval.
- `snapshot() → restore() → run N ticks` must land on exactly the state `run N ticks` lands on. Where a subsystem *deliberately* drops in-flight state on restore (a mid-leg path request belongs to the previous `NavigationSystem` instance's queue), the reset must at least be **idempotent**: restoring an already-restored snapshot must produce the same result, or a save written by a restored session would drift further every time it was loaded.
- What a session snapshot does and does not carry is stated in `CURRENT_SAVE_RESTORED_SCOPE` (`src/simulation/runtime/restore-session.ts`) and pinned in `tests/determinism/snapshot-restore-fidelity.test.ts`.

## Known limitations, recorded rather than silently fixed

- **Room-instance ids are derived from the anchor tile, and that deliberately does not settle ADR 0012.** `RoomZoningService` (#261) mints `<roomCatalogId>:<x>:<y>` when a `ZoneRoom` is accepted — never a counter, never `crypto.randomUUID()`. It is unique because the anchor was unzoned a moment before and is zoned after, and it needs neither of the ADR's two categories: it is reproducible from state like a *derived value*, and stable across ticks and carried in the save like an *allocated identity*, because the anchor cannot change while the instance exists. The day a feature moves or resizes a room, that stops being true and ADR 0012 has to be decided first — the id would then either be re-derived, invalidating every save that carries it and every prisoner's `accommodationInstanceId`, or kept while naming a tile the room no longer occupies.
- **A restored session's guard-coverage census is walked at the restore tick, so it can be *fresher* than a continuous run's, and that is deliberate.** `SafetyCoverageSystem` keeps a census rather than deriving one per read, filled by an `update` scheduled every 10 ticks; `restoreSimulationRuntime` now calls `takeCensus` at the load, so a run restored at tick T holds a census walked at T while a continuous run at the same tick holds one walked at the last multiple of 10 — up to 9 ticks apart. That is a divergence in the sense this list means, and it is recorded here so nobody later reports the two runs disagreeing as a defect. **It cannot reach determinism**, and the reason is a property rather than a promise: the census is in no snapshot, no save field and no state hash (`grep -n "safetyCoverage\|census" tests/helpers/determinism-state.ts src/simulation/determinism/*.ts` returns nothing), and `getCensus` has exactly one caller, `src/simulation/presentation/status-strip-projection.ts` — no system reads it, so nothing it says can change a tick. A replay verifier (ADR 0009) never sees it. What the freshness buys is the whole reason the call exists: a restored session arrives paused and publishes its status counts before any tick runs, so "the first scheduled update rebuilds it" is not a bound there but however long the player leaves the game paused, and a twelve-prisoner prison read `0 COVERAGE` under a green `Covered` for all of it. `docs/PERSISTENCE.md` carries the full reading under "What is deliberately excluded from the payload".
- **`JobSystem.performingSince` is not snapshotted — and the field, the class and the exclusion are all gone.** [ADR 0093](./adr/0093-a-carry-is-an-action.md) decision 5 made a carry an `ActionDefinition`, so the dwell timer is `CurrentActionComponent.phaseStartedAtTick`, **which the payload already carried**. A restored carrier therefore loses **nothing** to the dwell, and at most **two `ActionSystem` reconsideration cycles (40 ticks)** to the travel restart — which is the exclusion every other action already has, not a property of the carry. `tests/determinism/job-performing-restart-bound.test.ts` is the measurement, rewritten with the decision. **This bullet said the restored job "restarts its pickup/drop-off timer, so a restored session finishes that job later than a continuous one", put "later" at one `JobSystem` interval (5 ticks) with one full `ConstructionSystem` interval (10) of amplification for a build order waiting on the delivery, and is kept in that form here** because a claim that a cost went to zero can only be checked against the number it used to be. `docs/PERSISTENCE.md` carries the full reading, including the paragraph that argued a schema version would buy nothing — which was right, and is why nothing needed one: the field was not carried, the class was removed, and the dwell landed on a field the payload already held.
- **A restored session abandons an incident response rather than resuming it (ADR 0033, #352).** `IncidentResponseSystem` snapshots metrics only, so a restored session has no record of the response a save was taken during — and that record is what `releaseResponse` reads in order to *return* the responders and the sector lockdown, both of which the payload *does* carry. Before ADR 0033 the claim was therefore permanent: measured at v0.0.104, four guards and one sector still held 53,000 ticks after the restore, with no reachable caller of `GuardRoster.unassign` for an `'on-search'` guard. A restored session now releases the claim on this system's **first scheduled `update` after the load** — a reconciliation owed by a pending flag, never by a comparison against the tick the save was taken at, which is the trap `ProcurementSystem.update`'s `<=` comment states. **The bound is the distance from the save to that update: at most one `IncidentResponseSystem` interval (10 ticks), and zero when the save lands on one.** **Since ADR 0033's amendment (its open question 1, built) a fresh response is then mounted to the still-open incident on that same update**, out of the pool the release refilled — released first, dispatched anew second, both owed by the one flag. So the divergence that remains is a divergence in *timing* rather than in outcome, and that is the change worth stating precisely: measured in `tests/integration/incident-response-restore.test.ts`, a continuous run and a restored one now reach the **same** terminal state and the **same** `IncidentOutcome`, and the restored one reaches it later — 81 against 71 for a save anywhere in the first interval, and up to `containmentTicks` (60) later for a save taken late in a containment window, because the fresh response's clocks start at the re-dispatch tick. `respondersDispatched` diverges too, by exactly the required responder count, because a second dispatch really happened. A replay verifier (ADR 0009) therefore may compare the resource state and the eventual outcome across a restore boundary and may **not** compare *when* an open incident closed, nor a dispatch counter — a narrower prohibition than before, and still the same shape as `JobSystem.performingSince` above, one step larger. One case still diverges in outcome and is named rather than smoothed over: an incident already `'responding'` for which the pool cannot offer responders who are already standing at its post tile is not re-dispatched to at all, and lapses exactly as ADR 0033 decision 1 says.
- **`EntityStore.getSnapshot()`'s raw arrays are not a canonical state view.** `freeIndices` is a stack, and entries above `freeCount` are stale values `spawn` structurally cannot read; the save codec writes only the live prefix and restores the tail as zeroes (`src/simulation/entity/entity-codec.ts`). The two runs are equivalent, but the raw arrays are not equal — so a replay verifier must hash the **encoded** ledger, never the store's in-memory arrays. `tests/helpers/determinism-state.ts` does exactly that, and `snapshot-restore-fidelity.test.ts` asserts the stale entry is really there so the distinction cannot quietly stop mattering.
- **`IntelligenceLedger`'s id counter is carried, and a save written before it was carried still derives it.** `intel.<n>` is ADR 0012 category 1 — an allocated identity — but until this entry existed the counter was re-derived at restore from the maximum surviving id suffix, and `decayAll` *deletes* expired records, so that maximum is a lower bound on what has been minted rather than the counter. Measured: three tips, one decayed away, then one more tip — a continuous run mints `intel.4`, a run restored from that same save minted `intel.3`. The ids are persisted (they key every row of the payload's `intelligence` array), so this was a save-boundary divergence and not a private counter, which is the condition ADR 0012's Context names as the moment this shape becomes a defect. `contraband.intelligenceSequence` now carries it, as an **optional** field with no `SAVE_SCHEMA_VERSION` bump ([ADR 0038](./adr/0038-what-makes-a-save-compatible.md) §1: absence means what every build did before, so the older meaning is honoured rather than guessed). **The divergence therefore remains, bounded, for a save written before the field existed** — such a save restores with the derived counter, exactly as it always did, and the first save the new build writes then records whatever that derivation produced. A replay verifier (ADR 0009) may not compare `intel.<n>` suffixes across a restore of a save that does not carry the counter. Nothing in `src/` reads an intelligence id today (`grep -rn "intelligenceId\|intelId" src/` is empty; the two consumers, `new-session.ts` and `contraband/search-system.ts`, both go through `forTarget` and read `confidence`), so the bound is on a value nothing acts on yet — which is why this is recorded here rather than treated as a live defect. Guarded by `tests/determinism/intelligence-id-allocation.test.ts`.
- **Per-system `requestSequence` counters are outside snapshots.** `IncidentTriggerSystem` snapshots its `sequence` (it names incident records that outlive the tick); `SearchSystem`, `DeploymentSystem`, `PatrolSystem` and `ActionSystem` do not snapshot their `requestSequence`, which only names path requests against a `NavigationSystem` that a restored session rebuilds empty — so nothing diverges today, but any future use of those counters in state would. Metrics, by contrast, are now carried: #70 added `getSnapshot`/`loadSnapshot` to `DeploymentSystem` and `PatrolSystem` so patrol completion/missed counts survive a save, alongside the trigger/response/search metrics that already did. **`ActionSystem`'s are the exception and always have been**: `unmetDemandCycles`, `actionsStarted`, `actionsCompleted` and `routeFailures` are session diagnostics no payload holds, so a session restored into a fresh runtime starts them at zero — which is why `tests/determinism/contended-scan-order.test.ts` compares them across a restore as a **delta** rather than as a total.
- **The substitution counters are reset by a restore, deliberately and visibly (#435).** `ActionMetrics.substitutionCycles`, `contendedSubstitutionCycles` and the per-prisoner `SubstitutionRecordComponent` behind them are cleared when `PrisonerOperationsRuntime.loadSnapshot` runs, and `ActionMetrics.substitutionsCountedSinceTick` then reports the tick the window reopened at. Unlike the four above, clearing is not merely "the payload does not carry it": a per-prisoner count left standing would be re-indexed onto whoever the restored save puts at that slot, which is #111's shape one component further out. Nothing reads these counters back into a decision, so no behaviour diverges either way — measured in `tests/integration/contended-canteen-substitution-cost.test.ts`, a restored session counts, prisoner by prisoner, exactly what a continuous one counts over the same 6,000 ticks.
- **A stream re-seeded at restore does not make the restored session equal to a continuous one.** When a save omits a named stream this build registers, the restore seeds it from `deriveXoshiroState(masterSeed, name)` ([ADR 0038](./adr/0038-what-makes-a-save-compatible.md) §2) — which is deterministic and identical on every client, and is exactly the state a *new* session would have given that stream. What it is not is the state a continuous run under this build would hold: that run would have been drawing from the stream since tick 0. **The property claimed is the weaker one — same bundle, same state, every client, every load — and not "a restore is indistinguishable from having played on".** This is the same kind of recorded, bounded divergence as `JobSystem.performingSince` and the incident-response entries above, and it is bounded differently: it applies only to a stream the save does not carry, and only from the tick of the restore. A replay verifier (ADR 0009) may therefore not compare draws from a stream a bundle did not carry across a restore boundary. ADR 0009's evidence is a command stream from a seed rather than a bundle, so today no replay crosses one; if that changes, refusing such a restore becomes the honest answer and ADR 0038's decision §2 is the narrow thing to reverse.
