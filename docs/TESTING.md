# Testing contract

Lockstate treats tests as executable architecture. A feature is not complete because it appears to work in a browser; its behavior, boundaries and failure modes must be verifiable at the lowest appropriate layer.

## Supported commands

```bash
pnpm typecheck
pnpm test
pnpm test:watch
pnpm test:browser
pnpm verify
pnpm verify:assets
pnpm verify:deployment
pnpm verify:sql
```

`pnpm test` runs the complete Vitest suite once and fails when no test is discovered. `pnpm verify` typechecks test and production sources, runs the test suite and builds the production Cloudflare package.

`pnpm verify:sql` is separate from `pnpm verify` because it needs a PostgreSQL server: it applies every migration in `supabase/migrations/` and runs every pgTAP suite in `supabase/tests/` against a scratch database, using the compatibility harness in `scripts/sql/`. It is the check that can run when the Supabase local stack's container images are unreachable; it proves the SQL, not the hosted platform around it (see `docs/CLOUD_SAVE.md` for the cloud-save schema and `docs/TRUSTED_SERVICES.md` for the entitlement/challenge schema). **Four of the eight suites assert no behaviour at all**, and each is a rule over a system catalog rather than a list. `003_data_api_grants` pins the whole privilege surface for all three Supabase roles. `005_function_security_declarations` pins the function *declarations* — `prosecdef` and the pinned `search_path` — read back from `pg_proc`, because a suite that pinned privileges exhaustively and never read those two columns let a dropped `search_path` pass every assertion (#105 finding 5). `007_column_bound_coverage` enumerates every `text`/`jsonb`/`json`/`bytea` column in `public` from `pg_attribute` and requires each to name the mechanism that bounds it — a length check, an anchored regex, a closed value set, a BEFORE-row trigger, or a generated column — and requires that mechanism's catalog object to exist and to constrain that column (#189). `008_scalar_column_constraint_coverage` does the same for the numeric and timestamp columns, with one difference that matters: a scalar column may legitimately be unconstrained, so it has an allow-list — and an entry there must carry a real reason and **fails if the column later gains a constraint**, so acting on a finding forces the entry to be reclassified rather than left saying the state is unconstrained (#191). That rule reads constraints and nothing else, which let the other half of those reasons rot: two entries kept saying `CLIENT-WRITABLE … Open finding #194` after `20260824140000` revoked exactly the grants they named, and the suite stayed green because a column had *lost a grant* rather than *gained a constraint*. Each entry now also declares client-writability as a boolean checked against `has_column_privilege` for `anon` and `authenticated`, failing in both directions (#194, #260). All four are rules for the same reason: a list cannot notice a column, function or grant added tomorrow, and something added with no protection must **fail** rather than be merely un-asserted. A ninth gate lives on the TypeScript side rather than in pgTAP: `tests/foundation/rpc-status-vocabulary-contract.test.ts` asserts that every status each `SECURITY DEFINER` RPC can return is exactly the set the cloud client's row type names, in both directions — a status the database can return and the client does not name falls through an exhaustive `switch` silently, returning `undefined` at runtime with no compile error (#192). It checks the return path only, and says so: the request half needs a running PostgREST. `003_data_api_grants` also carries a rule of the same shape: no column whose default is `now()` may be written by a client role unless an allow-list entry gives a reason, because the four columns #194 found client-writable were found by an inventory rather than by a failing test — that suite pins what the grants *are*, not what they *ought to be* (#194). The other four suites do assert behaviour, and two of them assert every bound in **both** directions — refusing a value past the ceiling *and* admitting one exactly at it, because a database that refuses what the TypeScript contract permits is a defect rather than hardening (#105 finding 4). Separate from `pnpm verify` does **not** mean optional: it is a required CI step (see "Database provisioning" below). `pnpm test:browser` runs the Chromium project (`tests/browser/`) and is deliberately **not** part of `pnpm test` or `pnpm verify` — the ordinary suite stays fast, headless and browser-free. Separate is not optional: CI runs it as a required `browser` job, which provisions its own Chromium (see "Browser provisioning" below).

The measurement harness is likewise opt-in: `pnpm exec vitest run --config tests/perf/vitest.perf.config.ts`. Its files are named `*.perf.ts` so the default suite never collects them, and it asserts only correctness invariants — never elapsed time (see `docs/BENCHMARKING.md`). It covers persistence decode/save cost and, since #136, what one HUD repaint costs the localization runtime with its `Intl` formatters cached versus built per call (`tests/perf/localization-format-cache.perf.ts`) — reported as a ratio and a per-repaint figure, with the *guard* against the cache disappearing being a construction **count** in `tests/unit/services-localization.test.ts` and `tests/browser/ui-shell.spec.ts` rather than anything timed.

`pnpm verify:assets` is separate from `pnpm verify` for the same reason and by
the same rule: it reads the runtime atlas PNGs, which live in Git LFS, so it is
the only check that needs LFS content. CI runs it as a required `assets` job, so
ordinary runs stay on a cheap pointer-only checkout (see
[ADR-0014](./adr/0014-art-storage-and-runtime-asset-delivery.md)). Only `*.png`
is LFS-tracked; the atlas manifests and `asset-registry.json` are plain files, so
nothing in `pnpm verify` needs LFS content at all.

Separate does **not** mean optional, and a pointer-only checkout cannot pass it
silently. The validator recognises a Git LFS pointer and fails naming it rather
than treating an unfetched file as valid art, and the job asserts the PNG
signature and a size floor on every atlas before it even runs the validator. That
assertion is not belt-and-braces theatre: it is what caught `actions/checkout`
with `lfs: true` leaving pointers in place on this runner.

The `assets` job provisions `git-lfs` with `scripts/provision-git-lfs.sh` and
then fetches content with an explicit, path-scoped `git lfs pull` rather than
using `lfs: true`. On a self-hosted runner the workspace is already at the target
commit from the previous job, so checkout is a no-op, the LFS smudge filter never
runs, and `lfs: true` downloads objects that never reach the working tree. An
explicit pull materialises regardless, and takes a path filter so the job fetches
only the ~17 MB it reads instead of all 55 MB. Provisioning lives in the job that
uses it, idempotent and with no third-party apt repository, exactly as
`scripts/provision-postgres.sh` does for `verify:sql`.

The rejection modes themselves are proven in the ordinary suite.
`tests/contract/runtime-atlas-validation.test.ts` drives the same validator
against tiny synthetic fixtures — a missing direction, a short frame list, a
duplicate logical id, a drifting pivot, an oversized atlas, an out-of-bounds
rectangle, a stale registry — so a validator that stopped rejecting anything
fails `pnpm test` without needing any art at all.

## Database provisioning for `pnpm verify:sql`

`scripts/provision-postgres.sh` installs and starts what `pnpm verify:sql` needs on a Debian/Ubuntu machine and is safe to re-run:

```bash
scripts/provision-postgres.sh   # needs root or passwordless sudo
pnpm verify:sql                 # 268 pgTAP assertions
```

It is deliberately **version-agnostic**. It uses whichever PostgreSQL major version is already installed, or failing that whichever one the distribution ships, and installs the matching `postgresql-<major>-pgtap`. No third-party apt repository is added and no major version is pinned anywhere: the schema is executed and green on **PostgreSQL 16.13 + pgTAP 1.3.2** and on **18.6 + pgTAP 1.3.4**, and Ubuntu 26.04 does not package 16 at all. It then ensures the cluster is running and that the invoking user has a login role with SUPERUSER — the compatibility harness creates extensions and roles, so CREATEDB alone is insufficient. Set `DATABASE_URL` to point `pnpm verify:sql` at an existing server instead; the role step then does nothing.

CI runs that script and then `pnpm verify:sql` on the self-hosted runner, so the SQL is executed on every pull request. The same script is what `.claude/hooks/session-start.sh` uses for remote containers, so the two environments cannot drift into provisioning different databases.

A service container was rejected: `scripts/verify-supabase-sql.mjs` shells out to a local `psql` client that would have to be installed regardless, no published PostgreSQL image ships pgTAP, and the reason this check exists at all is to keep working where container images cannot be pulled.

## Default environment

Vitest runs in the Node environment by default. Pure simulation, protocol, serialization, migration, economy, navigation and deterministic scheduling tests must not import Phaser, touch the DOM or require browser globals.

A browser/E2E project may use Playwright or Vitest Browser Mode after a dedicated dependency and architecture review. Browser setup must remain explicit rather than silently changing the environment for every test.

**Approved browser project (issue #19).** `@playwright/test` (exact-pinned devDependency) drives Chromium against `tests/browser/`, run **only** via `pnpm test:browser` — never as part of `pnpm test` or `pnpm verify`. It stays explicit in exactly the way this section requires:

- Its specs are named `*.spec.ts`, and the root Vitest config collects only `*.test.ts`, so no browser file can be picked up by the default suite by accident.
- It uses its own Vite config and dev server (`tests/browser/vite.config.ts`), not the production Cloudflare build.
- It is devDependency-only and outside the production build graph — verified by building `HEAD` and `HEAD + browser project` side by side and confirming a **byte-identical** bundle. The claim is the identity, not the size: the two builds matched at 1,384.01 kB (gzip 360.73 kB) when that check was run, and the bundle has grown a great deal since — `docs/PERSISTENCE.md` records the step to 1,607.50 kB when the session runtime was wired in, and a production build at `9b6965a` reports 1,614.21 kB (gzip 425.43 kB) for `index-*.js` plus 231.35 kB for the worker chunk. Every size in this paragraph is anchored to a commit on purpose: nothing recomputes them, they move on most merges, and an unanchored "today" is a claim that ages the moment it is written -- this sentence carried 1,602.36 kB and 243.67 kB, neither of which was ever measured at the commit a reader would check. Re-running the comparison means building both sides again; the identity is the claim, and the figures are evidence from one run.

It exists because `fake-indexeddb` structurally cannot prove three things: durability across a real page navigation, what a real browser's `DOMException`s are actually named, and behavior under a genuinely exhausted storage quota (driven here through CDP `Storage.overrideQuotaForOrigin`, asserted via `navigator.storage.estimate()` so an ineffective override fails the test rather than passing vacuously). It found one real adapter defect — see `docs/PERSISTENCE.md`.

The **browser UI** (`tests/browser/ui-shell.spec.ts`, #65 and the HUD shell) is here on the same principle, not as a general licence to test UI in a browser. Five claims cannot be settled below this layer: that a real click on a real `disabled` button does nothing; that no `unhandledrejection` event fires; what a *computed* font stack and numeric variant actually resolve to; what `getBoundingClientRect` / `elementFromPoint` report for a layout at a given viewport; and what the DOM builders in `src/ui/hud/**` actually put on the page — the default suite runs in the `node` environment, so nothing headless ever executes `status-strip.ts`, and "the clock reads `--` until a session reports one" (#94) is a rendered-output claim rather than a mapping one. Everything else about the UI — the tab/collapse state machine, the view-model → display mapping that decides *what* the builders are told to show, the async-action gate's refusal and rejection-ownership rules, the design-token contract — is proven headlessly in `tests/unit/ui-*.test.ts`, in the default `node` environment with no DOM; a browser assertion on rendered text is paired with the mapping assertion underneath it rather than standing in for one. The browser layer found two layout defects that no unit test could have (a strip whose min-content width carried the tab bar off a 375px screen, and a minimap frame overlapping the tab bar at 768px); both now have assertions rather than a remembered viewport. It has since found a third defect of the same shape, in **child order** rather than in geometry: `paintAlerts` appended a newly-seen alert to the end of the list and updated the rest in place, so the drawn order was first-seen order — mounting with alerts `[a, b]` and updating to `[c, a, b]` laid out `a, b, c` (#209). Nothing headless could see it: the `node` environment never runs the builder, and the projection it disagrees with is correct. The order assertion is paired with a node-identity one, because the cheap way to make an order right is to empty the list and rebuild it, and that would silently discard the row identity `HudAlertViewModel.id` exists for.

Two later additions sit *inside* those five claims rather than beside them. That a refused command reaches the player (#207, extended to the world-drag route by #225) is a claim about rendered text, about computed style — the refusal line's `[hidden]` rule loses to the `display: flex` on the same selector unless it is written out, which is how the first draft of it shipped as a visible empty band — and about layout at 375px, where `hud.css` drops the alerts region entirely. That the save panel renders nothing outside the message catalog (#208) is a claim about what its builder puts on the page: it is checked by mounting the real panel in the `en-XA` pseudo-locale, where a string that never went through the localizer arrives unaccented and unbracketed, which is [ADR 0011](./adr/0011-localization-architecture.md)'s own stated purpose for that locale. The mapping underneath each — `refusalMessageKey` and the save panel's key registry — is asserted headlessly beside it, per the pairing rule above. #225 added the second route to the first of those: a finished world drag is delivered to the sink `mountHud` registers, and what the browser settles is that one gesture becomes **one** gated intent and that refusing it paints the line with no control marked, because the player pressed none. The tool that produces the gesture is proven headlessly beside it in `tests/unit/ui-build-tool.test.ts`, which is where "one gesture is one report" is asserted rather than assumed. #261 added a third route to the same claim, and it is the first one with no control on screen at all: the world's `KeyZ`/`KeyY` keys reach the HUD through the same tool, so what the browser settles is that a refused undo paints its own sentence -- not the build order's -- with nothing marked, while the keys themselves are measured against a real `WorldScene` in `tests/browser/world-scene-input.spec.ts` (including that a text field owning the keyboard silences them) and the routing is asserted headlessly in `tests/unit/ui-build-tool.test.ts` and `tests/unit/input.test.ts`.

Two claims were added here for the same reason and are worth naming, because both are about a *number the browser reports* rather than about rendered text:

- **Where the Build panel's last section is** (#143). The panel used to be its own only scroll container, so every catalogue row it gained pushed the "Enter coordinates" header further down inside it: at 1280x720 with a twelve-entry catalogue the header sat at y=845..889 in a panel clipped at y=638. The assertion measures the header's rectangle against the panel's client box at all five viewports the suite visits, with the panel unscrolled — a computed-`overflow-y` assertion would have passed *before* the fix as well, since the panel already had it. The catalogue is fed to the panel as view-model data, so the harness hands the real panel twelve entries; `BUILDABLE_REGISTRY` has two and the assembled app cannot yet show a third at all.
- **How many `Intl.NumberFormat` instances one repaint builds** (#136). The harness's `HudLocalizer` counts `formatNumber` calls and a `Proxy` construct trap counts constructions across one real `hud.update()`: 11 values formatted, 0 formatters built -- and only the second of those two numbers is asserted. Nothing headless executes the strip, so this is the only layer that can count what a real repaint really does.

Neither is a timing assertion; both are counts and positions, which is what keeps them out of `docs/BENCHMARKING.md`'s way.

The same three reasons apply to a **save-format migration**, which is why `tests/browser/local-save-migration.spec.ts` covers V1 → V2 (#50) here as well as in-process: a migration bites in production on a record an *older build* left in real origin storage, transported by structured clone rather than JSON and read back in a later page load by a build that only knows the new version. Its V1 records are built from the same checked-in `tests/fixtures/persistence/save-v1-in-progress.json` the in-process `tests/migrations/save-v1-to-v2.test.ts` uses, so the two layers cannot drift into disagreeing about what a V1 save looked like. This is an addition to the browser layer, not a replacement: the in-process migration tests remain the fast, primary proof, per "use the lowest layer that proves the behavior" above.

The **assembled application** (`tests/browser/app-shell.spec.ts`) is the only place the real `index.html` is ever loaded. Every other spec here drives a purpose-built harness page, which is the right shape for a module under test but means the page a player opens — renderer, HUD and save panel in one document, over real storage and real HTTP — had no coverage at all. Fifteen claims exist only once the pieces are assembled, and none can be settled a layer down: that Phaser's `Scale.RESIZE` canvas really is the size of the window and follows it across a resize; that `elementFromPoint` **and a real press** at the centre of the screen reach the canvas rather than the HUD, whose root is `pointer-events: none`; that every runtime atlas is fetched over HTTP and *decodes* at its manifest dimensions (a Git LFS pointer is served as `200 image/png` and only a decoder can tell the difference); that a prison created through the real save panel — panel → session controller → simulation worker snapshot → IndexedDB — is still listed after a real navigation; that every HUD control renders at the 44px `--tap-target` (the token is applied by CSS convention, and a token test cannot check a *rendered* box — a 24px control is one of the defects this layer already found by measuring); that pressing a real transport button reaches the real simulation worker over `postMessage` and comes back as a day counter that moves on screen (#94 — every layer of that is proven separately, and the defect was that they were not connected); and that the interface still mounts, and says why, when `Worker` construction throws (#82); that a control the simulation *refuses* says so on screen rather than to the console (#207 — with no prison created, "Place order" throws inside the real command sender, and what has to be proven is that `src/main.ts`'s own wiring carries that to the HUD: before the fix the only effect was a `console.warn` and `.hud` innerText was byte-identical before and after the press); and that **every interactive control on the page is reachable** — `elementFromPoint` at five points across each control (its centre and four points 20 % in from its edges) resolves to that control or something inside it, on every tab and at every viewport the suite visits, *and* every control is accounted for rather than merely visited: a control that is never laid out in any state the test reaches has escaped the check, so the two the responsive rules deliberately drop below 720px are named in the spec and anything else appearing there fails. That last one is the general form of a defect this layer had been blind to (#88): the save panel and the Build panel were two independently-positioned `fixed` layers, and with the Build panel's numeric fallback expanded — one tap from the default — it covered 91 % of the save panel at 1280x720 and all five of New prison, Save now, Export, Load and Delete did nothing, while every existing assertion stayed green — because presence and reachability are different properties and only the second is what a player has. Five sample points rather than one for the same reason at a smaller scale: on that layout at 900x600 the centre alone found 11 unreachable controls and the five found 13, the extra two being buttons whose lower fifth had been carried off the bottom of the viewport. Two are #149's: that a **second** prison loads in the same tab, in a second real `Worker` — the worker refuses every `simulation/initialize` after the first, so the page has to construct one per session, terminate the one before it and keep the renderer and the HUD attached across the swap, and only a browser has the thread (`tests/integration/session-second-load.test.ts` proves the composition, headlessly, against loopback transports); and that a `Worker` which cannot be constructed for a *later* session is reported on the panel and raised as #82's own notice rather than thrown, which needs a page that booted successfully and then had `Worker` taken away from it. The last two are #225's, and they are the world-drag route to the command #207 fixed on the panel route: that a wall refused after a **drag on the canvas** says so on screen (with the tool armed and no prison created, the real `BuildTool` reports the gesture, the HUD dispatches it and the real command sender throws — before the fix the drag went straight to that sender and its only report was a `console.warn`, and the mutation the issue predicted for it, deleting `onError` from the `BuildTool` options, was measured and survived the entire suite); and that **one drag is one transaction**, asserted over a tee on the real `postMessage` because a `transactionId` is minted on this thread and never echoed back, so no other layer can see it. The fourteenth is #146's, added after #264: that the **30-second autosave actually fires from play alone** — a prison created on the real page, a wall laid on the world, and a further generation reaching storage with no `pagehide` and no hidden `visibilitychange` in between, which is what separates the interval save from the best-effort lifecycle one that was the only automatic write before #146. The scheduler, the controller and the command sender each have complete unit tests; the join between them exists only in `src/main.ts`, because the sender is built at module scope and the controller inside `bootPersistence`. The interval is faked by shortening `window.setTimeout` calls of 30 s or more, which is deliberately narrower than `page.clock` — the simulation worker is a separate global scope and Phaser's `requestAnimationFrame` loop has to keep running, or the world drag is never processed. The fifteenth is #287's: that a save file the game **exported** can be **imported back**, which is the round trip the Import control exists for and the one claim in this file that needs a real download and a real file chooser as well as a worker and a storage backend. `SessionController.importInto` had been written, exported and reachable with no caller at all, so the application offered a download it could not read; the serialization layer's own round trip was never the gap (`tests/determinism/snapshot-restore-fidelity.test.ts` has proven that in-process for as long as it has existed), the player-reachable path was. What the browser settles is that the bytes the page produced are the bytes it reads: play a session, pause, save, Export, create a second empty prison, Import the downloaded file through a real chooser, then Save now — capturing from the worker the import restored into — and Export again, with the final payload equal to the exported one. The second prison is what keeps it non-vacuous (day one, tick zero, so an import that did nothing would compare against a fresh prison), and the control's four distinguishable refusals are asserted a layer down against a stub in `tests/browser/ui-shell.spec.ts`, because a save from a *newer* schema version is one this build cannot write. It deliberately does not re-test the HUD state machine, the responsive layout, the computed font stack, the camera transforms or the atlas schema: those are already proven in `tests/unit/ui-*.test.ts`, `tests/browser/ui-shell.spec.ts`, the Phaser-free `src/rendering/**` tests and `tests/contract/runtime-atlas-validation.test.ts`, and a browser test that repeats a headless one costs CI minutes and proves nothing new.

The **camera transforms** (`tests/browser/camera-coordinates.spec.ts`) are here for a reason that is narrower than the others and, on the evidence, the most necessary. `src/rendering/camera/coordinates.ts` reimplements Phaser's camera maths as pure functions so the renderer can convert coordinates without a live engine instance and the rules stay testable in the default environment. That reimplementation can be internally perfect and disagree with the engine that actually draws — and it was, for the whole life of the module. Issue #115: both functions modelled zoom as scaling about the viewport's corner while Phaser scales about its centre, so the build cursor was displaced by `origin × (1 / zoom − 1)` and a player could not place a wall where they clicked. The headless test could not fail, because it round-tripped each function through the other. Only a real camera can settle the claim, and only a real browser can hold one: `docs/CAMERA.md` explains why, and the spec compares `screenToWorld` against `camera.getWorldPoint` and `visibleWorldBounds` against `camera.worldView` at five zoom levels, drives a real mouse, and asserts that the old formula genuinely disagrees so a regression cannot pass. It deliberately does not re-test the tile-edge rule, `TILE_SIZE_PX`, zoom clamping or the culling margin: those are pure and already proven headlessly.

A **two-finger touch gesture** (`tests/browser/world-scene-touch.spec.ts`) is here because there is nowhere else it can be. A second finger needs a browser context created with `hasTouch` and CDP `Input.dispatchTouchEvent`; Playwright's own `page.touchscreen` places one finger, the default Vitest environment has no pointer events at all, and Phaser only delivers a second touch pointer because `WorldScene.create` calls `this.input.addPointer(2)` -- so every layer below this one is structurally unable to see a pinch. That is exactly what happened: `src/input/gestures.ts` is thoroughly unit-tested and `docs/INPUT.md`'s "Two fingers ... still move the camera" was carried by reading alone until #209's follow-up dispatched the first synthetic touch sequence this project has ever had. The spec asserts the pan is 1:1 and does not zoom, that separating and converging move the zoom in the right directions, that `ZOOM_BOUNDS` clamps at both ends, and -- the property that needs a real camera -- that the world point under the midpoint is **held** across all of it, read from Phaser's own `getWorldPoint` rather than from the project's `screenToWorld`, so the gesture cannot be confirmed by the transform it drives. It also settles a reading #209 recorded as unclassifiable: see `docs/CAMERA.md` on what an anchored zoom does to the scroll, and the two specs at the end of the file that test the alternative explanation (a harness carrying state across a touch boundary) instead of assuming it away. It deliberately does not re-test `TouchGestureTracker`'s arithmetic or `zoomAtScreenPoint`'s literals: both are proven headlessly, and this layer is for the wiring between them and a real engine.

**Whether a DOM lifecycle event reaches its handler at all** (`tests/browser/lifecycle-save.spec.ts`) is here for a reason this layer had not been used for before: a fake event target is not merely a weak proof, it is a *vacuous* one. It receives whatever a test dispatches at it, so it agrees with the browser no matter which object the browser really dispatches at. `LifecycleSaveHandler`'s unit tests were complete and green while its `pagehide` listener, registered on `document`, never fired once in production (issue #92) — `pagehide` is dispatched at `Window` and window events do not propagate down to the document. The spec therefore drives a real navigation to obtain real, browser-generated lifecycle events (recorded synchronously into `sessionStorage`, which survives the navigation even though the fire-and-forget save may not) and requires both of them, in the order the browser delivered them. It deliberately does not assert *which object* each listener is registered on: `visibilitychange` bubbles from `document` up to `window`, so an implementation that registered both listeners on `window` would receive both events and be correct in production, and failing it would pin the wiring's shape rather than its contract — which injected target each listener lands on is a statement about `LifecycleSaveOptions.targets`, and the unit tests make it there. It also does not assert that the lifecycle save reached IndexedDB: that save is best-effort by design and the interval autosave is the durability mechanism, so asserting it would test the wrong contract. Confirmed to have teeth by restoring the #92 wiring — both listeners back on `document` — under which the whole unit file still passes and this spec records `['visibility-hidden']` where it requires `['pagehide', 'visibility-hidden']`.

A single non-DOM Web API can be reviewed and approved narrower than a full browser/E2E environment: `fake-indexeddb` (a pure-JS, dependency-free `indexedDB` implementation, devDependency-only) is approved for testing `src/persistence/local/indexeddb-store.ts` specifically — see `docs/PERSISTENCE.md`. Tests using it import a fresh `IDBFactory` instance explicitly per test rather than the `/auto` global-polluting entry point, so the default Vitest environment stays `node` and unaffected for every other test.

## Browser provisioning for `pnpm test:browser`

`@playwright/test` is pinned but its browser binaries are not in the package and are not checked in, so a machine that has never run the suite fails with "Executable doesn't exist". `scripts/provision-playwright-browsers.sh` installs what the suite needs and is safe to re-run:

```bash
scripts/provision-playwright-browsers.sh   # no root, no apt, no third-party repository
pnpm test:browser                          # 101 tests
```

The suite starts its own dev server on port 5183 and **never reuses one that is already listening**. It used to reuse outside CI, which meant a run could attach to a server started from a different checkout of this repository — the suite then loaded that tree's `src/**` and reported on code the developer was not editing. That was observed, not theorised: a deliberately broken design token came back green because the page under test came from another worktree. Refusing to reuse turns that into a loud "port is already used"; set `LOCKSTATE_BROWSER_TEST_PORT` to run a second checkout alongside the first. The CI job sets it to a port the kernel just handed out, because the self-hosted runner shares its host with active development and 5183 is regularly taken there — the first run of that job died on exactly this.

Chromium only — `playwright.config.ts` pins `browserName: 'chromium'` and nothing here launches a second engine. It runs headless (the config never sets `headless: false`), so no display, xvfb or `DISPLAY` is required. The download is ~280 MiB (Chromium, the headless shell and ffmpeg) and unpacks to ~920 MB under `PLAYWRIGHT_BROWSERS_PATH`, default `~/.cache/ms-playwright`.

**Idempotent**, in the same style as `scripts/provision-postgres.sh`: it checks before it acts, and the check is the launch the suite itself performs. When the browser is already on disk and runs, it downloads nothing and exits in a few seconds — which, on the self-hosted runner that keeps its cache between jobs, is every run after the first.

It also carries the two environment-specific facts observed on Ubuntu 26.04 under WSL2, so nobody has to remember them:

- Playwright 1.56.1 has no build listing for Ubuntu 26.04 and refuses outright (`ERROR: Playwright does not support chromium on ubuntu26.04-x64`). The script retries with `PLAYWRIGHT_HOST_PLATFORM_OVERRIDE=ubuntu24.04-x64`, which downloads the 24.04 build; that build runs correctly and needs no override at run time. The retry happens **only** after an unmodified install has failed with that exact message, so it stops overriding by itself on a Playwright release that supports the host natively, and it never masks an unrelated install failure.
- `playwright install --with-deps` fails for the same reason, needs root, and installs a list of packages on the assumption that one is missing. The script launches the browser instead, and if that ever fails it reports exactly which library `ldd` says is missing. On this host nothing is: `ldd` on both the Chromium binary and the headless shell reports no missing library, and the suite is green against a browser tree installed into an empty directory.

CI runs that script in the `browser` job and then `pnpm test:browser`, so the layer that found the adapter defect in `docs/PERSISTENCE.md` and the two HUD layout defects above runs on every pull request instead of when a human remembers. The job is ordered after `assets` for two reasons, neither a data dependency: a browser run is a couple of minutes on a single self-hosted runner and there is no point spending it on a tree that does not build; and `assets` has already materialised the runtime atlases into the shared workspace, so the job's own path-scoped `git lfs pull` transfers nothing. That pull stays regardless, because the job has to be correct on a cold workspace — `app-shell.spec.ts` asks a real browser to decode the art, and a pointer-only checkout is exactly what it exists to catch. The job also fails if the suite skipped its way to green: `playwright test` already errors when no test matches and `forbidOnly` is on under CI, but neither covers a suite that ran and skipped.

## Test layers

| Layer | Purpose | Normal location |
| --- | --- | --- |
| Unit | One pure module, algorithm or invariant | Colocated `src/**/*.test.ts` |
| Contract | Typed boundary, schema, protocol or repository contract | `tests/contract/` or a named folder under `tests/` |
| Integration | Two or more real project modules wired together | `tests/integration/` |
| Determinism | Same initial state and command stream produce identical state/hash | `tests/determinism/` |
| Migration | Versioned fixture upgrades and forward-only save compatibility | `tests/migrations/` |
| Browser E2E | Real browser storage/durability, real `DOMException` names, real quota exhaustion, save migration off real storage, whether a real DOM lifecycle event reaches its handler, agreement between a pure transform and a real Phaser camera, what a two-finger touch gesture does to a real camera, and the assembled page: canvas sizing, hit-testing, image decode, a second session in a second real `Worker` | `tests/browser/`, via `pnpm test:browser` (own command, required CI job) |
| Measurement | Reported size/timing evidence with no timing assertions | `tests/perf/`, opt-in via its own Vitest config |
| Benchmark | Repeatable performance evidence, never correctness by elapsed time | `benchmarks/` and `docs/BENCHMARKING.md` |

Use the lowest layer that proves the behavior. Do not use a browser test to cover logic that can be proven by a fast headless unit or contract test.

## Naming and placement

- Use `*.test.ts` for executable Vitest files.
- Colocate narrow unit tests with their implementation.
- Put cross-module, persistence, protocol and integration fixtures under `tests/`.
- Keep reusable test-only helpers under `tests/helpers/`; production modules must not import them.
- Use descriptive behavior names. A failing test should identify the broken invariant without opening the implementation first.
- Avoid large snapshots for evolving UI or state. Prefer focused structural assertions and purpose-built fixture checks.

## Determinism and isolation

Tests must not depend on:

- execution order or another test's side effects;
- current wall-clock time;
- live network services;
- unseeded randomness;
- the developer's keyboard layout, locale, timezone or home directory;
- mutable process globals that are not restored;
- files left by a previous run.

Inject clocks and deterministic RNG interfaces into production code. Use fake timers only when the test owns the complete timer lifecycle, and always restore them. Seed values and command streams must be visible in the test or fixture so failures can be reproduced.

Vitest is configured to clear/restore mocks, stubbed environment variables and stubbed globals between tests. Tests remain responsible for closing workers, servers, database handles, timers and temporary directories they create.

## Network and external services

Unit and contract tests must not make live network calls. Supabase, Cloudflare and other provider behavior should be exercised through explicit adapters, local emulators where justified, recorded schema fixtures or separate deployment smoke tests. A test requiring credentials is not part of the ordinary pull-request test gate.

## Worker and renderer boundaries

- Simulation tests import the headless simulation API directly, not a Worker wrapper.
- Worker protocol tests validate message parsing, version negotiation, invalid-message rejection and round trips independently of Phaser.
- Renderer tests consume immutable snapshots/deltas and must not mutate worker-owned state.
- Phaser scene tests belong to an explicit renderer/browser layer and cannot become the only proof of simulation behavior.

## Fixtures and migrations

Persistent fixtures are versioned inputs, not opaque generated blobs. Keep them small enough to review, record the schema/build version and never rewrite an old fixture merely to make a migration test pass. Add a new expected fixture or migration when the contract changes.

## Pull-request evidence

Every issue and pull request must state which layers changed and include the commands actually executed. At minimum, ordinary changes require:

```bash
pnpm typecheck
pnpm test
pnpm build
```

Deployment-sensitive work also requires `pnpm verify:deployment`. Work touching `supabase/` or `scripts/sql/` requires `pnpm verify:sql` locally as well — CI runs it, but reviewing SQL that has never been executed is what produced the defects recorded in `docs/CLOUD_SAVE.md`. Performance-sensitive work requires a benchmark scenario and result evidence under the benchmark contract; elapsed-time assertions do not belong in unit tests.

## Coverage policy

There is no arbitrary repository-wide percentage threshold during the pre-alpha foundation. New behavior still requires tests. Coverage thresholds may be introduced only after representative systems exist and uncovered risk can be mapped to meaningful gates rather than a vanity number.

## Current executable baseline

`tests/foundation/repository-contract.test.ts` guards the pinned Node/pnpm metadata, strict compiler options, test-source inclusion and the rule that an empty suite cannot pass. It is a foundation contract, not a substitute for system-specific tests.

`tests/foundation/ci-configuration-contract.test.ts` is its sibling for the files that describe how the project is built, checked out and deployed. Issue #138 found several of those enforced by nothing, each for the same reason: the configuration and the check that is supposed to enforce it live apart, so editing one and not the other leaves the suite green. It asserts three agreements mechanically:

- **Every header `public/_headers` sets is asserted somewhere in `scripts/verify-deployment-preview.mjs`**, and every header on the `/*` rule appears in that script's `SECURITY_HEADER_BASELINE` with the same value. Note the direction. The verifier checks its baseline against a real preview response, which catches a header *deleted from or weakened in* `public/_headers` — the mutation that used to survive, where removing three of the four security headers left every gate green. This test checks the reverse inclusion, which catches a header *added to* `public/_headers` and asserted nowhere. Neither direction substitutes for the other. A third check holds the exact set of header *names* the `/*` rule must carry, which is the one direction the two inclusion checks cannot cover: deleting a header from `public/_headers` **and** from `SECURITY_HEADER_BASELINE` in the same change satisfies both of them, and that is precisely the shape of #138's surviving mutation one level down. There is now a **Content-Security-Policy**, along with HSTS and cross-origin isolation ([ADR-0021](./adr/0021-http-response-security-headers.md), closing #105 finding 12). Note what is and is not gated. `pnpm verify:deployment` runs `vite preview`, which serves `dist/` through workerd and so applies `public/_headers` exactly as production does — that is a real check that the headers reach a real response, and CI runs it. Nothing checks that the policy still lets the renderer run, because the verifier never opens a browser and the browser suite's server (`tests/browser/vite.config.ts`) deliberately loads no Cloudflare plugin and therefore applies no `_headers` at all. The renderer's requirements were measured by execution when the policy landed and are recorded in ADR-0021; a Phaser upgrade that began needing `'unsafe-eval'`, or a build that started emitting a `blob:` worker, would pass every check here and break the page.
- **Every executable file with a shebang is matched by a `.gitattributes` LF pattern.** Mode bits come from `git ls-files -s` and the resolved attribute from `git check-attr`, so this tracks what git will really do on checkout instead of re-implementing gitattributes pattern matching.
- **Every `scripts/provision-*.sh` is called by a workflow or by `.claude/hooks/session-start.sh`**, or is listed in the test's `INTENTIONALLY_MANUAL` map with the reason. That map is empty today; all four scripts are wired to a gate.
`tests/foundation/unconsumed-content-contract.test.ts` makes "declared but unconsumed" a checked state instead of something a sweep rediscovers (issue #141). A content id referenced by nothing -- no `.ts` file under `src/` or `tests/`, excluding `src/content/` itself, because content referencing content is not consumption -- must appear in one of two lists with a reason: `PROTECTED_BY_DECISION` for the ids an accepted decision depends on, `AWAITING_CONSUMER` for the ones nothing names yet. Both directions fail: an id that is removed from a catalog while a list still accounts for it, and an id that gains a consumer while a list still says it has none. The first is the point -- `room.delivery-bay`, `room.storage-room` and `object.loading-dock-door` are all unreferenced *and* load-bearing for ADR 0017 and #99, and deleting one of them leaves every other test file in the suite green.

It gates the narrower measure deliberately. "No consumer in `src/` outside the catalogs" is the honest answer to "does the game use this" and covers 53 of the 62 declared ids; gating that would mean 53 entries whose reason is uniformly "the system that would use it is not wired yet". Both figures are computed and asserted by the test rather than written here, because this sentence said 58 for as long as it did with nothing recomputing it. `src/content/validate-catalog.ts` already argues this trade-off for enum discovery, and its conclusion holds here: a list nobody reads enforces nothing.

`tests/foundation/navigation-deferred-status-contract.test.ts` is the same family applied to an *exported accessor* rather than a content id, and it holds a decision open in both directions (issue #177). ADR 0007's deferred-status section named `PathRequestQueue.getPending(id)`/`pendingIds()` as the answer to its "structured deferred status" requirement, and neither ever gained a caller: measured, both were free to `return undefined`/`return []` with the whole suite green. The ADR's 2026-08-25 amendment deleted them, because the decision they were named for — two states, no deferred event stream — is what all six production callers of `requestRoute` already do with `NavigationSystem.getResult(id) === undefined`, and queue depth is `size()`. This gate keeps the deletion attached to its record: it fails if either name reappears anywhere in `src/`, if the amendment goes, or if the sentence the amendment amends is edited rather than amended, and it fails if any of the six consumers stops reading the two-state status or any of the three `loadSnapshot` paths stops clearing a stale request id — the case `getPending` would have diagnosed and which is prevented instead. Re-adding the accessor was measured against the rest of the suite: **2 failures, both here**, and nothing else. Two of its own assertions were sharpened the same way — the restore check is scoped to the `loadSnapshot` body because a whole-file search for the id being set to `undefined` matches `setPathRequestId`'s own signature and survives the mutation, and the comment-stripping control exists because the module and the ADR both name the deleted accessors in prose saying they are gone.

**A text assertion does not imply visibility, and the browser layer now says so where it matters.** `toContainText` and `toHaveText` pass on a locator inside a `display: none` subtree, or on one with a zero-size box — so a rendered-text assertion can be green about something no player can see. That is how the #82 alert survived: `app-shell.spec.ts` asserted the alerts list contains "Simulation unavailable" and it did, in the DOM, while measured at 1280x800 with `Worker` blocked the row was `offsetParent === null` with a 0x0 rect and `.hud` innerText never mentioned it (#220 — and note `.hud__corner` computed to `display: block` there, so this was the Alerts section starting collapsed, not the ≤720px media query). The assertions that should be painted are now paired with `toBeVisible()`: the save panel's empty row and status line, the refusal row on both of its paths, the unavailable row on the real page with `Worker` blocked, and the incident badge — that last one because a badge is the non-colour carrier of the state, so one that is present and unpainted defeats its own purpose. Two of them were proven with a hide-the-element mutation (`display: none !important` on the refusal row, then on the save-panel empty row), each of which fails only on the new visibility assertion.

The #82 guard itself was **deliberately left DOM-only** for one release, with the measurement written above it, because pairing it with `toBeVisible()` would have failed while the sentence was still routed into the alerts list — where that alert should go was #220's design decision and not a test's to make. #220 settled it: the sentence now goes to `.hud__unavailable`, a HUD grid row of its own that is laid out at every width and needs no section opened, and the guard asserts `toBeVisible()`, a non-zero rendered box and that `.hud` innerText contains the sentence, at 1280x720 and again at 375x812. The comment above it records the old measurement, so the history of the false pass stays readable at the assertion that used to be it.

`tests/foundation/composition-root-contract.test.ts` guards the wirings only `src/main.ts` performs. The composition root is by construction the one module no unit test executes -- it reaches for browser globals, constructs a `Worker`, mounts into a real document and runs at import -- so every component it connects is tested in isolation and the *connecting* is tested nowhere. Three defects have landed in exactly that gap, each with a flawless component behind it: #82 (`mountInterface` inside `bootPersistence`, so a browser that could not start a worker got a canvas and nothing else), #199 (`WorldScene` reading `window.localStorage` itself rather than taking the injected store) and #146 (nothing calling `markDirty`, so the 30-second autosave never fired). Measured on the last of those: removing the one wiring line from `main.ts` restores the defect exactly, with `tsc` clean and 1,579 tests passing.

The gate is textual and its bound is stated in the file: it proves a wiring is **written**, not that it works -- the behaviour of each seam belongs to that seam's own tests, and the assembled page belongs to `tests/browser/app-shell.spec.ts`. What it buys is the one thing neither layer gives, that deleting a line from the composition root fails something. Entries are deliberately few: each names a defect that actually happened, and a wiring nobody has broken does not earn a line, because a list of every call in `main.ts` would be a second copy of the file that nobody reads.

That bound is not decorative, and issue #264 measured what it costs when the other half is missing. Prefixing the `markDirty` wiring with `if (Number.isNaN(0))` keeps the pinned substring byte-for-byte and makes the line unreachable; `tsc` stayed clean and the whole Vitest suite stayed green, because the browser backstop this paragraph points at did not yet exist for #146 -- `grep -n "autosave\|markDirty" tests/browser/*.spec.ts` matched nothing. It exists now: `app-shell.spec.ts` creates a prison, lays a wall on the world and requires a further generation to reach storage from the interval alone, with no `pagehide` and no hidden `visibilitychange` in between. The reading half of the pair was not weakened to get there -- it is correct for what it claims, and what it claims is not behaviour.

`tests/foundation/fault-code-reachability-contract.test.ts` is the third of that family and its subject is the worker's refusal vocabulary. `ProtocolFaultCode` is a closed twelve-member enum, and it has twice been found carrying members nothing could produce: #139/#184 (`unsupported-protocol-version` and `unknown-message-kind`, because the worker computed the decoder's classification and reported a hard-coded `invalid-message` instead) and #187 finding 2 (`duplicate-message` and `sequence-gap`, because every kernel refusal reported `invalid-state`). Both times a person found it by reading the enum and the whole suite was green. A code the worker cannot emit is a reason the main thread can never be given, so it is now a gate: an unemitted member must be recorded with a reason, and a recorded member that gains a producer must have its entry removed. The list is currently **empty**, which is the assertion -- the same shape as `ui-orchestration-boundaries`'s deliberately-empty manifests.

Two things about that file are worth reading before copying it. First, it scans the **producing surface only** -- `src/simulation/protocol/decode.ts` and `src/simulation/worker/**` -- because four fault-code spellings appear elsewhere under entirely different vocabularies: `sync-engine.ts`'s `PullResult.reason`, `simulation-message-keys.ts`'s worker-*state* label, `worker-session-host.ts`'s consumer-side `error.code ===` comparison, and `kernel.ts`'s own `CommandRejectionKind` discriminant. A repository-wide scan would count all four, so if the worker ever stopped emitting `invalid-payload` the gate would stay green on the strength of an unrelated union in the persistence tree. Second, and this is the part that generalises: while the vocabulary is *fully* reachable, widening that scope cannot make any of the main assertions fail -- more matches when everything already matches changes nothing, and that mutation **survives**. So the scope is pinned by a negative control that asserts those four foreign occurrences exist and are outside the surface, rather than by an argument in a comment. The comment-stripping in the same file is the opposite case and says so: measured across the producing surface, no fault code appears in a comment without also appearing in code, so replacing the stripper with the identity function survives too, and the file records that it is precautionary there rather than load-bearing.

`tests/foundation/challenge-rejection-code-reachability-contract.test.ts` is that file's sibling for the other closed refusal vocabulary, and the larger one: `ChallengeRejectionCode` has twenty-three members and sits on the trust boundary [ADR 0009](./adr/0009-challenge-verification-strategy.md) describes, where the code is the difference between "your build is too old" and "these hashes disagree with the replay". It has **two** directions where its model has one, and the reason generalises. Issue #264 S4-S6 found three members — `evidence-too-large`, `command-after-final-tick` and `objective-metric-missing` — that no test in the suite reached: each was mutated to a no-op, the last in the `tsc`-clean `?? 0` form that returns `verified` with `rankedScore: 0` for a run whose objective metric the replay never produced — `verified` being the one tier ADR 0009 makes eligible for public ranking — and each survived with zero delta. An emission-only gate would have been **green throughout that**, because all twenty-three do have a `reject(...)` call site; what was missing was a test, not a producer. So this gate asks both questions: every code must appear in `src/services/challenges/verification.ts`, the one module that constructs a rejection, *and* in `tests/unit/services-challenge-verification.test.ts`, the tests that drive the pipeline. Both lists are empty, and both fail in the stale direction.

Its scope needs the same negative control and needs it harder. `'invalid-shape'` is spelled by five other result unions under `src/` — including one in the pipeline's own directory, `ChallengeDefinitionAuthenticationResult` in `challenge.ts` — and by the five test files that drive those, so both "scan `src/services/challenges/`" and "scan `tests/`" are already too wide, and ten foreign occurrences are asserted to exist outside both surfaces. The sharper case is why `CHALLENGE_REJECTION_CODES` was moved into `src/services/challenges/rejection-codes.ts` instead of staying beside the pipeline: the declaration spells all twenty-three literals, so a producing surface that contained it would report every code emitted *unconditionally*, whatever the pipeline did. That is asserted rather than assumed. The comment stripping here is the precautionary case and the file says so: measured, neither scanned file spells a code in a comment without also spelling it in code, so an identity stripper leaves all six assertions green.

The gate is textual and states its bound: "named by an exercising test file" is a floor, not proof that a test drives the code. The runtime proof is the behavioural tests beside it, which is why #264's three findings needed both halves — a reachability gate satisfied by an allow-list entry is not the same thing as coverage. The same change replaced three self-comparisons in that file with field-sensitive assertions. `expect(seen[0]).toEqual(challengeDefinitionBytes(definition))` compares a function's output to its own output and therefore holds for *any* function of the definition, including one that discards `limits` and both allow-lists — which is exactly what #264 S1 did, with the whole suite green. The replacements enumerate the leaves of the fixture (`tests/helpers/field-sensitivity.ts`, nested: `limits.maxTicks`, not `limits`) and require each one to change the signed bytes, the definition hash and the evidence hash. Enumerating rather than naming is the point: #264 S2 and S3 are both cases where the guard tampered a field the mutation happened to keep. The self-comparison itself is **kept and labelled**, in the shape `tests/unit/camera-coordinates.test.ts` records for the assertion that let #115 ship: it is not the proof, it is the link that pins the bytes the verifier is handed to the function whose field sensitivity is proven exhaustively next to it.

`tests/foundation/message-kind-reachability-contract.test.ts` is the third reachability gate, after the two above, and its subject is the thing both of theirs travel on: the eighteen **protocol message kinds** of [ADR 0003](./adr/0003-simulation-worker-protocol.md). `tests/foundation/` gated commands, content ids, input actions, fault codes and challenge rejection codes, and gated message kinds nowhere — and issue #274 finding A2 established that the gap was live. **Nothing in `src/` has ever sent a `protocol/handshake`.** Every occurrence is the receiver, the kind list, the schema or the transfer switch; `WorkerSessionHost.initialize` sends `simulation/initialize` as the worker's first message and `handleInitialize`'s guard accepts it because the state is still `uninitialized`, so decision 4's version and capability negotiation happens for nobody and `WorkerState`'s `'ready'` is a state no `transition(...)` call reaches. Verifying that against the tree found two more the audit had not named: `protocol/ping` has no sender either, and neither does `simulation/event`, which no main-thread `switch (message.kind)` even has a case for. With `simulation/delta` — #274 A1's half that holds — that is **four of eighteen kinds declared, schema-checked and sent by nothing**, each now recorded with a reason and failing in the stale direction the moment it gains a sender.

Its trap is a shape rather than a scope, and that is the difference from its two models. `src/simulation/worker/state-machine.ts:444` reads `private handleHandshake(msg: Extract<MainToWorkerMessage, { kind: 'protocol/handshake' }>)`, and so does the handler for every other main-to-worker kind: seven annotations containing the exact substring `kind: '<K>'`, all seven of them **receivers**, all seven inside the one module that by construction can send none of them. A gate written as a substring scan would have reported all seven sent and been **green on A2 the day it was written** — measured, by dropping the trailing comma from the send pattern: `unsentMainToWorker` goes from `['protocol/handshake', 'protocol/ping']` to `[]`. So a send is `kind: '<K>'` *terminated by a comma*, an object-literal property, which is how all seventeen real send sites in `src/` are written and which mechanically excludes the type positions, the `case '<K>':` labels in both the receiving switches and `transferables.ts`, the bare literals in the kind lists, and the `kind: z.literal('<K>'),` in the schemas. The file states the rule's own bound: a send written with no trailing comma would be missed, which fails in the safe direction, and a *type* literal carrying a second member would be counted, which the direction check refuses because a main-to-worker kind cannot be constructed inside `src/simulation/worker/`.

That is also why `MAIN_TO_WORKER_MESSAGE_KINDS` did **not** need moving out of `types.ts` the way `CHALLENGE_REJECTION_CODES` did. The declaration, the eighteen schemas and the transfer switch all sit inside the scanned surface and all spell every kind, and none of them contributes a send — because here the shape and not the file list is what separates sending from naming. The test asserts that rather than assuming it. Scope still matters at one boundary and it is load-bearing there, unlike in either model: `tests/contract/` and `tests/unit/worker-state-machine.test.ts` send all four of the unsent kinds in exactly the shape the scan matches, so widening the surface from `src/` to the repository turns every entry green. Eight sending test files are asserted to exist and to be outside the surface, which doubles as the positive control that the pattern finds real sends at all.

The second direction is **provocation**, and it is derived rather than listed. `protocol/handshake-accepted` and `protocol/pong` *are* constructed (`state-machine.ts:453` and `:467`), so a send-only gate reports both fine — but both sites sit inside `handleHandshake` and `handlePing`, whose only trigger is a kind nothing sends. The test splits the state machine into class members, reads each member's handled kind from the same `Extract<...>` annotation that makes a substring scan wrong, and calls a worker-to-main kind reachable only when one of its send sites is unprompted (`fault`, `publishClockState`, `publishStatusCounts`) or sits in a handler for a kind the main thread really sends. So six of eighteen kinds are dead, not four, and wiring the handshake makes two entries stale in one run — its own and `protocol/handshake-accepted`’s; `protocol/pong` waits on `protocol/ping`, which is the second half of the same one-line fix. The comment stripping here is precautionary and the file says so: measured across all 262 files under `src/`, no comment spells the send shape at all, so an identity stripper leaves every assertion green.

**What the gate does not do is decide.** Whether `protocol/handshake` should be sent, deleted, or folded into `simulation/initialize` is an ADR 0003 decision-4 question on #274's owner queue; the gate records the state and makes any answer to it visible.

Two of its assertions exist because its own evidence went stale, and they are the part worth copying. The entry for `simulation/event` named the main-thread modules that `switch (message.kind)` and called them "the complete set"; #283 added a fifth, `src/ui/simulation-alerts.ts`, whose own header calls itself the third translator of worker messages, and every assertion in the file stayed green because the entry's *conclusion* — that nothing reads `simulation/event` — was still true. An absolute that is nearly true reads as true. So the enumeration is now derived from the scan: the set of dispatchers is pinned, every module in it must be **named in the entry** (the assertion #283 would have failed), and each is required to have a `default` and no `simulation/event` case, which is what the entry actually concludes. The count *word* in the sentence is spelled from the measurement rather than typed beside it, and that detail was itself measured: written the obvious way, as `toContain('the five main-thread modules ...')`, the check is satisfiable by changing the numeral in the sentence and the numeral in the assertion together — one search-and-replace, and exactly the edit a sixth dispatcher would prompt. Deriving the numeral from the scanned count leaves nowhere to say "five" but the sentence itself.

The second is about how the file cites code at all. Nine of its citations were line numbers pointing at code #283 had moved — +67 lines in `state-machine.ts`, +98 in `types.ts` — while the identical citations here and in ADR 0003 were corrected in the same change, because a human remembered the docs and nothing in the suite could check either. A line number is not a fact about the code; it is a fact about every insertion above it, so no gate can verify one without re-deriving it. A symbol name is a fact about the code, so the citations are now written `<basename>.ts#<symbol>` and `ANCHORED_CITATIONS` requires every anchor to name a declaration the cited module still makes. The scan is scoped to the file's comments and allow-list reasons rather than its whole source, and that is load-bearing rather than tidy: measured, a whole-file scan sweeps up the assertion's own expected-value list, so a citation deleted from a sentence stays green. Its bound is stated in the file — it proves the name is declared in the cited module, not that the declaration is the one the sentence means, which is still strictly more than a line number could prove. The convention is deliberately confined to that one file for now; extending it is a separate change with its own review.

`tests/foundation/unconsumed-action-contract.test.ts` is the same shape for the semantic input actions, and #200 asked for it by name. **Eleven are declared and nine have a reader**; when the gate was written it was nine and four. `src/rendering/scene/world-scene.ts` polls `isActive` for `camera.up`/`camera.down`/`camera.left`/`camera.right`, and switches on `camera.zoom.in`/`camera.zoom.out`/`build.cancel`/`edit.undo`/`edit.redo`. The other two -- `selection.primary` and `build.confirm` -- are declared, given a locale string apiece, and read by nothing. It was five, and three of those five were bound to keys a player could press: measured in a browser before #200 item 2, `Equal` and `Minus` left the zoom at 1 across ten presses and `Escape` neither cleared a pending wall run nor stopped it committing. The suite could not tell: deleting the `Equal` binding and deleting the `Escape` binding each left it green. Wiring them is what moved this figure, and this gate is what made the move visible. The undo pair (#261) moved it again from the other end -- both arrived declared *and* consumed in one change, so the allow-list never held an entry for either, and only the denominators moved. A reader means the action id as a single-quoted literal in a `.ts` file under `src/`, **excluding `src/input/` itself** -- declaring an action, binding a key to it and constructing an event carrying it are what the input tier does to *describe* a control, and `src/input/pointer.ts` returning `{ action: 'build.confirm', ... }` is the clearest case, because the array it returns is discarded by its only caller. Unlike its content sibling this gate does not count `tests/`, because here the strict measure needs two allow-list entries rather than fifty-three. Both directions fail, and that is what makes it a gate rather than a note: wiring `build.cancel` to `WorldScene.cancelBuild` -- #200 item 2 -- failed the stale check until its entry went, which is how three of the original five left the list, and deleting an unconsumed action fails the still-declared check with the reason it was listed for. Which of those two happens is #200 item 3, an owner decision against `AGENTS.md` boundary 10 and #141, so the list records the two remaining facts and decides nothing. The comment stripping is load-bearing here in a way it is not everywhere: `world-scene.ts` carries comments naming the very ids that have no reader, so an unstripped scan reports them consumed by the sentences saying they are not -- measured, that mutation fails the gate.

`tests/foundation/unreachable-invariant-contract.test.ts` makes "an exported invariant enforcer that nothing calls" a checked state rather than something a sweep rediscovers (issue #159). Every exported `assert*` function under `src/` must have a production call site — in another `src/` module, or elsewhere in its own module, which is the shape `assertGaplessSchedule`'s module-load loop over `DEFAULT_REGIME_SCHEDULES` has — or appear in `INTENTIONALLY_UNWIRED` with the reason. A call from `tests/` is recorded and is deliberately **not** sufficient: #158 declined to write a test for `assertGaplessDeploymentSchedule` because "testing a function nothing calls only converts dead code into tested dead code", so a gate satisfiable by that change would be a gate in name only. Both directions fail: an enforcer that loses its last production call site, and an allow-list entry that gains one or that names a function the scan no longer finds. `assertGaplessDeploymentSchedule` is the one entry, because whether to wire it into the deployment-schedule construction path or delete it is an open owner decision (#159 item 1), not an implementation detail. Its scanning rules live in `tests/helpers/invariant-enforcers.ts` and are exercised against fixtures in both directions, the same split `canonical-iteration-contract.test.ts` uses; comments are stripped with `canonical-iteration.ts`'s existing stripper rather than a second copy of that rule, and that is load-bearing — with the stripper replaced by an identity function, a commented-out call reads as a real one and the gate's main assertion goes green while nothing calls the enforcer.

`tests/foundation/art-catalog-generator-contract.test.ts` guards the one generator in this repository whose output is committed. Issue #141 found `tooling/build-source-art-catalog.mjs` invoked by nothing at all — not `package.json`, not a workflow, not another script — so editing an input silently did not regenerate the committed catalog. It is now `pnpm content:source-art`, and the test asserts it stays reachable, stays documented with the command an operator types, and refuses git-lfs pointer inputs **before** it deletes the published output. The generator itself still cannot be run in a pointer-only checkout without destroying 23 tracked images — measured with the guard removed: it exits 0, reports success, and republishes 132-byte pointer files under content-addressed names.

The refusal is therefore **executed** and only the ordering is read. It used to be read too: the whole guard was asserted as source order, that `pointers.push(` and `pointers.length > 0` appeared before `rm(outputDir`, and issue #264 measured the gap — `if (pointers.length > 0 && false)` leaves every searched substring in place and in the same order, so the refusal became unreachable with the gate green, and `tooling/` is outside `tsconfig`'s `include`, so `tsc` never saw it either. The scan and the refusal now live in `tooling/source-art-lfs-guard.mjs` with their reading injected, so a test drives them with a fixture in either state — pointer heads and PNG heads — and asserts the throw, its count, the offending filename and the `git lfs pull` remedy. What stays textual is the one thing that still cannot be executed here: that the generator **awaits** that guard before its `rm`. This is the same pattern as `tooling/validate-runtime-atlas.mjs`, whose hand-written `.d.mts` lets `pnpm test` drive the implementation CI runs rather than a second copy of the rules.

`tests/foundation/documentation-claims-contract.test.ts` asserts documentation claims against the code, for the subset of them that is mechanically checkable (issue #121). `docs/ARCHITECTURE.md` declares its contracts binding, so a false sentence in it is a defect: it once listed "compressed immutable save versions" and "Supabase cloud sync" among things the app has, when nothing compresses anything and no module in `src/` can reach the cloud client at all — which sent one agent looking for a compression ratio and another for a wiring bug. Both claims are now asserted, in the direction that matters: the test fails when the *code* makes the sentence false, so the sentence gets rewritten in the same change instead of quietly becoming a lie. `docs/ROADMAP.md`'s Phase 0 claims about a linter and a pull-request template are asserted the same way, in both directions. Comments are stripped with `canonical-iteration.ts`'s shared stripper rather than a local copy of that rule (#188), and that is load-bearing: with the stripper replaced by an identity function, `src/persistence/size.ts` -- which explains in prose that its estimate exists so a *future* backend can decide when compression is worth it -- reads as a module that compresses, and the gate fails on a sentence that is true.

One assertion in that file runs the stripper the other way, and the reason it exists is the second time the same sentence went wrong. The gate for "nothing credits the treasury" scans `.credit(` call sites and asserts exactly one — `ProcurementSystem.cancel`'s refund. That guards the code and cannot guard the *claim*, because the claim lives in the prose the scan strips: "nothing credits the treasury **at all**" is false the moment that refund exists, "nothing credits it **on a schedule**" is true, they differ by four words, and #282 wrote the false one back into `src/ui/hud/projection.ts` in the same change that applied the correct qualifier to the clause beside it. So a companion assertion reads comments rather than code and requires every negated claim about crediting the treasury under `src/` to carry "on a schedule" — five modules state it and all five now do. Its denominator is the set of stating modules, so a scan that stopped seeing them fails rather than reporting compliance, and stripping the `//` markers is load-bearing: the sentence it was written for wraps across two comment lines, so a scan that left the markers in place misses the one file that was wrong. Its bound is stated in the file: it catches the phrase, not the idea, and "the treasury has no income" would carry the same absolute in words no prose scan should try to read.

`tests/foundation/documentation-links-contract.test.ts` asserts every relative markdown link resolves to a file that exists. A confident pointer to an absent file is this repository's most frequent defect, and this covers the subset of it that is mechanically checkable: a link target is unambiguously a path, while a filename backticked in prose may be a module, a concept, or an example. It deliberately does not check the latter.

`tests/foundation/comment-stripping-contract.test.ts` guards the one helper almost every gate above depends on. Nearly all of them strip comments before scanning, so that a doc comment *discussing* a mechanism is not read as the mechanism, and they all share `stripComments` in `tests/helpers/canonical-iteration.ts` rather than each carrying a copy of that rule (#188). That made it a single point of silent failure, and #278 was it: the stripper removed block comments with one regex and then line comments with another, so a `//` comment containing the two adjacent characters `/` and `*` -- which is what any glob or path looks like -- opened a block comment that ran to the next terminator anywhere below. Measured on the tree that reported it, **197 lines of real code in 19 files were blanked before any gate saw them**, including 80 consecutive lines of `src/content/default-locale-en.ts`. No gate failed. Nine of them simply scanned less and stayed green, and three were demonstrated blind by injecting a violation into a blanked span and watching them pass: `canonical-iteration-contract`, `localization-key-completeness` and `ui-orchestration-boundaries`, the last being the gate for `AGENTS.md` boundary 1. Reordering the two passes is not a fix -- it mirrors the defect onto block comments containing `//` -- so the stripper now walks the text once and knows at every position whether it is in code, a line comment, a block comment, a string, a template literal (including the code inside `${...}`, at any depth) or a regular expression literal. It is deliberately not built on `typescript/unstable/ast/scanner`: that is a scanner without a parser, and measured against it, `const re = /https:\/\//;` comes back with its trailing `//;` reported as a line comment, because deciding that is `reScanSlashToken`, which the parser calls.

The gate has two halves, and the second is the one that would have caught #278. The first is fixtures in both directions -- a comment is removed; a delimiter inside a string, a template, a regular expression or a URL is not -- each with its expected output written out. The second strips **every `.ts` file under `src/` and `tests/`** and checks each line against a deliberately dumb oracle built on the line's first two characters rather than on the scanner it is checking, because an oracle sharing the scanner's idea of where a comment starts would agree with it about the lines it got wrong: a line the stripper blanks must look like a comment line, and a line that is a whole-line comment must be blanked. On the old stripper that assertion names 156 blanked code lines. A fixture suite cannot catch a stripper that is wrong about the file it is actually pointed at.

One instance of the same defect is still live and is recorded rather than fixed: `stripSourceComments` in `src/content/validate-catalog.ts` is the same two-pass regex, and worse in that it replaces a block comment with a single space and so destroys line structure as well. Measured over the 134 files it scans it loses real code in two of them, which leaves the enum discovery in `tests/unit/simulation-message-keys.test.ts` blind to that span. Unifying the two means deciding whether a scanner of this size ships in the client bundle and where it lives, which is an architectural decision rather than an implementation detail.

`tests/foundation/localization-key-completeness.test.ts` is the [ADR 0011](./adr/0011-localization-architecture.md) gate widened past the HUD. It scans every `.ts` file under `src/` (comments stripped) for a `<name>Key: '<literal>'` declaration and asserts each one resolves to real text in the bundled default locale, which is `defaultMessageCatalogEn` -- `src/content/default-locale-en.ts` merged under `src/services/localization/default-catalog.ts`'s service strings, so neither file alone is the whole default locale. A key field is typed as a well-formed identifier and never as "a key that exists", so a typo type-checks, passes schema validation and renders as the raw identifier on screen. It is scanned rather than assembled from imported catalogs on purpose: a list of catalog modules is a list that goes stale, which is how nine declared `input.action.*` descriptions had no entry anywhere while the suite was green. Every `*Key` field name must be classified as translatable or explicitly exempted with a reason, so a new key-shaped field cannot land in neither list. Comments are stripped with `canonical-iteration.ts`'s shared stripper rather than a local copy (#188). That stripper replaces every removed character with a space and keeps every newline, so an offset into the stripped text is an offset into the source and the failure message can name a line as well as a file; the local copy it replaced deleted block comments outright, which would have put the first declaration in `src/services/entitlements/products.ts` at line 32 instead of line 60. A separate assertion checks the property rather than pinning a line: every reported line, read back out of the real file, must contain the key it names.

The four module-boundary gates -- `tests/unit/navigation-no-phaser.test.ts`, `tests/unit/services-layer-boundaries.test.ts`, `tests/unit/rendering-module-boundaries.test.ts` and `tests/unit/ui-hud-messages.test.ts`'s architectural block -- were joined by two more in #206, and one of them was rewritten. `rendering-module-boundaries.test.ts` asserted that no rendering module matched `/new (SimulationRuntime|Kernel|SparseWorld|ConstructionSystem)\b/`. `SimulationRuntime` is an `export interface` (`src/simulation/runtime/new-session.ts`), so that alternative could never match anything — `tsc` rejects `new SimulationRuntime(...)` — and it was the one naming the thing the failure message was about; the exported factory that really builds a runtime, `createNewSimulationRuntime`, was matched by nothing. Measured before the fix: a rendering module constructing and exporting a live runtime at module scope left the whole suite green with `tsc -b` clean. The construction forms are now a typed catalog in `tests/helpers/module-boundaries.ts`, and `tests/unit/module-boundary-rules.test.ts` checks **every entry against the declarations `src/simulation/**` actually exports** — an entry naming an interface, a type alias, a module-private class or a renamed export fails with a message saying which. That check is the part that makes the defect unrepeatable rather than merely fixed once.

`tests/unit/input-module-boundaries.test.ts` and `tests/unit/ui-orchestration-boundaries.test.ts` cover the two trees under `src/` that no boundary test reached. `src/input/**` imports no package at all and depends on exactly one thing outside its own tree, the type-only `KeyValueStore` contract, which is `docs/INPUT.md`'s "renderer-agnostic, user-settings concern" made executable; it reaches for exactly one browser global, `resolveBrowserKeyValueStore`'s `globalThis.localStorage`, recorded with the reason rather than forbidden, because the placement is the argued decision `docs/INPUT.md` states and #199 landed. `src/ui/*.ts` — the top-level modules the HUD gate never sees, five when that gate was written and eight today — gets a manifest of which layer each may know and **whether it may run that layer's code or only name its types**, since a module permitted to name `RestoredScope` gaining the ability to call `restoreSimulationRuntime` is one line of diff and is the step that turns a view into a second source of truth. A coverage assertion keeps the two UI gates exhaustive between them, so a new subtree under `src/ui/` cannot land inside neither. Every list fails in both directions, every scan reports the number of files it read so an empty result cannot pass for compliance, and the shared rules are fixture-pinned in both directions in `tests/unit/module-boundary-rules.test.ts` — comments stripped with `canonical-iteration.ts`'s shared stripper rather than a local copy of that rule.

`tests/unit/ui-hud-messages.test.ts` remains the narrower and stronger gate for the HUD specifically: it works from the `HUD_MESSAGE_KEYS` registry rather than from a scan, so it also checks placeholder filling, key spelling, that no HUD module hard-codes a `hud.*` literal outside `messages.ts`, and `AGENTS.md` boundary 1 (`src/ui/hud/**` may not import `src/simulation/**`). Its scope is still exactly `src/ui/hud/**` and `src/ui/primitives/**`; `tests/unit/ui-orchestration-boundaries.test.ts` covers the top level, and asserts that between them the two reach every `.ts` file under `src/ui/`.

The word "specifically" in that sentence was load-bearing, and issue #208 is what it cost: that gate's collection roots are `src/ui/hud` and `src/ui/primitives`, and `src/ui/save-panel.ts` is in neither — so about thirty English literals rendered from the one UI module outside every localization check, while the repository-wide gate above passed it trivially by asking only whether the keys it *declares* resolve. `tests/unit/ui-save-panel-status.test.ts` now carries both halves for the modules directly under `src/ui/`: the same registry check over `SAVE_PANEL_MESSAGE_KEYS` (resolution, placeholder filling, key spelling, one failure key per action), and a scan asserting that none of those eight modules writes a sentence-shaped literal into `textContent` or into a `message:` field. The module list is read from the directory and compared, so a module added to `src/ui/` fails until it is checked or excluded with a reason rather than inheriting the hole this one was in. #206 part 2 asked for the same widening for the *import* boundaries and landed it as `tests/unit/ui-orchestration-boundaries.test.ts`, quoted above; the two are deliberately separate files with separate lists, because one answers "which layers may this module know" and the other "may this module put a sentence on screen", and a single allow-list carrying both reasons would be read for neither. That literal scan now covers eight modules, because `brand-badge.ts` and `brand-messages.ts` joined them.

`tests/unit/ui-brand-badge.test.ts` is the registry check for the third such registry, and it exists because the naming rule the repository-wide gate depends on does not reach it: `tests/foundation/localization-key-completeness.test.ts` scans for a `<name>Key: '<literal>'` declaration, and `BRAND_MESSAGE_KEY`'s fields are `region`, `wordmark`, `stage`, `build`, `description` — not one of them ends in `Key`. That is exactly the hole `SAVE_PANEL_MESSAGE_KEY` fell into, which is why a registry check is written per registry rather than assumed. It also asserts the build identity is a valid `identifierSchema` value, because that identity is written into `SaveEnvelope.gameVersion` and reported as the worker handshake's `workerBuildId`: a commit containing a character that schema rejects would give a page that boots, renders a correct-looking badge, and then fails to save, with the failure appearing nowhere near its cause. What the badge *renders* is not asserted there — that file runs in the `node` environment with no `document`, so `createBrandBadge` cannot be called at all, and rendered-output claims belong one layer up.

The one claim about the badge that **only** the browser layer can settle is that the build identity was injected at all. `src/shared/build-identity.ts` falls back to a visible `unknown` whenever the compile-time `define` is absent, and the default Vitest environment has no `define` — so every headless test necessarily exercises the fallback, and a build that shipped `lockstate-unknown-unknown` to every player would leave the whole headless suite green. `tests/browser/app-shell.spec.ts` asserts the injected value and that it is not `unknown`. That assertion is a statement about *production* only because `vite.config.ts` and `tests/browser/vite.config.ts` import one resolver module (`tooling/build-identity.mjs`) rather than each carrying a copy: with a copy in the test config, the suite would be proving the copy.

`tests/determinism/` is the executable form of `docs/DETERMINISM.md` and, through [ADR 0009](./adr/0009-challenge-verification-strategy.md), of the challenge-verification guarantee: same seed plus same command stream reproduces an identical state hash, `snapshot() → restore() → run N ticks` equals running those ticks straight through, named RNG streams cannot perturb each other, and system order is a property of the declarations rather than of registration order. `ambient-nondeterminism-contract.test.ts` is a static contract in the spirit of `navigation-no-phaser.test.ts`: it walks the real transitive import graph out of `src/simulation/` and rejects clock, locale, DOM, storage and randomness sources, with a single per-file allow-list that fails when an entry goes stale. `canonical-iteration-contract.test.ts` is the second static contract of that family and covers the one rule in `docs/DETERMINISM.md` that had no guard at all (#132): it scans `src/simulation/`, `src/content/` and `src/persistence/` for enumerations of a `Map`/`Set` that reach no sort, and every one it finds must be either sorted or recorded in its allow-list with the reason insertion order is safe there. Its scanning rules live in `tests/helpers/canonical-iteration.ts` and are exercised against fixtures in both directions, the same split `tests/unit/simulation-message-keys.test.ts` uses with `src/content/validate-catalog.ts` — a static contract is only as good as its pattern, and a pattern that quietly stops matching leaves a green suite and no guard. Persistence was added by #177, which also had to make the scanner tell an array's `.entries()` from a `Map`'s — it does so from array-only usage of the same receiver expression in the same file, and both directions of that rule are fixture-pinned. Its scope is still a real limit: a `Map`-order walk in `src/rendering/` is not covered, deliberately, because rendering is not simulation and its sprite pools iterate insertion order by design. A determinism test that cannot fail is worse than none, so every test there is written against a break that was actually demonstrated — see that directory's table in `docs/DETERMINISM.md`.
