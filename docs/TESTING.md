# Testing contract

Lockstate treats tests as executable architecture. A feature is not complete because it appears to work in a browser; its behavior, boundaries and failure modes must be verifiable at the lowest appropriate layer.

## Supported commands

```bash
pnpm typecheck
pnpm test
pnpm test:watch
pnpm test:browser
pnpm test:artifact
pnpm test:perf
pnpm verify
pnpm verify:assets
pnpm verify:deployment
pnpm verify:sql
```

`pnpm test` runs the complete Vitest suite once and fails when no test is discovered. `pnpm verify` typechecks test and production sources, runs the test suite and builds the production Cloudflare package.

`pnpm typecheck` runs **two** TypeScript projects, and the second one is the newer half. `tsconfig.json` covers `src/`, `tests/` and the two Vite configs under the full strict set. `tsconfig.tools.json` covers `benchmarks/`, `scripts/` and `tooling/` — about 3,600 lines of `.mjs` that build the product, deploy it and gate its performance — with `allowJs` and `checkJs`, inheriting that strict set and dropping exactly two flags: `noImplicitAny`, because annotating 181 glue parameters buys nothing about how a call into `src/` is checked, and `noUncheckedIndexedAccess`, because JavaScript has no non-null assertion operator so the only way to satisfy it in a `.mjs` file is a JSDoc cast at every index. `tests/foundation/typecheck-coverage-contract.test.ts` asserts that every tracked module file falls inside one of the two, that the two do not overlap, and that `pnpm typecheck` actually runs both — enumerated from `git ls-files` rather than from a list of directory names, so a *fourth* untypechecked directory fails it too.

Why the second project exists at all is worth stating, because the obvious version of it does nothing. Until #602 those three directories were outside every `include`, so a production signature change was invisible to `pnpm typecheck` **and** to `pnpm test`; PR #581 inserted a required parameter *second* into `LocomotionStore.advance` and `benchmarks/scenarios/actor-render-publication.mjs` kept calling it with three arguments, which passed `writeTile` as the predicate and refused every walker its first edge. But turning on `checkJs` over those files, on its own, still reports nothing: every production symbol reaches a benchmark through `benchmarks/production-modules.mjs`, which imports by `import()` of a computed URL string, and TypeScript resolves no non-literal dynamic import — so the whole production surface arrives as `any`. What makes the gate bite is the derived `@returns` types on that file's five loaders, written as `Pick<typeof import('../src/…'), 'X'>` so they follow the production signature rather than restating it. Measured both ways: with the loaders untyped the reintroduced three-argument call produced zero errors; with them typed it produces `Argument of type '(key: any, tile: any) => void' is not assignable to parameter of type '(key: number, from: TilePosition, to: TilePosition) => boolean'`.

`pnpm verify:sql` is separate from `pnpm verify` because it needs a PostgreSQL server: it applies every migration in `supabase/migrations/` and runs every pgTAP suite in `supabase/tests/` against a scratch database, using the compatibility harness in `scripts/sql/`. It is the check that can run when the Supabase local stack's container images are unreachable; it proves the SQL, not the hosted platform around it (see `docs/CLOUD_SAVE.md` for the cloud-save schema and `docs/TRUSTED_SERVICES.md` for the entitlement/challenge schema). **Four suites assert no behaviour at all** — `003`, `005`, `007` and `008` — and each is a rule over a system catalog rather than a list. The denominator is deliberately not written: it is `ls supabase/tests/ | wc -l`, and it is the half of this sentence that has now rotted three times. Measured rather than counted: those four are the ones with no `throws_ok`, no `lives_ok`, no `set local role` and no `INSERT` into a `public` table (007 and 008 insert only into their own temporary declaration tables). `003_data_api_grants` pins the whole privilege surface for all three Supabase roles. `005_function_security_declarations` pins the function *declarations* — `prosecdef` and the pinned `search_path` — read back from `pg_proc`, because a suite that pinned privileges exhaustively and never read those two columns let a dropped `search_path` pass every assertion (#105 finding 5). `007_column_bound_coverage` enumerates every `text`/`jsonb`/`json`/`bytea` column in `public` from `pg_attribute` and requires each to name the mechanism that bounds it — a length check, an anchored regex, a closed value set, a BEFORE-row trigger, or a generated column — and requires that mechanism's catalog object to exist and to constrain that column (#189). `008_scalar_column_constraint_coverage` does the same for the numeric and timestamp columns, with one difference that matters: a scalar column may legitimately be unconstrained, so it has an allow-list — and an entry there must carry a real reason and **fails if the column later gains a constraint**, so acting on a finding forces the entry to be reclassified rather than left saying the state is unconstrained (#191). A suite doing both is the shape to copy, not an exception to the rule — a rule that nothing drives is a rule nobody has watched fail. **This split has now been wrong in both directions, and both are recorded here rather than overwritten, because a correction is no more durable than the claim it corrected.** `849c6e5` wrote "Four of the eight suites assert no behaviour at all" and "The other four suites do assert behaviour" — true of the four it named, and arithmetically sound at 4+4=8. The resolution after that was to leave the first half at four and take the second to seven — **and it rotted a third time the same way, which is why both counts are now gone from this paragraph.** Re-derived 2026-09-15 by running the criterion below over `supabase/tests/`: there are **twelve** suites, not eleven, and the behavioural set is **eight**, not seven — `012_telemetry_ingest` arrived and neither half moved, exactly as at `9b17e1a`. Check it rather than trusting it: the four are the suites with no `throws_ok`, no `lives_ok`, no `set local role` and no `INSERT` into a `public` table. All four, and the catalog halves of 009, 010 and 011, are rules for the same reason: a list cannot notice a column, function or grant added tomorrow, and something added with no protection must **fail** rather than be merely un-asserted. One further gate lives on the TypeScript side rather than in pgTAP (this said "a ninth", an ordinal counted from the stale total above): `tests/foundation/rpc-status-vocabulary-contract.test.ts` asserts that every status each `SECURITY DEFINER` RPC can return is exactly the set the cloud client's row type names, in both directions — a status the database can return and the client does not name falls through an exhaustive `switch` silently, returning `undefined` at runtime with no compile error (#192). It checks the return path only, and says so: the request half needs a running PostgREST. `003_data_api_grants` also carries a rule of the same shape: no column whose default is `now()` may be written by a client role unless an allow-list entry gives a reason, because the four columns #194 found client-writable were found by an inventory rather than by a failing test — that suite pins what the grants *are*, not what they *ought to be* (#194). **Every suite the criterion above does not name** does assert behaviour — and wherever one of them drives a bound it drives it in **both** directions: refusing a value past the ceiling *and* admitting one exactly at it, because a database that refuses what the TypeScript contract permits is a defect rather than hardening (#105 finding 4). That is stated as a rule about bounds rather than as a count of suites, because the count is the part that keeps rotting. Separate from `pnpm verify` does **not** mean optional: it is a required CI step (see "Database provisioning" below). `pnpm test:browser` runs the Chromium project (`tests/browser/`) and is deliberately **not** part of `pnpm test` or `pnpm verify` — the ordinary suite stays fast, headless and browser-free. Separate is not optional: CI runs it as a required `browser` job, which provisions its own Chromium (see "Browser provisioning" below).

The measurement harness is `pnpm test:perf`, and since #1083 CI runs it — a required step in the `verify` job, not something a contributor has to remember. Separate from `pnpm test` does not mean optional, exactly as it does not for `pnpm test:browser` and `pnpm verify:sql`. It goes through its own Vitest config (`tests/perf/vitest.perf.config.ts`) and that is not a formality: the config sets `testTimeout: 900_000` against the root config's `5_000`, and on the five-second budget these files go red on time rather than on anything about the code — six `Test timed out in 5000ms` failures when #1083 was filed, and 12 of the 35 when the same run was repeated with `--testTimeout=5000` on a loaded container. The count tracks the machine; that there is a count at all is the reason the config exists. `tests/foundation/ci-configuration-contract.test.ts` holds the script and the CI step together, so removing either is red. Its files are named `*.perf.ts` so the default suite never collects them, and it asserts only correctness invariants — never elapsed time (see `docs/BENCHMARKING.md`). It covers persistence decode/save cost and, since #136, what one HUD repaint costs the localization runtime with its `Intl` formatters cached versus built per call (`tests/perf/localization-format-cache.perf.ts`) — reported as a ratio and a per-repaint figure, with the *guard* against the cache disappearing being a construction **count** in `tests/unit/services-localization.test.ts` and `tests/browser/ui-shell.spec.ts` rather than anything timed.

`pnpm verify:assets` is separate from `pnpm verify` for the same reason and by
the same rule: it reads the runtime atlas PNGs, which live in Git LFS, so it is
the only check that needs LFS content. CI runs it as a required `assets` job, so
ordinary runs stay on a cheap pointer-only checkout (see
[ADR-0014](./adr/0014-art-storage-and-runtime-asset-delivery.md)). `*.png` and, under
`assets/source/**`, `*.blend` are LFS-tracked — **this said "only `*.png`", which
`.gitattributes` has contradicted since the line was written**: `cbb2bfd` added
both patterns in the same commit and six `.blend` files already existed. The
conclusion is unaffected: the atlas manifests and `asset-registry.json` are plain
files, and nothing in `pnpm verify` needs LFS content at all.

Separate does **not** mean optional, and a pointer-only checkout cannot pass it
silently. The validator recognises a Git LFS pointer and fails naming it rather
than treating an unfetched file as valid art, and the job asserts the PNG
signature and a size floor on every atlas before it even runs the validator. That
assertion is not belt-and-braces theatre: it is what caught `actions/checkout`
with `lfs: true` leaving pointers in place on this runner.

The `assets` job provisions `git-lfs` with `scripts/provision-git-lfs.sh` and
then fetches content with an explicit, path-scoped `git lfs pull` rather than
using `lfs: true`. On a self-hosted runner the workspace is already at the target
commit from the previous job, so checkout is a no-op, the LFS smudge filter never
runs, and `lfs: true` downloads objects that never reach the working tree. An
explicit pull materialises regardless, and takes a path filter so the job fetches
only the ~17 MB it reads instead of all 55 MB. Provisioning lives in the job that
uses it, idempotent and with no third-party apt repository, exactly as
`scripts/provision-postgres.sh` does for `verify:sql`.

The rejection modes themselves are proven in the ordinary suite.
`tests/contract/runtime-atlas-validation.test.ts` drives the same validator
against tiny synthetic fixtures — a missing direction, a short frame list, a
duplicate logical id, a drifting pivot, an oversized atlas, an out-of-bounds
rectangle, a stale registry — so a validator that stopped rejecting anything
fails `pnpm test` without needing any art at all.

## Self-hosted runner prerequisites (`woogitsu-linux-*`)

The workflows use Linux self-hosted runners. These are the boundaries between tools installed by a job and state the host operator must supply; a successful run on one persistent runner does not prove a newly rebuilt runner has the same state. This list describes repository requirements, not an inventory of every machine in the pool.

| Capability | Repository setup or check | Required host state when the job cannot elevate |
| --- | --- | --- |
| Git, Bash, standard Linux shell tools and network access | GitHub Actions checks out the repository; provisioning scripts use `bash`, `curl`, `tar`, `mktemp` and `install`. | The Actions runner and these basic tools must already work. The repository does not install them. |
| Node and package manager | CI, browser and database migration jobs use `actions/setup-node` with `.node-version`, then Corepack activates pnpm 11.22.0. | `version.yml` is an exception: it calls `npm version` without `setup-node` or `pnpm install`, so Node/npm must already be on that runner's `PATH`. |
| PostgreSQL, `psql` and matching pgTAP | `scripts/provision-postgres.sh` checks, installs or starts the local cluster and verifies a login `SUPERUSER` role for the runner user before `pnpm verify:sql`. | Without root or passwordless sudo, preinstall the server, client and matching pgTAP extension; start the cluster and create the role. `DATABASE_URL` can instead select an already provisioned server. |
| Git LFS client and asset content | `scripts/provision-git-lfs.sh` checks or installs the client in `assets` and `browser`; each job then runs a path-scoped `git lfs pull`. | Preinstall `git-lfs` if apt installation cannot elevate. LFS objects must be reachable; a checkout with pointer files is insufficient. |
| Chromium and its shared libraries | `scripts/provision-playwright-browsers.sh` downloads Chromium into the runner user's cache and checks a real launch. It prints missing libraries and Playwright's package-install command. | Preinstall any missing system libraries; the script does not run apt or `playwright install --with-deps`. No display server is required. |
| Supabase CLI | The database migration job calls `scripts/provision-supabase-cli.sh`, which installs the pinned standalone CLI if absent. | Give `SUPABASE_CLI_INSTALL_DIR` a writable directory on `PATH`, grant passwordless sudo, or preinstall the required CLI version. The download also needs `curl` and `tar`. |
| Python 3 | `branch-gc.yml` checks for `python3` and fails with an actionable message when absent. | Preinstall `python3`; no repository step provisions it. |

The PostgreSQL, Git LFS and Supabase scripts only need elevation when they must change host state. On a fully provisioned no-sudo runner they can succeed without it. Rebuilding a host requires checking these prerequisites again; do not infer them from a previous CI success on a different runner. The database migration workflow also needs its separately configured project credentials and approval environment; this table covers local tools only.

## Database provisioning for `pnpm verify:sql`

`scripts/provision-postgres.sh` installs and starts what `pnpm verify:sql` needs on a Debian/Ubuntu machine and is safe to re-run:

```bash
scripts/provision-postgres.sh   # needs root or passwordless sudo
pnpm verify:sql                 # 412 pgTAP assertions
```

It is deliberately **version-agnostic**. It uses whichever PostgreSQL major version is already installed, or failing that whichever one the distribution ships, and installs the matching `postgresql-<major>-pgtap`. No third-party apt repository is added and no major version is pinned anywhere: the schema is executed and green on **PostgreSQL 16.13 + pgTAP 1.3.2** and on **18.6 + pgTAP 1.3.4**, and Ubuntu 26.04 does not package 16 at all. It then ensures the cluster is running and that the invoking user has a login role with SUPERUSER — the compatibility harness creates extensions and roles, so CREATEDB alone is insufficient. Set `DATABASE_URL` to point `pnpm verify:sql` at an existing server instead; the role step then does nothing.

CI runs that script and then `pnpm verify:sql` on the self-hosted runner, so the SQL is executed on every pull request. The same script is what `.claude/hooks/session-start.sh` uses for remote containers, so the two environments cannot drift into provisioning different databases.

A service container was rejected: `scripts/verify-supabase-sql.mjs` shells out to a local `psql` client that would have to be installed regardless, no published PostgreSQL image ships pgTAP, and the reason this check exists at all is to keep working where container images cannot be pulled.

## Default environment

Vitest runs in the Node environment by default. Pure simulation, protocol, serialization, migration, economy, navigation and deterministic scheduling tests must not import Phaser, touch the DOM or require browser globals.

A browser/E2E project may use Playwright or Vitest Browser Mode after a dedicated dependency and architecture review. Browser setup must remain explicit rather than silently changing the environment for every test.

**Approved browser project (issue #19).** `@playwright/test` (exact-pinned devDependency) drives Chromium against `tests/browser/`, run **only** via `pnpm test:browser` — never as part of `pnpm test` or `pnpm verify`. It stays explicit in exactly the way this section requires:

- Its specs are named `*.spec.ts`, and the root Vitest config collects only `*.test.ts`, so no browser file can be picked up by the default suite by accident.
- It uses its own Vite config and dev server (`tests/browser/vite.config.ts`), not the production Cloudflare build.
- It is devDependency-only and outside the production build graph — verified by building `HEAD` and `HEAD + browser project` side by side and confirming a **byte-identical** bundle. The claim is the identity, not the size: the two builds matched at 1,384.01 kB (gzip 360.73 kB) when that check was run, and the bundle has grown a great deal since — `docs/PERSISTENCE.md` records the step to 1,607.50 kB when the session runtime was wired in, and a production build at `9b6965a` reports 1,614.21 kB (gzip 425.43 kB) for `index-*.js` plus 231.35 kB for the worker chunk. Every size in this paragraph is anchored to a commit on purpose: nothing recomputes them, they move on most merges, and an unanchored "today" is a claim that ages the moment it is written -- this sentence carried 1,602.36 kB and 243.67 kB, neither of which was ever measured at the commit a reader would check. Re-running the comparison means building both sides again; the identity is the claim, and the figures are evidence from one run.

It exists because `fake-indexeddb` structurally cannot prove three things: durability across a real page navigation, what a real browser's `DOMException`s are actually named, and behavior under a genuinely exhausted storage quota (driven here through CDP `Storage.overrideQuotaForOrigin`, asserted via `navigator.storage.estimate()` so an ineffective override fails the test rather than passing vacuously). It found one real adapter defect — see `docs/PERSISTENCE.md`.

The **browser UI** (`tests/browser/ui-shell.spec.ts`, #65 and the HUD shell) is here on the same principle, not as a general licence to test UI in a browser. Five claims cannot be settled below this layer: that a real click on a real `disabled` button does nothing; that no `unhandledrejection` event fires; what a *computed* font stack and numeric variant actually resolve to; what `getBoundingClientRect` / `elementFromPoint` report for a layout at a given viewport; and what the DOM builders in `src/ui/hud/**` actually put on the page — the default suite runs in the `node` environment, so nothing headless ever executes `status-strip.ts`, and "the clock reads `--` until a session reports one" (#94) is a rendered-output claim rather than a mapping one. Everything else about the UI — the tab/collapse state machine, the view-model → display mapping that decides *what* the builders are told to show, the async-action gate's refusal and rejection-ownership rules, the design-token contract — is proven headlessly in `tests/unit/ui-*.test.ts`, in the default `node` environment with no DOM; a browser assertion on rendered text is paired with the mapping assertion underneath it rather than standing in for one. The browser layer found two layout defects that no unit test could have (a strip whose min-content width carried the tab bar off a 375px screen, and a minimap frame overlapping the tab bar at 768px); both now have assertions rather than a remembered viewport. It has since found a third defect of the same shape, in **child order** rather than in geometry: `paintAlerts` appended a newly-seen alert to the end of the list and updated the rest in place, so the drawn order was first-seen order — mounting with alerts `[a, b]` and updating to `[c, a, b]` laid out `a, b, c` (#209). Nothing headless could see it: the `node` environment never runs the builder, and the projection it disagrees with is correct. The order assertion is paired with a node-identity one, because the cheap way to make an order right is to empty the list and rebuild it, and that would silently discard the row identity `HudAlertViewModel.id` exists for.

Two later additions sit *inside* those five claims rather than beside them. That a refused command reaches the player (#207, extended to the world-drag route by #225) is a claim about rendered text, about computed style — the refusal line's `[hidden]` rule loses to the `display: flex` on the same selector unless it is written out, which is how the first draft of it shipped as a visible empty band — and about layout at 375px, where `hud.css` drops the alerts region entirely. That the save panel renders nothing outside the message catalog (#208) is a claim about what its builder puts on the page: it is checked by mounting the real panel in the `en-XA` pseudo-locale, where a string that never went through the localizer arrives unaccented and unbracketed, which is [ADR 0011](./adr/0011-localization-architecture.md)'s own stated purpose for that locale. The mapping underneath each — `refusalMessageKey` and the save panel's key registry — is asserted headlessly beside it, per the pairing rule above. #225 added the second route to the first of those: a finished world drag is delivered to the sink `mountHud` registers, and what the browser settles is that one gesture becomes **one** gated intent and that refusing it paints the line with no control marked, because the player pressed none. The tool that produces the gesture is proven headlessly beside it in `tests/unit/ui-build-tool.test.ts`, which is where "one gesture is one report" is asserted rather than assumed. #261 added a third route to the same claim, and it is the first one with no control on screen at all: the world's `KeyZ`/`KeyY` keys reach the HUD through the same tool, so what the browser settles is that a refused undo paints its own sentence -- not the build order's -- with nothing marked, while the keys themselves are measured against a real `WorldScene` in `tests/browser/world-scene-input.spec.ts` (including that a text field owning the keyboard silences them) and the routing is asserted headlessly in `tests/unit/ui-build-tool.test.ts` and `tests/unit/input.test.ts`.

Two claims were added here for the same reason and are worth naming, because both are about a *number the browser reports* rather than about rendered text:

- **Where the Build panel's last section is** (#143). The panel used to be its own only scroll container, so every catalogue row it gained pushed the "Enter coordinates" header further down inside it: at 1280x720 with a twelve-entry catalogue the header sat at y=845..889 in a panel clipped at y=638. The assertion measures the header's rectangle against the panel's client box at all five viewports the suite visits, with the panel unscrolled — a computed-`overflow-y` assertion would have passed *before* the fix as well, since the panel already had it. The catalogue is fed to the panel as view-model data, so the harness hands the real panel twelve entries; `BUILDABLE_REGISTRY` holds **twenty-one** rows, so twelve is a fixture length chosen to exceed the panel rather than a claim about the catalogue. **This said the registry "has two and the assembled app cannot yet show a third at all"**, which `6cededc` (#320) made three and `b097e70` (#384, ADR 0028 phase 4) made twenty-one; `src/ui/hud/build-panel.ts:485` and `tests/browser/ui-shell.spec.ts:1899-1903` both already say twenty-one.
- **How many `Intl.NumberFormat` instances one repaint builds** (#136). The harness's `HudLocalizer` counts `formatNumber` calls and a `Proxy` construct trap counts constructions across one real `hud.update()`: 11 values formatted, 0 formatters built -- and only the second of those two numbers is asserted. Nothing headless executes the strip, so this is the only layer that can count what a real repaint really does.

Neither is a timing assertion; both are counts and positions, which is what keeps them out of `docs/BENCHMARKING.md`'s way.

The same three reasons apply to a **save-format migration**, which is why `tests/browser/local-save-migration.spec.ts` covers V1 → V2 (#50) here as well as in-process: a migration bites in production on a record an *older build* left in real origin storage, transported by structured clone rather than JSON and read back in a later page load by a build that only knows the new version. Its V1 records are built from the same checked-in `tests/fixtures/persistence/save-v1-in-progress.json` the in-process `tests/migrations/save-v1-to-v2.test.ts` uses, so the two layers cannot drift into disagreeing about what a V1 save looked like. This is an addition to the browser layer, not a replacement: the in-process migration tests remain the fast, primary proof, per "use the lowest layer that proves the behavior" above.

The **assembled application** (`tests/browser/app-shell.spec.ts`) is the only place the real `index.html` is ever loaded. Every other spec here drives a purpose-built harness page, which is the right shape for a module under test but means the page a player opens — renderer, HUD and save panel in one document, over real storage and real HTTP — had no coverage at all. Seventeen claims exist only once the pieces are assembled, and none can be settled a layer down: that Phaser's `Scale.RESIZE` canvas really is the size of the window and follows it across a resize; that `elementFromPoint` **and a real press** at the centre of the screen reach the canvas rather than the HUD, whose root is `pointer-events: none`; that every runtime atlas is fetched over HTTP and *decodes* at its manifest dimensions (a Git LFS pointer is served as `200 image/png` and only a decoder can tell the difference); that a prison created through the real save panel — panel → session controller → simulation worker snapshot → IndexedDB — is still listed after a real navigation; that every HUD control renders at the 44px `--tap-target` (the token is applied by CSS convention, and a token test cannot check a *rendered* box — a 24px control is one of the defects this layer already found by measuring); that pressing a real transport button reaches the real simulation worker over `postMessage` and comes back as a day counter that moves on screen (#94 — every layer of that is proven separately, and the defect was that they were not connected); and that the interface still mounts, and says why, when `Worker` construction throws (#82); that a control the simulation *refuses* says so on screen rather than to the console (#207 — with no prison created, "Place order" throws inside the real command sender, and what has to be proven is that `src/main.ts`'s own wiring carries that to the HUD: before the fix the only effect was a `console.warn` and `.hud` innerText was byte-identical before and after the press); and that **every interactive control on the page is reachable** — `elementFromPoint` at five points across each control (its centre and four points 20 % in from its edges) resolves to that control or something inside it, on every tab and at every viewport the suite visits, *and* every control is accounted for rather than merely visited: a control that is never laid out in any state the test reaches has escaped the check, so the two the responsive rules deliberately drop below 720px are named in the spec and anything else appearing there fails. That last one is the general form of a defect this layer had been blind to (#88): the save panel and the Build panel were two independently-positioned `fixed` layers, and with the Build panel's numeric fallback expanded — one tap from the default — it covered 91 % of the save panel at 1280x720 and all five of New prison, Save now, Export, Load and Delete did nothing, while every existing assertion stayed green — because presence and reachability are different properties and only the second is what a player has. Five sample points rather than one for the same reason at a smaller scale: on that layout at 900x600 the centre alone found 11 unreachable controls and the five found 13, the extra two being buttons whose lower fifth had been carried off the bottom of the viewport. Two are #149's: that a **second** prison loads in the same tab, in a second real `Worker` — the worker refuses every `simulation/initialize` after the first, so the page has to construct one per session, terminate the one before it and keep the renderer and the HUD attached across the swap, and only a browser has the thread (`tests/integration/session-second-load.test.ts` proves the composition, headlessly, against loopback transports); and that a `Worker` which cannot be constructed for a *later* session is reported on the panel and raised as #82's own notice rather than thrown, which needs a page that booted successfully and then had `Worker` taken away from it. The last two are #225's, and they are the world-drag route to the command #207 fixed on the panel route: that a wall refused after a **drag on the canvas** says so on screen (with the tool armed and no prison created, the real `BuildTool` reports the gesture, the HUD dispatches it and the real command sender throws — before the fix the drag went straight to that sender and its only report was a `console.warn`, and the mutation the issue predicted for it, deleting `onError` from the `BuildTool` options, was measured and survived the entire suite); and that **one drag is one transaction**, asserted over a tee on the real `postMessage` because a `transactionId` is minted on this thread and never echoed back, so no other layer can see it. The fourteenth is #146's, added after #264: that the **30-second autosave actually fires from play alone** — a prison created on the real page, a wall laid on the world, and a further generation reaching storage with no `pagehide` and no hidden `visibilitychange` in between, which is what separates the interval save from the best-effort lifecycle one that was the only automatic write before #146. The scheduler, the controller and the command sender each have complete unit tests; the join between them exists only in `src/main.ts`, because the sender is built at module scope and the controller inside `bootPersistence`. The interval is faked by shortening `window.setTimeout` calls of 30 s or more, which is deliberately narrower than `page.clock` — the simulation worker is a separate global scope and Phaser's `requestAnimationFrame` loop has to keep running, or the world drag is never processed. The fifteenth is #287's: that a save file the game **exported** can be **imported back**, which is the round trip the Import control exists for and the one claim in this file that needs a real download and a real file chooser as well as a worker and a storage backend. `SessionController.importInto` had been written, exported and reachable with no caller at all, so the application offered a download it could not read; the serialization layer's own round trip was never the gap (`tests/determinism/snapshot-restore-fidelity.test.ts` has proven that in-process for as long as it has existed), the player-reachable path was. What the browser settles is that the bytes the page produced are the bytes it reads: play a session, pause, save, Export, create a second empty prison, Import the downloaded file through a real chooser, then Save now — capturing from the worker the import restored into — and Export again, with the final payload equal to the exported one. The second prison is what keeps it non-vacuous (day one, tick zero, so an import that did nothing would compare against a fresh prison), and the control's four distinguishable refusals are asserted a layer down against a stub in `tests/browser/ui-shell.spec.ts`, because a save from a *newer* schema version is one this build cannot write. The sixteenth is the accessibility playtest of 2026-08-29's: that **a command press leaves the keyboard somewhere a player can use**. Every command-issuing control in the HUD shares one `BusyGroup`, which sets `disabled` on all of them while a command is in flight — and a disabled element is blurred by the browser, which re-enabling does not undo — so measured keyboard-only on the assembled page, with the pointer tripwire live, New prison, Buy, Place order, Designate, Hire and Admit each left `document.activeElement === document.body`, every one of them with `data-action-failed` null and the count it moves actually moved, so none was a masked refusal. The *rules* for giving focus back — only focus the group took, only while nothing else has claimed it, only to a control that can still hold it — are pure predicates in `src/ui/primitives/focus-handoff.ts` and are proven headlessly in `tests/unit/ui-focus-handoff.test.ts` and `tests/unit/ui-async-action-gate.test.ts`. What only the assembled page can settle is that `disabled` and `hidden` really blur a control, that focus really lands on `<body>`, and that the one group really is shared by the status strip, four HUD panels and a save panel that `bootPersistence` mounts into the HUD — no harness page has all of them at once. The Rooms panel's *Designate* is in the same test for the opposite reason: it hides itself before it dispatches, so the busy group never sees it holding focus and the hand-off to the control that replaced it has to come from the panel, which is a fact about that panel and not about the primitive. The seventeenth is #703's, and it is the second one in this file about the *status strip* rather than about a panel: that the strip's ninth chip is **on screen** and that the Regime roster's four rows are the prison's four highest risk tiers. Both halves are decided in pure functions proven headlessly beside it -- `projectStatusMetrics` and `projectPrisonerRoster`'s ordering -- and neither of those can settle what only the assembled page has. The chip is the visibility rule below in its sharpest form: `.hud-strip__metrics` is `overflow-x: auto` with the scrollbar suppressed in both engines, so a chip that does not fit is *absent with nothing saying so* (#634), and the harness page has an empty brand slot where `src/main.ts` puts 351.9px of chrome -- a third of the strip's fixed width present on one page and missing from the other. So the chip's own box is read against the metrics row's box, with `offsetParent` beside it, and the label is required to be the authored words rather than the `classification-group.high-risk.name` key that names them. The roster half needs a real prison -- ADR 0045 makes an enclosed perimeter a precondition of zoning and `AdmitPrisoner` is refused with no accommodation at all, so the test buys bricks, orders ten wall segments, zones an *empty* cell and admits twelve, which leaves every arrival waiting at `accommodation-assignment` with a real drawn tier. What makes the claim complete rather than a proxy is that the expected window is computed from the **exported save file** (`payload.simulation.prisoners.components.riskTier`, every prisoner's tier by entity index) with the clock paused first: the panel shows four of twelve, so nothing on screen could otherwise say what the other eight are. An earlier version stood in for that with "the window holds more than one distinct tier" and failed a run whose window was four prisoners at one tier -- a *correct* top-four window, and exactly the case where the sort is working hardest.

It deliberately does not re-test the HUD state machine, the responsive layout, the computed font stack, the camera transforms or the atlas schema: those are already proven in `tests/unit/ui-*.test.ts`, `tests/browser/ui-shell.spec.ts`, the Phaser-free `src/rendering/**` tests and `tests/contract/runtime-atlas-validation.test.ts`, and a browser test that repeats a headless one costs CI minutes and proves nothing new.

The **camera transforms** (`tests/browser/camera-coordinates.spec.ts`) are here for a reason that is narrower than the others and, on the evidence, the most necessary. `src/rendering/camera/coordinates.ts` reimplements Phaser's camera maths as pure functions so the renderer can convert coordinates without a live engine instance and the rules stay testable in the default environment. That reimplementation can be internally perfect and disagree with the engine that actually draws — and it was, for the whole life of the module. Issue #115: both functions modelled zoom as scaling about the viewport's corner while Phaser scales about its centre, so the build cursor was displaced by `origin × (1 / zoom − 1)` and a player could not place a wall where they clicked. The headless test could not fail, because it round-tripped each function through the other. Only a real camera can settle the claim, and only a real browser can hold one: `docs/CAMERA.md` explains why, and the spec compares `screenToWorld` against `camera.getWorldPoint` and `visibleWorldBounds` against `camera.worldView` at five zoom levels, drives a real mouse, and asserts that the old formula genuinely disagrees so a regression cannot pass. It deliberately does not re-test the tile-edge rule, `TILE_SIZE_PX`, zoom clamping or the culling margin: those are pure and already proven headlessly.

A **two-finger touch gesture** (`tests/browser/world-scene-touch.spec.ts`) is here because there is nowhere else it can be. A second finger needs a browser context created with `hasTouch` and CDP `Input.dispatchTouchEvent`; Playwright's own `page.touchscreen` places one finger, the default Vitest environment has no pointer events at all, and Phaser only delivers a second touch pointer because `WorldScene.create` calls `this.input.addPointer(2)` -- so every layer below this one is structurally unable to see a pinch. That is exactly what happened: `src/input/gestures.ts` is thoroughly unit-tested and `docs/INPUT.md`'s "Two fingers ... still move the camera" was carried by reading alone until #209's follow-up dispatched the first synthetic touch sequence this project has ever had. The spec asserts the pan is 1:1 and does not zoom, that separating and converging move the zoom in the right directions, that `ZOOM_BOUNDS` clamps at both ends, and -- the property that needs a real camera -- that the world point under the midpoint is **held** across all of it, read from Phaser's own `getWorldPoint` rather than from the project's `screenToWorld`, so the gesture cannot be confirmed by the transform it drives. It also settles a reading #209 recorded as unclassifiable: see `docs/CAMERA.md` on what an anchored zoom does to the scroll, and the two specs at the end of the file that test the alternative explanation (a harness carrying state across a touch boundary) instead of assuming it away. It deliberately does not re-test `TouchGestureTracker`'s arithmetic or `zoomAtScreenPoint`'s literals: both are proven headlessly, and this layer is for the wiring between them and a real engine.

The **minimap's mapping** (`tests/browser/world-scene-minimap.spec.ts`) is here for a reason worth stating separately, because it is about *where a claim can be stated exactly* rather than about a browser API. Issue #793's mapping is an identity: a point at the centre of `.hud-minimap__surface` must land on the same world position `frameCameraOnFirstWorld` centres a session's first paint on, both being `WorldRenderView.loadedBounds`'s own midpoint written twice in `world-scene.ts`. Asserting it on the assembled page cannot be done: the only camera readout there is a screen-to-tile reading taken by pressing the world, which answers in whole tiles or, through `playtest-harness.ts`'s `calibrate()`, in whole pixels after a bisection costing around a dozen real presses per reading — so a `toEqual` between two of those means "these agree to within a pixel", which is not what the source says, and three of them in one test cost 40 s of a 60 s budget. Against the world-scene harness the equality is exact, and neither side of it is computed by the spec: the camera is framed by the scene's own arrival path, displaced with Phaser's `setScroll`, and then asked to navigate to the centre. The world is materialised from a real `SparseWorld`, snapshotted as the worker snapshots its own and projected through the production `WorldRenderView.fromSnapshot`, so a spec chooses a chunk *layout* and never the rectangle it then checks the mapping against. That layout is one chunk wide and two tall starting at chunk (1,2) — not square, not at the origin, asymmetric between the axes — because the starter chunk the app-level gate runs on is 32x32 at (0,0), which is exactly the shape that hides an origin-blind or a transposed mapping: dropping `minTileX` and transposing the axes were both mutated and both survive a square world at the origin. What stays on the assembled page (`tests/browser/hud-minimap-navigates.spec.ts`) is the three claims that need it — that the panel no longer swallows the click, that `hud.ts`'s own normalization of a `MouseEvent` against `getBoundingClientRect()` is not transposed or inverted, and that the gesture reaches no command channel — and its two corner clicks are on the *anti-diagonal* for the same reason the harness world is not square: on the diagonal, `fx` and `fy` are equal at both points, and transposing the HUD's derivation passed the diagonal version of that test.

The **environment artwork** (`tests/browser/environment-art.spec.ts`) is here for three claims, and each is unreachable a layer down for a different reason. The sheets under `/game-content/source-art/` are Git LFS content, so a checkout that has not pulled them serves about 132 bytes of pointer text as `200 image/png` — the same trap `app-shell.spec.ts` catches for the actor atlases, and only a decoder can tell the difference. The cutting itself is `createImageBitmap` with a crop rectangle and a resize, a 2D canvas context and Phaser's texture manager, none of which exist in `environment: 'node'`. And the third is the one a suite can most easily fake: that the pixels on the screen came from the art. The spec reads the rendered frame through the renderer's own `snapshotPixel`, **removes the artwork by hand**, reads the same pixel again and requires the two to differ — because a spec that only proved the sprites were *created* would stay green if they drew nothing. It aims by moving the camera and always samples the exact centre of the drawing buffer, which is the centre whatever the device pixel ratio is and whichever way up the snapshot comes, so there is no coordinate transform in the harness to get wrong. Two further pixel comparisons are structural rather than aesthetic: that a finished `wall-brick` order does not paint a full-tile block over the floor of the room it walls (the order stays in the construction snapshot after `finalizeConstruction` writes the edge, so the same wall reached the painter twice), and that the atlas frames hold opaque mid-range colour rather than the transparent canvas they started as. Everything decidable without pixels — which sheet, which rectangle, which frame, how they pack, which identities are on the colour fallback — is in `tests/unit/environment-art.test.ts`, and it deliberately does not re-test the source-art catalog schema or the packing arithmetic here.

**Whether a DOM lifecycle event reaches its handler at all** (`tests/browser/lifecycle-save.spec.ts`) is here for a reason this layer had not been used for before: a fake event target is not merely a weak proof, it is a *vacuous* one. It receives whatever a test dispatches at it, so it agrees with the browser no matter which object the browser really dispatches at. `LifecycleSaveHandler`'s unit tests were complete and green while its `pagehide` listener, registered on `document`, never fired once in production (issue #92) — `pagehide` is dispatched at `Window` and window events do not propagate down to the document. The spec therefore drives a real navigation to obtain real, browser-generated lifecycle events (recorded synchronously into `sessionStorage`, which survives the navigation even though the fire-and-forget save may not) and requires both of them, in the order the browser delivered them. It deliberately does not assert *which object* each listener is registered on: `visibilitychange` bubbles from `document` up to `window`, so an implementation that registered both listeners on `window` would receive both events and be correct in production, and failing it would pin the wiring's shape rather than its contract — which injected target each listener lands on is a statement about `LifecycleSaveOptions.targets`, and the unit tests make it there. It also does not assert that the lifecycle save reached IndexedDB: that save is best-effort by design and the interval autosave is the durability mechanism, so asserting it would test the wrong contract. Confirmed to have teeth by restoring the #92 wiring — both listeners back on `document` — under which the whole unit file still passes and this spec records `['visibility-hidden']` where it requires `['pagehide', 'visibility-hidden']`.

A single non-DOM Web API can be reviewed and approved narrower than a full browser/E2E environment: `fake-indexeddb` (a pure-JS, dependency-free `indexedDB` implementation, devDependency-only) is approved for testing `src/persistence/local/indexeddb-store.ts` specifically — see `docs/PERSISTENCE.md`. Tests using it import a fresh `IDBFactory` instance explicitly per test rather than the `/auto` global-polluting entry point, so the default Vitest environment stays `node` and unaffected for every other test.

## Browser provisioning for `pnpm test:browser`

`@playwright/test` is pinned but its browser binaries are not in the package and are not checked in, so a machine that has never run the suite fails with "Executable doesn't exist". `scripts/provision-playwright-browsers.sh` installs what the suite needs and is safe to re-run:

```bash
scripts/provision-playwright-browsers.sh   # no root, no apt, no third-party repository
pnpm test:browser                          # the Chromium project; `--list` reports the count
```

The suite starts its own dev server on port 5183 and **never reuses one that is already listening**. It used to reuse outside CI, which meant a run could attach to a server started from a different checkout of this repository — the suite then loaded that tree's `src/**` and reported on code the developer was not editing. That was observed, not theorised: a deliberately broken design token came back green because the page under test came from another worktree. Refusing to reuse turns that into a loud "port is already used"; set `LOCKSTATE_BROWSER_TEST_PORT` to run a second checkout alongside the first. The CI job sets it to a port the kernel just handed out, because the self-hosted runner shares its host with active development and 5183 is regularly taken there — the first run of that job died on exactly this.

Chromium only — `playwright.config.ts` pins `browserName: 'chromium'` and nothing here launches a second engine. It runs headless (the config never sets `headless: false`), so no display, xvfb or `DISPLAY` is required. The download is ~280 MiB (Chromium, the headless shell and ffmpeg) and unpacks to ~920 MB under `PLAYWRIGHT_BROWSERS_PATH`, default `~/.cache/ms-playwright`.

**Idempotent**, in the same style as `scripts/provision-postgres.sh`: it checks before it acts, and the check is the launch the suite itself performs. When the browser is already on disk and runs, it downloads nothing and exits in a few seconds — which, on the self-hosted runner that keeps its cache between jobs, is every run after the first.

It also carries the two environment-specific facts observed on Ubuntu 26.04 under WSL2, so nobody has to remember them:

- Playwright 1.56.1 has no build listing for Ubuntu 26.04 and refuses outright (`ERROR: Playwright does not support chromium on ubuntu26.04-x64`). The script retries with `PLAYWRIGHT_HOST_PLATFORM_OVERRIDE=ubuntu24.04-x64`, which downloads the 24.04 build; that build runs correctly and needs no override at run time. The retry happens **only** after an unmodified install has failed with that exact message, so it stops overriding by itself on a Playwright release that supports the host natively, and it never masks an unrelated install failure.
- `playwright install --with-deps` fails for the same reason, needs root, and installs a list of packages on the assumption that one is missing. The script launches the browser instead, and if that ever fails it reports exactly which library `ldd` says is missing. On this host nothing is: `ldd` on both the Chromium binary and the headless shell reports no missing library, and the suite is green against a browser tree installed into an empty directory.

CI runs that script in the `browser` job and then `pnpm test:browser`, so the layer that found the adapter defect in `docs/PERSISTENCE.md` and the two HUD layout defects above runs on every pull request instead of when a human remembers. The job is ordered after `assets` for two reasons, neither a data dependency: a browser run is a couple of minutes on a single self-hosted runner and there is no point spending it on a tree that does not build; and `assets` has already materialised the runtime atlases into the shared workspace, so the job's own path-scoped `git lfs pull` transfers nothing. That pull stays regardless, because the job has to be correct on a cold workspace — `app-shell.spec.ts` asks a real browser to decode the art, and a pointer-only checkout is exactly what it exists to catch. The job also fails if the suite skipped its way to green: `playwright test` already errors when no test matches and `forbidOnly` is on under CI, but neither covers a suite that ran and skipped.

## The one condition under which the browser suites retry (#616, #652)

Both Playwright configs set `retries: 0` and that is still the default. Neither `pnpm test:browser` nor `pnpm test:artifact` runs `playwright test` directly, though: each runs `tests/browser/run-suite.ts` with a `--suite` name, and that wrapper runs the suite once and retries it **only** when every failing test observed `net::ERR_NETWORK_CHANGED` while it was running.

That error is Chromium aborting in-flight requests because the operating system's network configuration changed underneath it. Issue #616 diagnosed it from a retained trace after three earlier investigations had failed to, and it has turned `main` red five times in four different-looking ways — a harness global that never appears, a `page.evaluate` returning `undefined` in 229 ms, and a simulation worker whose module graph was truncated so a correctly-written panel stayed pending until the test's own expectation gave up. One cause; the symptom depends only on which modules were in the aborted set. It is not a product defect: production is a built bundle over one origin, not several hundred dev-server module requests.

The owner ruled on 2026-08-30 that this class, and nothing adjacent to it, may be retried. Three properties are what make that safe rather than a permission to be green, and each is pinned by `tests/foundation/browser-network-changed-retry-contract.test.ts` or `tests/foundation/browser-network-changed-signature.test.ts`:

- **The evidence covers the whole test.** #616's fifth occurrence measured the aborts spread across ~52 seconds, so anything that samples console errors at one instant could miss the window or be tripped by it. `tests/browser/network-changed-fixture.ts` holds `requestfailed` and `console` listeners on the browser **context** for the lifetime of every test — context, because the fifth occurrence aborted the *simulation worker's* module graph rather than the page's — and appends each observation to a file as it happens, so a 60-second timeout that never reaches fixture teardown still leaves the evidence behind.
- **It retries on nothing else.** The matcher takes one exact error, anchored on the right. `net::ERR_INTERNET_DISCONNECTED`, `net::ERR_NETWORK_IO_SUSPENDED` and `net::ERR_ABORTED` are all refused, and one failing test without evidence refuses the whole retry rather than narrowing it.
- **It is loud and countable.** A retry writes `LOCKSTATE_BROWSER_SUITE_RETRY` to stdout, a refusal writes `LOCKSTATE_BROWSER_SUITE_NO_RETRY`, and each observing test writes `LOCKSTATE_NETWORK_CHANGED_OBSERVED` carrying the error text. CI tees all of it into `browser-suite.log` for the dev-server gate; the artefact step captures its output into a shell variable and prints it, because `tests/foundation/ci-configuration-contract.test.ts` requires that job to have exactly one `tee` target, so those lines land in the job log rather than in the uploaded file. That last line is the direct answer to what made this class invisible for three investigations: `grep -c ERR_NETWORK_CHANGED browser-suite.log` returned **0** on every one of the five occurrences, because the evidence existed only inside a retained trace.

Every spec in `tests/browser/` therefore imports its `test` object from `./network-changed-fixture` rather than from `@playwright/test`, and the contract test fails in both directions if one ever does otherwise — a spec written by copying a pre-#616 header would run with no listeners attached and be silently absent from the evidence.

**Both gates, since #652, and for one merge it was only one.** `pnpm test:artifact` invoked `playwright test` directly until then, so the artefact gate recorded no evidence and nothing decided a retry for it — while `production-artifact.spec.ts` imported the fixture like every other spec, which is what made the gap read as covered from every file involved: the listeners really did attach, and `appendEvidence` returned at its first line because nothing set `LOCKSTATE_NETWORK_CHANGED_EVIDENCE`. The owner ruled on 2026-08-30 to route the second gate through the same wrapper rather than write the exception down, so the decision exists once. `tests/browser/browser-suites.ts` is the registry of what the wrapper can drive, and the contract test now fails if a `playwright*.config.ts` appears that is neither driven nor recorded there as deliberately excluded — `playwright.playtest.config.ts` is the one exclusion, because it is not a gate.

Measured on this branch rather than argued: with the signature fabricated through the page console (nothing in Playwright or CDP can make Chromium genuinely emit it), the artefact gate goes `1 failed, 2 passed` → `LOCKSTATE_BROWSER_SUITE_RETRY suite=artifact` → `1 passed` → exit 0, and the same command run the old way on the same fabricated abort exits 1 with no retry line at all. An ordinary wrong expectation in the same suite gets `LOCKSTATE_BROWSER_SUITE_NO_RETRY suite=artifact failures=1 withSignature=0` and stays red.

## Test layers

| Layer | Purpose | Normal location |
| --- | --- | --- |
| Unit | One pure module, algorithm or invariant | Colocated `src/**/*.test.ts` |
| Contract | Typed boundary, schema, protocol or repository contract | `tests/contract/` or a named folder under `tests/` |
| Integration | Two or more real project modules wired together | `tests/integration/` |
| Determinism | Same initial state and command stream produce identical state/hash | `tests/determinism/` |
| Migration | Versioned fixture upgrades and forward-only save compatibility | `tests/migrations/` |
| Browser E2E | Real browser storage/durability, real `DOMException` names, real quota exhaustion, save migration off real storage, whether a real DOM lifecycle event reaches its handler, agreement between a pure transform and a real Phaser camera, what a two-finger touch gesture does to a real camera, and the assembled page: canvas sizing, hit-testing, image decode, a second session in a second real `Worker` | `tests/browser/`, via `pnpm test:browser` (own command, required CI job) |
| Production artefact | The built client, served from `dist/` through workerd: that the bundle boots, that its emitted worker chunk is reachable and parses, that compile-time `define`s survived, and that one command and one persistence round trip complete | `tests/browser/production-artifact.spec.ts`, via `pnpm test:artifact` (run inside the `browser` CI job) |
| Measurement | Reported size/timing evidence with no timing assertions | `tests/perf/`, via `pnpm test:perf` and its own Vitest config (required CI step in `verify`) |
| Benchmark | Repeatable performance evidence, never correctness by elapsed time | `benchmarks/` and `docs/BENCHMARKING.md` |

Use the lowest layer that proves the behavior. Do not use a browser test to cover logic that can be proven by a fast headless unit or contract test.

### Reading the text is not seeing it (#720)

A rendered-text assertion at the browser layer answers less than it looks like
it does. `textContent`, `innerText`, `toHaveText` and `toContainText` all read
the DOM, and `overflow: hidden` is a painting decision that never touches the
text node — so an element showing ten characters of a sentence satisfies every
one of them. `ui-shell.spec.ts`'s `expectLaidOut` closes a *different* hole,
that the element is laid out at all; a clipped element is laid out.

On 2026-08-31 the HUD's alerts log showed about ten characters of every
sentence in it, at every viewport, with the whole suite green. Four separate
acts of DOM probing during a playtest reported it correct and **only a
screenshot found it** (#720).

`tests/browser/clipping.ts` is the assertion that was missing.
`expectNotClipped(page, selector, what)` compares `scrollWidth`/`scrollHeight`
against `clientWidth`/`clientHeight` and reports an element in two states —
`cut`, where the overflowing axis is `overflow: hidden` or `clip` and the
content is never painted, and `spilled`, where it is `visible` and the content
is painted outside the element's own box, over whatever sits beside it. An
`auto` or `scroll` box is not a finding: there is overflow and the player can
reach it, which is what the scrolling alerts list is for. Pair it with a text
assertion the way `expectLaidOut` is paired with one; all three answer
different questions.

Two things it deliberately does **not** cover, so a green result is not read
as more than it is. `.ui-sr-only` is excluded, because the visually-hidden
pattern is a clipped 1x1 box on purpose. And a scroll container that hides
content below its own fold with no scrollbar drawn to say so is reachable, so
this check is silent about it — that is an affordance defect and needs its own
assertion (`.save-panel` on the Build and Rooms tabs;
`docs/research/2026-08-31-playing-the-twelve.md` §11).

### Reading the DOM afterwards is not seeing it either (#700)

`expectNotClipped` answers "is the string where the element is". It cannot
answer "was the string ever on a screen", and on 2026-08-31 that was the
difference between a green suite and a defect the owner found by playing.

A neglected prison lost three prisoners. The escape sentence — *"{name} broke
out — no guard reached them in time."* — **was written correctly all three
times**, in the `danger` band, unhidden, naming the person, and was replaced
**1 ms, 0 ms and 0 ms later** by the all-clear recorded on the same tick.
Across 21.8 minutes of play the sentence reached **zero animation frames**
(#700, `docs/research/2026-08-31-playing-the-nine-changes.md` §2c).

**No assertion in the suite could have failed on that**, and the reason is
worth stating rather than assuming. A browser test reads the DOM *after* the
event, so it reads the replacement and passes. A 100 ms poll cannot help: the
playtest's own poll took 52 samples and never landed on a sentence that stood
for 1 ms. And `vitest.config.ts` is `environment: 'node'` with no jsdom, so
`hud.ts`'s `applyEventNotice` — the function that writes the band — is
unreachable from `pnpm test` at all, and an animation frame does not exist
there.

`tests/browser/alert-dwell.ts` is the assertion that was missing.
`installBandRecorder(page, selector)` starts a `MutationObserver` for the
**writes** and a `requestAnimationFrame` loop for the **paints**;
`readBandRecording(page)` brings back both, and the finding is the difference
between them. The frame log keeps *spans* — first frame, last frame, frame
count — so `expectPaintedFor(recording, text, minimumMs, what)` can assert
what nothing else here can: this sentence was on screen, unbroken, for at
least this long. A span caught in exactly one frame measures 0 ms, which is
honest: it was painted, and nobody could read it.

**Deliver the view models the way the worker does.** `src/main.ts` calls
`hud.update` synchronously once per worker message with no frame batching, and
`SimulationWorkerStateMachine.publishEvents` posts one message per event in a
single loop — so two events on one tick are two DOM writes inside one frame
budget. `deliverAsTheWorkerWould(page, models)` hands each model over in its
own task through a `MessageChannel`. A sequence applied in a single
`page.evaluate` would measure a path the application never takes and would
report every sentence as surviving.

**An instrument that observes nothing must fail, not pass**, because a blind
instrument is worse than the defect it was written for. Four guards, and
`ui-escape-sentence-survival.spec.ts` exercises each rather than describing
it: a selector matching nothing throws at install; a read with no recorder
throws; every assertion first requires at least two animation frames and at
least one observed write; and `expectNeverPainted` — the assertion a *control*
arm uses — additionally requires that the text **was written**, so "it never
reached a frame" cannot pass for a sentence nobody produced.

That last guard is what keeps the control arm from rotting into a tautology.
`ui-escape-sentence-survival.spec.ts` keeps the red half of red-then-green
permanently: one arm measures the escape as `main` produces it, and a second
rebuilds the pre-#703-ruling-6 stream — the all-clear recorded on the escape's
own tick, through the same production recorder — and asserts the instrument
catches it. The code that makes the first arm green lives in
`src/simulation/incidents/response-system.ts`, which that spec does not touch.


### Comments are not executed, and one shape of them is now gated

`tests/foundation/comment-symbol-existence-contract.test.ts` reads every
backticked **member path** (`RoomInstanceRegistry.residentIds`) and
**three-segment screaming constant**
(`STATE_INCOME_WITHHELD_PER_UNMET_NEED_MINOR_UNITS`) in every comment under
`src/` and `tests/` **and in every guide at the top level of `docs/`**, and
fails when the name resolves to nothing in the repository's code. The guides
are read as a second corpus with its own floors; `docs/adr/` and
`docs/research/` are deliberately not read, for the reason the contract's own
docblock measures. Issue #543 is the reason: a comment in module A stating a
fact about module B has no test tying the two together, and this repository has
paid for it repeatedly — a comment that was false for 51 releases sent two
agents hunting a fixed defect.

**It gates the vocabulary half of that class, not the behavioural half**, and
the distinction is worth knowing before reaching for it. It catches
`WorkerStateMachine.publishEvents` when the class is
`SimulationWorkerStateMachine`, and a docblock naming an assertion helper that
does not exist. It cannot catch *"nothing debits the treasury on a schedule"*
going false when `PayrollSystem` lands, because that sentence names no symbol;
nor `RoomInstanceRegistry.residentIds` when the caller moved to
`residentIdsWithExistingPlace`, because both accessors are real. Those stay the
discipline.

**A comment may still name something that is gone — it just has to say so.**
A deletion record whose prose carries *"used to"*, *"no longer"*, *"deleted"*,
*"there is no"* or one of the other markers, within about two wrapped lines of
the name, is exempt. That is a convention with teeth rather than a hole: this
tree already writes deletion records that way, every one of the six in it
passed before the gate existed, and the marker window is deliberately narrow
because the first version read markers over the whole comment block and a
hundred-line docblock's unrelated *"there is no ..."* exempted a real defect.

### A conflict marker is invisible to every other gate (#983)

`tests/foundation/merge-conflict-marker-contract.test.ts` reads every **tracked**
file — enumerated from `git ls-files`, read out of the working tree — and fails
when a line *begins* with a merge conflict marker.

The reason it is a gate rather than a habit is that nothing else here can see
one. Measured at `1ad2189a` (v0.0.483) with ``>>>>>>> origin/main` committed into `docs/research/README.md` and nothing else
changed: both `pnpm typecheck` projects exit 0, `tests/foundation` reports
**483 passed (483)** and `pnpm test` reports **401** files and **4729 passed |
1 skipped**. `docs/**` is on no TypeScript project's `include`, no test imports
a Markdown file, and the markers render as literal text inside a table cell, so
the index goes on looking approximately right in a diff. That index is also the
file this repository conflicts on constantly — every research note appends at
the same point — so the residue has a well-worn route in.

It reports three shapes separately. A **complete hunk** is a conflict `git
merge` wrote and nobody resolved. An **unpaired marker line** is what a
mis-scoped resolution regex leaves behind, and is the shape #983 is actually
about — a check that required the pair, as that issue first proposed, would be
blind to it. A **marker-shaped line the strict patterns cannot read** is the
second-pattern discipline `tests/foundation/adr-quotation-verbatim-contract.test.ts`
learned the hard way in #981: a pattern cannot report its own misses.

**What keeps it from shouting at documentation is that a marker must start the
line.** Prose quotes a marker inline in backticks — this paragraph does — and
`git` only ever writes one at column zero. A bare `=======` is never a finding
on its own, because it is a legal setext heading underline; it counts only in a
file that already carries an open or close line, and that blind spot is named
in the contract rather than left to be discovered. Measured across all 1390
tracked text files at that base: **zero** lines begin with seven `<`, `>`, `|`
or `=`, so the rule costs nothing today. Git LFS pointers are text and are
scanned; the 23 screenshots under `docs/research/` are skipped by the same
NUL-byte heuristic `git` uses. The whole walk is 133 ms.

### The production artefact layer, and the hole it closes

`pnpm test:browser` and `pnpm test:artifact` both drive Chromium and they are
not the same test. The first runs a **Vite dev server over `src/**`** using
`tests/browser/vite.config.ts`, which says of itself that it "loads no
Cloudflare plugin and never participates in `pnpm build`". Everything it proves
is a statement about the sources. The second runs `vite preview` over `dist/`
with the production `vite.config.ts`, so the page under test is workerd serving
the built client with `public/_headers` applied exactly as production applies
them.

Until `pnpm test:artifact` existed, **nothing in this repository had ever
executed the artefact a player downloads.** That is not a gap between two
similar checks; it is a gap with three existing checks stacked either side of
it, each of which stops one step short:

- `pnpm build` proves the bundle compiles and emits, and `vite.config.ts`'s
  `assertContentValidationIsShipped` plugin reads one marker out of the emitted
  chunk. It runs no code.
- `scripts/verify-cloudflare-build.mjs` reads the generated Wrangler config and
  the emitted files. It runs no code.
- `scripts/verify-deployment-preview.mjs` serves `dist/` through workerd and
  asserts the response headers — and names the hole itself: *"What it CANNOT
  check is that the policy still lets the renderer run, because it never opens
  a browser. ... A Phaser upgrade that started needing `'unsafe-eval'`, a
  cross-origin CDN or a `blob:` worker would pass every check in this
  repository and break the page."*

Two defect classes were **measured** slipping through all of them, and each is
now an assertion in `tests/browser/production-artifact.spec.ts`:

1. **A `define` that reaches the dev server and not the artefact.** Deleting
   `buildIdentityDefines()` from `vite.config.ts` — the *production* config —
   leaves `tsc` clean, `pnpm build` green, `verify-cloudflare-build.mjs` green,
   and `app-shell.spec.ts`'s own build-badge test green, because
   `tests/browser/vite.config.ts` carries an independent copy of the same
   resolver. Measured: that mutation shipped `lockstate-unknown-unknown` to
   every player with the badge test passing in 2.6 s.
2. **A worker chunk that is served as something other than JavaScript.**
   `wrangler.jsonc` sets `assets.not_found_handling:
   "single-page-application"` in every environment, and that fallback covers
   `/assets/*` too — so a chunk hash the deployment does not have is not a 404
   but **HTTP 200 with the index.html body**, cached `immutable`. `new Worker()`
   on that constructs, fails to parse, never posts `simulation/ready`, and the
   session times out after 15 s. No `requestfailed` listener sees it, because
   the request succeeds. The media type of the chunk the page actually loaded is
   asserted for exactly this.

**It is deliberately two tests and not a second copy of `app-shell.spec.ts`.**
The sources are the same sources; what differs between a dev server and a
bundle is the small set above plus tree shaking, chunking and the shipped CSP.
Measured cost is ~14 s per CI run — a 3.3 s production build and a 10.9 s
suite — inside a `browser` job that already takes about five minutes. Keep it
that shape: behaviour belongs in the layers below, and a duplicate suite here
would be paid for on every pull request for ever.

`dist/` is an **input** to this suite, not something it builds.
`tests/browser/playwright.artifact.config.ts` fails with a message naming
`pnpm build` when `dist/index.html` is absent, deliberately rather than
building one itself: a suite that builds its own subject can pass on a tree
nobody deployed. It also needs the Git LFS runtime art for the same reason
`pnpm test:browser` does — the renderer decodes every atlas — which is one more
reason it runs inside the `browser` job, where the art has already been pulled.

**The two suites share `tests/browser/` and must not share its specs.**
`tests/browser/playwright.config.ts` matches `*.spec.ts` across that directory,
so it collected `production-artifact.spec.ts` too and drove it against the dev
server. Measured, CI run 33271621137, job `browser`, step "Run the real-browser
suite" (`Running 255 tests using 1 worker`):

```
✘  80 tests/browser/production-artifact.spec.ts:128:3 ... (951ms)
   Error: A Worker was constructed from
   "/src/simulation/worker/worker.ts?worker_file&type=module", which is not a
   fingerprinted chunk under /assets/.
✓  81 tests/browser/production-artifact.spec.ts:249:3 ... (4.1s)
```

`?worker_file` is Vite's **dev-server** worker URL; the production build was
never wrong, and the artefact suite proper never ran in that job because the
job died before reaching it. Both lines are this layer's own failure mode: test
80 red about a subject it was not looking at, and test 81 green for the wrong
reason — a full worker round trip asserted in "the built client" with no
`dist/` involved at all. `playwright.config.ts` now carries the `testIgnore`
that is the mirror image of `playwright.artifact.config.ts`'s `testMatch`, and
`tests/foundation/browser-suite-partition-contract.test.ts` fails — in
`pnpm test`, with no browser and no build — when any spec in that directory is
claimed by both configs or by neither.

## Naming and placement

- Use `*.test.ts` for executable Vitest files.
- Colocate narrow unit tests with their implementation.
- Put cross-module, persistence, protocol and integration fixtures under `tests/`.
- Keep reusable test-only helpers under `tests/helpers/`; production modules must not import them.
- Use descriptive behavior names. A failing test should identify the broken invariant without opening the implementation first.
- Avoid large snapshots for evolving UI or state. Prefer focused structural assertions and purpose-built fixture checks.

## Determinism and isolation

Tests must not depend on:

- execution order or another test's side effects;
- current wall-clock time;
- live network services;
- unseeded randomness;
- the developer's keyboard layout, locale, timezone or home directory;
- mutable process globals that are not restored;
- files left by a previous run.

Inject clocks and deterministic RNG interfaces into production code. Use fake timers only when the test owns the complete timer lifecycle, and always restore them. Seed values and command streams must be visible in the test or fixture so failures can be reproduced.

Vitest is configured to clear/restore mocks, stubbed environment variables and stubbed globals between tests. Tests remain responsible for closing workers, servers, database handles, timers and temporary directories they create.

## Network and external services

Unit and contract tests must not make live network calls. Supabase, Cloudflare and other provider behavior should be exercised through explicit adapters, local emulators where justified, recorded schema fixtures or separate deployment smoke tests. A test requiring credentials is not part of the ordinary pull-request test gate.

## Worker and renderer boundaries

- Simulation tests import the headless simulation API directly, not a Worker wrapper.
- Worker protocol tests validate message parsing, version negotiation, invalid-message rejection and round trips independently of Phaser.
- Renderer tests consume immutable snapshots/deltas and must not mutate worker-owned state.
- Phaser scene tests belong to an explicit renderer/browser layer and cannot become the only proof of simulation behavior.

## Fixtures and migrations

Persistent fixtures are versioned inputs, not opaque generated blobs. Keep them small enough to review, record the schema/build version and never rewrite an old fixture merely to make a migration test pass. Add a new expected fixture or migration when the contract changes.

## Pull-request evidence

Every issue and pull request must state which layers changed and include the commands actually executed. At minimum, ordinary changes require:

```bash
pnpm typecheck
pnpm test
pnpm build
```

Deployment-sensitive work also requires `pnpm verify:deployment`. Work touching `supabase/` or `scripts/sql/` requires `pnpm verify:sql` locally as well — CI runs it, but reviewing SQL that has never been executed is what produced the defects recorded in `docs/CLOUD_SAVE.md`. Performance-sensitive work requires a benchmark scenario and result evidence under the benchmark contract; elapsed-time assertions do not belong in unit tests.

## Coverage policy

There is no arbitrary repository-wide percentage threshold during the pre-alpha foundation. New behavior still requires tests. Coverage thresholds may be introduced only after representative systems exist and uncovered risk can be mapped to meaningful gates rather than a vanity number.

## Current executable baseline

`tests/foundation/repository-contract.test.ts` guards the pinned Node/pnpm metadata, strict compiler options, test-source inclusion and the rule that an empty suite cannot pass. It is a foundation contract, not a substitute for system-specific tests.

`tests/foundation/ci-configuration-contract.test.ts` is its sibling for the files that describe how the project is built, checked out and deployed. Issue #138 found several of those enforced by nothing, each for the same reason: the configuration and the check that is supposed to enforce it live apart, so editing one and not the other leaves the suite green. **Each `describe` block in it pins one such agreement**, and the file is the list — this paragraph is not, and a sentence here counting the blocks would be wrong within the week, as one counting three of them was on the day it was written. Three are worth reading in full, because each records a mutation that used to survive:

- **Every header `public/_headers` sets is asserted somewhere in `scripts/verify-deployment-preview.mjs`**, and every header on the `/*` rule appears in that script's `SECURITY_HEADER_BASELINE` with the same value. Note the direction. The verifier checks its baseline against a real preview response, which catches a header *deleted from or weakened in* `public/_headers` — the mutation that used to survive, where removing three of the four security headers left every gate green. This test checks the reverse inclusion, which catches a header *added to* `public/_headers` and asserted nowhere. Neither direction substitutes for the other. A third check holds the exact set of header *names* the `/*` rule must carry, which is the one direction the two inclusion checks cannot cover: deleting a header from `public/_headers` **and** from `SECURITY_HEADER_BASELINE` in the same change satisfies both of them, and that is precisely the shape of #138's surviving mutation one level down. There is now a **Content-Security-Policy**, along with HSTS and cross-origin isolation ([ADR-0021](./adr/0021-http-response-security-headers.md), closing #105 finding 12). Note what is and is not gated. `pnpm verify:deployment` runs `vite preview`, which serves `dist/` through workerd and so applies `public/_headers` exactly as production does — that is a real check that the headers reach a real response, and CI runs it. Nothing checks that the policy still lets the renderer run, because the verifier never opens a browser and the browser suite's server (`tests/browser/vite.config.ts`) deliberately loads no Cloudflare plugin and therefore applies no `_headers` at all. The renderer's requirements were measured by execution when the policy landed and are recorded in ADR-0021; a Phaser upgrade that began needing `'unsafe-eval'`, or a build that started emitting a `blob:` worker, would pass every check here and break the page.
- **Every executable file with a shebang is matched by a `.gitattributes` LF pattern.** Mode bits come from `git ls-files -s` and the resolved attribute from `git check-attr`, so this tracks what git will really do on checkout instead of re-implementing gitattributes pattern matching.
- **Every `scripts/provision-*.sh` is called by a workflow or by `.claude/hooks/session-start.sh`**, or is listed in the test's `INTENTIONALLY_MANUAL` map with the reason. That map is empty today; all four scripts are wired to a gate.

Two later blocks in the same file are about the *supply chain and the credential* rather than about a configuration file agreeing with a script, and they are the reason to read the file rather than this paragraph. The **workflow action pinning contract** requires every `uses:` in `.github/workflows/**` to name a 40-character commit rather than a tag, and to say beside it which release that sha is — a tag is a mutable pointer in somebody else's repository, so `@v4` means "whatever that owner makes it mean next". `tests/foundation/deploy-blocked-announcement-contract.test.ts` is the gate for a failure that reported itself as *nothing at all* (issue #424). `deploy.yml` runs on `CI`'s completion and its `staging` job requires `conclusion == 'success'`; when that guard rejects a run every job skips, and GitHub concludes a run whose every job skipped as `skipped` — no red X, no notification, indistinguishable from a run with nothing to do. **And a state attribute does not imply the state.** The sibling of the paragraph above, found the same way and worth stating separately because the false pass is one layer further from the pixels. `createPanel` collapses a panel by setting `hidden` on its body and stamping `data-collapsed`; `hud.css` gives two panel bodies a flex `display` of their own, which outranks the user agent's `[hidden] { display: none }`. The fold assertions therefore read `getClientRects().length` on the body, and the fix is a stylesheet line rather than a per-panel `:not([hidden])`, so a third panel with its own `display` cannot inherit it. This is the same lesson as the `--tap-target` one: a token is not a layout, an attribute is not a layout, and only a measured box is.

`tests/foundation/composition-root-contract.test.ts` guards the wirings only `src/main.ts` performs. The composition root is by construction the one module no unit test executes -- it reaches for browser globals, constructs a `Worker`, mounts into a real document and runs at import -- so every component it connects is tested in isolation and the *connecting* is tested nowhere. Three defects have landed in exactly that gap, each with a flawless component behind it: #82 (`mountInterface` inside `bootPersistence`, so a browser that could not start a worker got a canvas and nothing else), #199 (`WorldScene` reading `window.localStorage` itself rather than taking the injected store) and #146 (nothing calling `markDirty`, so the 30-second autosave never fired). Measured on the last of those: removing the one wiring line from `main.ts` restores the defect exactly, with `tsc` clean and 1,579 tests passing.

The gate is textual and its bound is stated in the file: it proves a wiring is **written**, not that it works -- the behaviour of each seam belongs to that seam's own tests, and the assembled page belongs to `tests/browser/app-shell.spec.ts`. What it buys is the one thing neither layer gives, that deleting a line from the composition root fails something. Entries are deliberately few: each names a defect that actually happened, and a wiring nobody has broken does not earn a line, because a list of every call in `main.ts` would be a second copy of the file that nobody reads.

That bound is not decorative, and issue #264 measured what it costs when the other half is missing. Prefixing the `markDirty` wiring with `if (Number.isNaN(0))` keeps the pinned substring byte-for-byte and makes the line unreachable; `tsc` stayed clean and the whole Vitest suite stayed green, because the browser backstop this paragraph points at did not yet exist for #146 -- `grep -n "autosave\|markDirty" tests/browser/*.spec.ts` matched nothing. It exists now: `app-shell.spec.ts` creates a prison, lays a wall on the world and requires a further generation to reach storage from the interval alone, with no `pagehide` and no hidden `visibilitychange` in between. The reading half of the pair was not weakened to get there -- it is correct for what it claims, and what it claims is not behaviour.

`tests/foundation/fault-code-reachability-contract.test.ts` is the third of that family and its subject is the worker's refusal vocabulary. `ProtocolFaultCode` is a closed enum -- `grep -c "^  '" ` its `PROTOCOL_FAULT_CODES` block for the size -- and it keeps being found carrying members nothing could produce: #139/#184 (`unsupported-protocol-version` and `unknown-message-kind`, because the worker computed the decoder's classification and reported a hard-coded `invalid-message` instead), #187 finding 2 (`duplicate-message` and `sequence-gap`, because every kernel refusal reported `invalid-state`), and #444 item 1 (`shutting-down`, described below). The first two a person found by reading the enum, the third a mutation found; the whole suite was green every time, which is the point of the family. A code the worker cannot emit is a reason the main thread can never be given, so it is now a gate: an unemitted member must be recorded with a reason, and a recorded member that gains a producer must have its entry removed. **The gate itself was the third instance.** Its matcher asked whether the code's literal appeared anywhere in the producing surface, and `'shutting-down'` appears there three times -- every one of them the `WorkerState` of that name, never a fault. A pure rename of the worker state turned the gate red, which is the whole proof: the collision was *inside* the surface being scanned, where the docblock's careful scoping of same-named strings elsewhere in `src/` could not reach it (#444 item 1). The matcher now requires the literal in an **emitting position** -- an argument to `fault(`, or a value of `COMMAND_REJECTION_FAULT_CODES` or `PROTOCOL_DECODE_ERROR_CODES` -- and `shutting-down` is recorded in `UNEMITTED_CODES` with its reason. So the list is no longer empty, and the assertion is no longer "empty": it is that every recorded member carries a reason and that no member outside the list is unemitted. Whether `shutting-down` should instead be given the emitter it lacks is #444 item 2, an open decision, because it changes session lifetime.

Two things about that file are worth reading before copying it. First, it scans the **producing surface only** -- `src/simulation/protocol/decode.ts` and `src/simulation/worker/**` -- because four fault-code spellings appear elsewhere under entirely different vocabularies: `sync-engine.ts`'s `PullResult.reason`, `simulation-message-keys.ts`'s worker-*state* label, `worker-session-host.ts`'s consumer-side `error.code ===` comparison, and `kernel.ts`'s own `CommandRejectionKind` discriminant. A repository-wide scan would count all four, so if the worker ever stopped emitting `invalid-payload` the gate would stay green on the strength of an unrelated union in the persistence tree. Second, and this is the part that generalises: while the vocabulary is *fully* reachable, widening that scope cannot make any of the main assertions fail -- more matches when everything already matches changes nothing, and that mutation **survives**. So the scope is pinned by a negative control that asserts those four foreign occurrences exist and are outside the surface, rather than by an argument in a comment. The comment-stripping in the same file is the opposite case and says so: measured across the producing surface, no fault code appears in a comment without also appearing in code, so replacing the stripper with the identity function survives too, and the file records that it is precautionary there rather than load-bearing.

`tests/foundation/challenge-rejection-code-reachability-contract.test.ts` is that file's sibling for the other closed refusal vocabulary, and the larger one: `ChallengeRejectionCode` has twenty-four members and sits on the trust boundary [ADR 0009](./adr/0009-challenge-verification-strategy.md) describes, where the code is the difference between "your build is too old" and "these hashes disagree with the replay". It has **two** directions where its model has one, and the reason generalises. Issue #264 S4-S6 found three members — `evidence-too-large`, `command-after-final-tick` and `objective-metric-missing` — that no test in the suite reached: each was mutated to a no-op, the last in the `tsc`-clean `?? 0` form that returns `verified` with `rankedScore: 0` for a run whose objective metric the replay never produced — `verified` being the one tier ADR 0009 makes eligible for public ranking — and each survived with zero delta. An emission-only gate would have been **green throughout that**, because all twenty-four do have a `reject(...)` call site; what was missing was a test, not a producer. So this gate asks both questions: every code must appear in `src/services/challenges/verification.ts`, the one module that constructs a rejection, *and* in `tests/unit/services-challenge-verification.test.ts`, the tests that drive the pipeline. Both lists are empty, and both fail in the stale direction.

Its scope needs the same negative control and needs it harder. `'invalid-shape'` is spelled by five other result unions under `src/` — including one in the pipeline's own directory, `ChallengeDefinitionAuthenticationResult` in `challenge.ts` — and by the five test files that drive those, so both "scan `src/services/challenges/`" and "scan `tests/`" are already too wide, and ten foreign occurrences are asserted to exist outside both surfaces. The sharper case is why `CHALLENGE_REJECTION_CODES` was moved into `src/services/challenges/rejection-codes.ts` instead of staying beside the pipeline: the declaration spells all twenty-four literals, so a producing surface that contained it would report every code emitted *unconditionally*, whatever the pipeline did. That is asserted rather than assumed. The comment stripping here is the precautionary case and the file says so: measured, neither scanned file spells a code in a comment without also spelling it in code, so an identity stripper leaves all six assertions green.

The gate is textual and states its bound: "named by an exercising test file" is a floor, not proof that a test drives the code. The runtime proof is the behavioural tests beside it, which is why #264's three findings needed both halves — a reachability gate satisfied by an allow-list entry is not the same thing as coverage. The same change replaced three self-comparisons in that file with field-sensitive assertions. `expect(seen[0]).toEqual(challengeDefinitionBytes(definition))` compares a function's output to its own output and therefore holds for *any* function of the definition, including one that discards `limits` and both allow-lists — which is exactly what #264 S1 did, with the whole suite green. The replacements enumerate the leaves of the fixture (`tests/helpers/field-sensitivity.ts`, nested: `limits.maxTicks`, not `limits`) and require each one to change the signed bytes, the definition hash and the evidence hash. Enumerating rather than naming is the point: #264 S2 and S3 are both cases where the guard tampered a field the mutation happened to keep. The self-comparison itself is **kept and labelled**, in the shape `tests/unit/camera-coordinates.test.ts` records for the assertion that let #115 ship: it is not the proof, it is the link that pins the bytes the verifier is handed to the function whose field sensitivity is proven exhaustively next to it.

Re-measuring all thirteen of #264's survivors against `main` after those changes found the two enumerations were the right medicine and not the whole of it, because the same disease had a third form in the same file: a **mirror mock**. Every replay stub in `services-challenge-verification.test.ts` was written `replay: ({ evidence }) => ({ ... })` and filled its outcome in from the evidence it had just been handed — `checkpoints: evidence.checkpoints`, `metrics: { ...evidence.claimedMetrics }`. That inverts what [ADR 0009](./adr/0009-challenge-verification-strategy.md) makes the replay for: it is the independent authority the claim is checked against, and "the claimed score is present only so it can be contradicted". A mirror can differ only in the one field a test edits by hand, so `checkpointsAgree` and `metricsAgree` were driven on their per-field value comparisons and never on their **set** comparisons — "the trusted side produced a different number of checkpoints", "the trusted side produced a metric the claim does not mention" describe a state no stub in the file could construct. Measured: deleting `if (claimedKeys.length !== replayedKeys.length) return false;` from `metricsAgree`, and `if (left.length !== right.length) return false;` from `checkpointsAgree`, each left 190 files and 2,106 tests green with zero delta, while turning "claimed a subset of what the replay produced" into a publicly rankable `verified` row. The fix is the same in kind as the other two: the new stubs state a literal outcome instead of echoing one, which is the only shape that can disagree about something the test did not think to name. Generalised, all three forms of the defect are one — **the fixture supplied both sides of the comparison**, so every equality the production code checks held by construction — and the cure is to enumerate a set the production code declares (input leaves, rejection codes, disagreement shapes) rather than to sample from the fixture. One caution worth carrying: a loop bound derived from the constant under test is the same self-reference wearing a different hat, and it fails worse. Sizing an expiry loop as `ceil(confidence / DEFAULT_INTELLIGENCE_DECAY_PER_INTERVAL)` does not go red at a decay of `0`, it hangs.

Two of the thirteen were still live at that re-measurement and are closed with the same discipline. `IntelligenceSystem` — the caller of the `decayAll` three tests drive directly — was named by nothing, so `DEFAULT_INTELLIGENCE_DECAY_PER_INTERVAL = 0` was a session in which intelligence never decays and every tip is the permanent truth flag the architecture notes forbid, with the whole suite green; `tests/unit/contraband-intelligence.test.ts` now reports a tip into a real `createNewSimulationRuntime` and steps the real kernel, asserting direction and cadence against the exported constant rather than against `0.1`, because the magnitude is deliberately unpinned. And `MAX_STACK_FRAMES` could go from 12 to 100,000: not a privacy leak, since `redactText` truncates the joined frames either way, but unbounded work in the one handler that runs during a crash and an unbounded `frameCount`. Its fixture depth is a **literal** 200 and the test says why — `MAX_STACK_FRAMES + 5` would have made the assertion true for any bound at all.

The mirror mock left one field behind it, and issue #318 is what finishing the job looks like when the fixture shape is already known to be the problem. `outcome.finalTick` — the replay's own answer to when the run ended — reached the verified result as `replayedTick` and was compared against nothing, while every other number the replay produced was checked against the claim; #316 recorded that as an owner decision rather than asserting it either way, since pinning the current behaviour would have locked in "reported, not checked" by accident. The owner ruled it a missing check, and it is now `final-tick-mismatch`, first among the agreement comparisons. What matters for testing is that **a mirror stub cannot drive this check at all, in either direction.** Every mirror in the file writes `finalTick: evidence.finalTick`, so the trusted side is a function of the untrusted one: the two agree about the tick for every submission, including one whose claim a test edits by hand, because editing the claim moves both sides at once. The set comparisons #316 fixed could at least be reached by overriding one side; this one could not be reached at all. So a test of it written the old way would have passed with the comparison deleted and guarded nothing, which is a worse outcome than no test — and `tests/unit/services-challenge-verification.test.ts` keeps that measurement as a labelled control rather than a claim: the mirror verifies a run whose claimed length is 300 while the pipeline is told nothing it can disagree with, and that control stays green with the production comparison removed, by design. The tests that bite state their outcome as literals and enumerate the closed set the comparison declares — an integer disagrees in two directions, later and earlier, each with a self-consistent outcome — plus a case that disagrees about the tick *and* the hash *and* the metrics, which is what pins the check's position in the verdict order rather than merely its existence. The same self-reference caution applies to the fixture as it does to a loop bound: `finalTick: evidence.finalTick + 1` would rebuild the mirror, so the claim is a literal, and a guard asserts the fixture still makes the claim those literals were written against — the group goes red there if `buildEvidence()` moves, instead of quietly agreeing again.

The fourth form of the same disease is a **round trip against its own inverse**, and #264 S11 is where it lived. `tests/determinism/snapshot-restore-fidelity.test.ts` checked twelve subsystems as `const before = toJsonValue(read()); write(read()); expect(toJsonValue(read())).toEqual(before)`, and four more as "write it twice and compare the second to the first". **Both are satisfied by a `write` that does nothing**, for every subsystem in both lists, which is the same defect as the mirror mock read backwards: the value the assertion compares against was produced by the code the assertion is about. Measured against that file alone, gutting one subsystem's `loadSnapshot` to `return;` at a time: **eight of the sixteen left it 11/11 green** — `intelligence`, `confiscations`, `tunnels`, `containers`, `jobWorkers`, `roomInstances`, `incidentResponse` and `jobs`. The other eight were killed by the session-level tests in the same file rather than by these two, which is the finding #264 recorded and why none of the eight was a whole-suite survivor: `session-save-round-trip.test.ts` and `incident-escape-riot.test.ts` catch what the tests that *name* those subsystems do not. That is the `camera-coordinates.test.ts` shape exactly — a round trip that cannot fail, standing where the proof is supposed to be. The cure is the one the other three forms needed: compare against something the code under test did not produce. Each case now carries a **donor** snapshot — a valid state of that subsystem which this run does not hold — and the assertions are ordered so the weak one can no longer stand alone: the donor really differs, loading it is observed *in full* (so a `loadSnapshot` that ignores its argument, or drops one field of it, fails), and only then is the run's own snapshot restored and required to come back exactly. Nine donors are an independent session's snapshot, never stepped; three are literals, because this scenario leaves `tunnels`, `jobWorkers` and `incidentResponse` in exactly the state a fresh session has — `tunnels` was `[] → [] → []`, the most vacuous case in the file — and a written-out document is the strongest available donor. Those three literals are pinned by an assertion that fails if the scenario ever starts populating them, so the case cannot silently return to comparing a fresh session against itself. After the change all sixteen no-ops fail.

Issue #375 is the argument that the fourth form deserves a sweep rather than one more entry, and the sweep found three more of it — all three in the same place, which is the part worth carrying. **A restore that only one line in `src/` performs is the shape most likely to be asserted by nothing.** `DeploymentSystem.loadSnapshot` and `PatrolSystem.loadSnapshot` had exactly one caller each — `restoreSimulationRuntime` — and none anywhere in `tests/`: measured at v0.0.98, replacing each method's assignments with `return;` left **217 files / 2,463 tests green**, alone and together with the utility restore deleted as well. Two tautologies named by the same issue are closed with it, and the second one corrects the issue's own reading, which is worth keeping because the distinction is useful. `tests/unit/hud-projections.test.ts` asserted `riot.requiredResponders` against `runtime.incidentResponseSystem.requiredResponderCount(8)` — the very method the projection calls, so both sides were one side, and it caught nothing whatever (measured: halving the requirement in production left that file green, and turns it red now that the figure is a literal). `tests/integration/incident-response-restore.test.ts` re-derived its responder count from the policy with the production expression, and that one is **not** vacuous in the same way: the constant is compared against *observed* runtime state, so ten cases in that file do go red when the requirement changes. What a self-derived constant cannot notice is a change to the rule that computes it — it re-derives, follows, and every comparison holds. Both are literals now, with the policy inputs they describe pinned in a case of their own so a changed policy fails loudly instead of being silently followed.

`tests/foundation/message-kind-reachability-contract.test.ts` is the third reachability gate, after the two above, and its subject is the thing both of theirs travel on: the **protocol message kinds** of [ADR 0003](./adr/0003-simulation-worker-protocol.md). `tests/foundation/` gated commands, content ids, input actions, fault codes and challenge rejection codes, and gated message kinds nowhere — and issue #274 finding A2 established that the gap was live. **Nothing in `src/` has ever sent a `protocol/handshake`.** Every occurrence is the receiver, the kind list, the schema or the transfer switch; `WorkerSessionHost.initialize` sends `simulation/initialize` as the worker's first message and `handleInitialize`'s guard accepts it because the state is still `uninitialized`, so decision 4's version and capability negotiation happens for nobody and `WorkerState`'s `'ready'` is a state no `transition(...)` call reaches. Verifying that against the tree found two more the audit had not named: `protocol/ping` has no sender either, and neither does `simulation/event`, which no main-thread `switch (message.kind)` even has a case for. With `simulation/delta` — #274 A1's half that holds — that was **four kinds declared, schema-checked and sent by nothing**: four of eighteen when the gate was written, four of twenty once #104 added `simulation/request-projection` and `simulation/projection`, and **three of twenty** since ADR 0040 slice 1 (#414) gave `simulation/delta` a sender. Each is recorded with a reason and fails in the stale direction the moment it gains one, which is exactly what #414 had to pay: the entry could not survive the sender, so deleting it — and lowering every denominator beside it — was a step of that change rather than a tidy-up after it. The two kinds #104 added moved every denominator and none of the three lists, which is the outcome this gate exists to require of a new kind: both are sent from `src/`, and the reply is provoked by a request the main thread really constructs.

`tests/foundation/projection-reachability-contract.test.ts` is the fourth member of that family, and it measures what none of the other three can see. The message-kind gate asks whether a *message kind* has a sender; a **read model with no message at all** is invisible to it, which is why `simulation/status-counts` was sent, provokable and green throughout the period in which nine of the ten projections it was supposed to have generalised were unreachable from anything but their own tests (issue #104). So this one starts from the directory rather than from the vocabulary: it reads every exported `project*` out of `src/simulation/presentation/` and requires each to have a route — a `PROJECTION_CATALOG` entry, or a recorded entry naming the other channel that carries it (`projectClockPosition` is the one, computed main-side from the tick `simulation/clock-state` publishes). Two further gates sit under it: `PROJECTION_CATALOG` is a `Record<ProjectionId, …>`, so a declared id with no binding does not compile, and `tests/contract/worker-projection-channel.test.ts` drives **every** declared id through a real `SimulationWorkerStateMachine` over a populated scenario and decodes every reply, because a `Record` can be satisfied by an entry that throws. Measured in all three directions before landing: adding an unrouted `projectVisitation` to the read-model layer fails the foundation gate; deleting `hud/staff` from the vocabulary fails two of its assertions; deleting the dispatch case fails eight of the eleven contract assertions. The gate also used to record the state the route was in — reachable, and painted by nothing yet — and was written to fail the day a module under `src/ui/` started using the requester, so that entry could not go quietly stale. That is what happened, first twice and since six times over: `src/ui/simulation-room-needs.ts` reads `hud/room-list` and `hud/room-detail`, `src/ui/simulation-build-queue.ts` reads `hud/build-queue`, and `simulation-intake.ts`, `simulation-pending-deliveries.ts`, `simulation-held-guards.ts` and `simulation-staff-coverage.ts` have each since read one more. The entry is gone and the assertion runs the other way — there must be a reader, and deleting the last one fails — with every one named individually in that file's `PAINTERS`, so a reader that is renamed or moved out of `src/ui/` fails there rather than being replaced in silence by whichever other module happens to satisfy the count. **The count in this sentence is the thing here most likely to be stale**; `PAINTERS` is the list, and it is what a reader should count.

Its trap is a shape rather than a scope, and that is the difference from its two models. `state-machine.ts#handleHandshake` is declared `private handleHandshake(msg: Extract<MainToWorkerMessage, { kind: 'protocol/handshake' }>)`, and so is the handler for every other main-to-worker kind: seven annotations containing the exact substring `kind: '<K>'`, all seven of them **receivers**, all seven inside the one module that by construction can send none of them. A gate written as a substring scan would have reported all seven sent and been **green on A2 the day it was written** — measured, by dropping the trailing comma from the send pattern: `unsentMainToWorker` goes from `['protocol/handshake', 'protocol/ping']` to `[]`. So a send is `kind: '<K>'` *terminated by a comma*, an object-literal property, which is how all seventeen real send sites in `src/` are written and which mechanically excludes the type positions, the `case '<K>':` labels in both the receiving switches and `transferables.ts`, the bare literals in the kind lists, and the `kind: z.literal('<K>'),` in the schemas. The file states the rule's own bound: a send written with no trailing comma would be missed, which fails in the safe direction, and a *type* literal carrying a second member would be counted, which the direction check refuses because a main-to-worker kind cannot be constructed inside `src/simulation/worker/`.

That is also why `MAIN_TO_WORKER_MESSAGE_KINDS` did **not** need moving out of `types.ts` the way `CHALLENGE_REJECTION_CODES` did. The declaration, the eighteen schemas and the transfer switch all sit inside the scanned surface and all spell every kind, and none of them contributes a send — because here the shape and not the file list is what separates sending from naming. The test asserts that rather than assuming it. Scope still matters at one boundary and it is load-bearing there, unlike in either model: `tests/contract/` and `tests/unit/worker-state-machine.test.ts` send all four of the unsent kinds in exactly the shape the scan matches, so widening the surface from `src/` to the repository turns every entry green. Eight sending test files are asserted to exist and to be outside the surface, which doubles as the positive control that the pattern finds real sends at all.

The second direction is **provocation**, and it is derived rather than listed. `protocol/handshake-accepted` and `protocol/pong` *are* constructed -- `state-machine.ts#handleHandshake` posts `kind: 'protocol/handshake-accepted',` and `#handlePing` posts `kind: 'protocol/pong',` -- so a send-only gate reports both fine — but both sites sit inside `handleHandshake` and `handlePing`, whose only trigger is a kind nothing sends. The test splits the state machine into class members, reads each member's handled kind from the same `Extract<...>` annotation that makes a substring scan wrong, and calls a worker-to-main kind reachable only when one of its send sites is unprompted (`fault`, `publishClockState`, `publishStatusCounts`) or sits in a handler for a kind the main thread really sends. So six of eighteen kinds are dead, not four, and wiring the handshake makes two entries stale in one run — its own and `protocol/handshake-accepted`’s; `protocol/pong` waits on `protocol/ping`, which is the second half of the same one-line fix. The comment stripping here is precautionary and the file says so: measured across all 262 files under `src/`, no comment spells the send shape at all, so an identity stripper leaves every assertion green.

**What the gate does not do is decide.** Whether `protocol/handshake` should be sent, deleted, or folded into `simulation/initialize` is an ADR 0003 decision-4 question on #274's owner queue; the gate records the state and makes any answer to it visible.

Two of its assertions exist because its own evidence went stale, and they are the part worth copying. The entry for `simulation/event` named the main-thread modules that `switch (message.kind)` and called them "the complete set"; #283 added a fifth, `src/ui/simulation-alerts.ts`, whose own header calls itself the third translator of worker messages, and every assertion in the file stayed green because the entry's *conclusion* — that nothing reads `simulation/event` — was still true. An absolute that is nearly true reads as true. So the enumeration is now derived from the scan: the set of dispatchers is pinned, every module in it must be **named in the entry** (the assertion #283 would have failed), and each is required to have a `default` and no `simulation/event` case, which is what the entry actually concludes. The count *word* in the sentence is spelled from the measurement rather than typed beside it, and that detail was itself measured: written the obvious way, as `toContain('the five main-thread modules ...')`, the check is satisfiable by changing the numeral in the sentence and the numeral in the assertion together — one search-and-replace, and exactly the edit a sixth dispatcher would prompt. Deriving the numeral from the scanned count leaves nowhere to say "five" but the sentence itself.

The second is about how the file cites code at all. Nine of its citations were line numbers pointing at code #283 had moved — +67 lines in `state-machine.ts`, +98 in `types.ts` — while the identical citations here and in ADR 0003 were corrected in the same change, because a human remembered the docs and nothing in the suite could check either. A line number is not a fact about the code; it is a fact about every insertion above it, so no gate can verify one without re-deriving it. A symbol name is a fact about the code, so the citations are now written `<basename>.ts#<symbol>` and `ANCHORED_CITATIONS` requires every anchor to name a declaration the cited module still makes. The scan is scoped to the file's comments and allow-list reasons rather than its whole source, and that is load-bearing rather than tidy: measured, a whole-file scan sweeps up the assertion's own expected-value list, so a citation deleted from a sentence stays green. Its bound is stated in the file — it proves the name is declared in the cited module, not that the declaration is the one the sentence means, which is still strictly more than a line number could prove. The convention is deliberately confined to that one file for now; extending it is a separate change with its own review.

`tests/foundation/unconsumed-action-contract.test.ts` is the same shape for the semantic input actions, and #200 asked for it by name. **Eleven are declared and nine have a reader**; when the gate was written it was nine and four. `src/rendering/scene/world-scene.ts` polls `isActive` for `camera.up`/`camera.down`/`camera.left`/`camera.right`, and switches on `camera.zoom.in`/`camera.zoom.out`/`build.cancel`/`edit.undo`/`edit.redo`. `tests/foundation/unreachable-invariant-contract.test.ts` makes "an exported invariant enforcer that nothing calls" a checked state rather than something a sweep rediscovers (issue #159). `tests/foundation/documentation-claims-contract.test.ts` asserts documentation claims against the code, for the subset of them that is mechanically checkable (issue #121). `docs/ARCHITECTURE.md` declares its contracts binding, so a false sentence in it is a defect: it once listed "compressed immutable save versions" and "Supabase cloud sync" among things the app has, when nothing compresses anything and no module in `src/` can reach the cloud client at all — which sent one agent looking for a compression ratio and another for a wiring bug. `tests/foundation/documentation-links-contract.test.ts` asserts every relative markdown link resolves to a file that exists. A confident pointer to an absent file is this repository's most frequent defect, and this covers the subset of it that is mechanically checkable: a link target is unambiguously a path, while a filename backticked in prose may be a module, a concept, or an example. It deliberately does not check the latter.

`tests/foundation/documentation-commit-citation-contract.test.ts` is its sibling for the other half of a durable claim. `documentation-version-claim-contract.test.ts` requires a version in prose to name the commit it belongs to, and that escape hatch only works if the commit exists — which nothing checked, and which had already failed twice: `0269665` shipped a fabricated `d0b6e18` in the commit whose subject was dating an undated count, and the handover paragraph recording that fabrication named a second one, caught by hand before the push. A citation is **a backtick span whose entire content is 7 to 40 hexadecimal characters** — 197 occurrences across 48 files. Narrow on measured evidence rather than taste: widening it to any hex run in the text takes the corpus from 74 distinct tokens to 109 and the non-resolving ones from 3 to 36, and 33 of those 36 are correctly not commits — state hashes, atlas digests, RNG outputs, fixture UUIDs, the `actions/checkout` pin. Two further shapes are hexadecimal by coincidence and are excluded with the class named: an all-decimal run of eight or more characters (`supabase/migrations/` timestamps, Actions run ids, a byte count) and a decimal carrying a C# `float` suffix quoted out of decompiled source. **This gate could not exist until the checkout changed**, which is the part worth reading before touching either: `actions/checkout` defaults to `fetch-depth: 1`, and on one commit every citation fails to resolve whether or not it is real, so the gate would have been vacuous or impossible. `.github/workflows/ci.yml`'s `verify` job therefore checks out at `fetch-depth: 0`. **What that depth costs lives in that workflow's own comment and is deliberately not restated here.** This sentence used to carry its own copy — "2.14 MiB and about half a second for 1,115 commits" — and both halves were wrong by the time anyone re-measured them; the figure was the third copy of one measurement, and copying it a fourth time correctly would only have reset the clock. The workflow comment now gives every number the command that produces it, which is the half that does not rot. Two things about that cost belong here rather than there, because they are why the check is affordable at all: this repository's bulk is the art in Git LFS, which never enters the git pack, and the deepening is paid once on a runner that reuses its workspace. One warning for whoever reads those numbers next — **the commit count is not monotonic.** It has already gone down, because `delete-branches.yml` prunes merged branches and their commits stop being reachable from any ref, so a smaller count than last time is the cleanup working and not a rewritten history. A count that only grows is at least predictable; this one is not, and a reader who assumes otherwise will conclude the measurement is broken. (`docs/HANDOVER-2026-08-26.md` also carries the old figures and is left alone on purpose: it is dated, and says what was measured that day rather than what is true now.) The gate reads that setting back out of the workflow, so deleting it fails in the commit that deletes it; and on a checkout too shallow to answer it **fails**, naming `fetch-depth` and the step, rather than skipping — same argument as the `assets` job's pointer check, which is that a job silently validating stubs is worse than no job. It asserts two things of every citation: that it resolves, and that it is reachable from a branch or tag this repository publishes. The second exists because `fetch-depth: 0` fetches `refs/heads/*` and `refs/tags/*` and nothing else, so a sha that lives only on an agent's unpushed worktree answers one way locally and another in CI — and `docs/AGENT_WORKFLOW.md`'s worktree-and-cherry-pick method produces exactly that. Not hypothetical: `docs/NAVIGATION.md` anchors two measurements at such a commit, which is what this gate found on its first run, with no mutation involved.

`tests/foundation/documentation-source-anchor-contract.test.ts` is the third member of that pair, and it exists because the first two both look straight past the most common citation form here. A `file:line` anchor is a rooted path with a `:NNN` on the end, and `documentation-links-contract.test.ts`'s extractor requires the span to end in a dot-extension, so a span like `` `<rooted-path>.ts:165` `` is not a path to it and never was. Issue #444 measured what that cost: of the 38 fully-qualified `src/**` anchors into the worker, protocol, kernel, clock and RNG directories, ten landed on unrelated code, and **every one of the ten was in range**. So the value of this gate is stated as a bound before it is stated as a benefit — it checks that the file is there and that the line is a line that file has, and it cannot check that the line is the code the sentence means, because a line number is a fact about every insertion above it. ADR 0006 puts the limit sharply: *"an anchor that drifts onto plausible-looking code is worse than one that drifts onto nothing"*, and this catches only the second kind. It is worth having anyway, for the same reason the links gate is: it is the subset that is mechanically checkable, it costs milliseconds, and it fails in the commit that deletes or truncates the cited module. Two design choices carry the weight. Only **rooted** spans are read, which is not merely a false-positive filter — this corpus deliberately writes a *historical* anchor as a bare basename (ADR 0003's *"the nine used to read `types.ts:7`"*, `STATUS-QUEUE.md`'s *"this entry cited `:437`"*), so reading only rooted spans means no allowlist is needed for that class and none exists. And `docs/research/` is out of scope, because its README makes those records read-only dated history — *"a record here does not become wrong, it becomes older"* — which would make a build failure there demand the one edit that directory forbids. It carries 487 of the corpus's 789 anchors. Excluding it would leave every remaining assertion a "found nothing", so the excluded directory doubles as the **positive control**: `docs/research/audit-2026-08-26/05-performance.md` cites three lines of a 127-line `coordinates.ts`, and the same check is run over the research corpus asserting it still finds exactly those three. Watched going red: an in-scope anchor pushed past EOF, and the same one's path misspelled, each fail one case naming the document and the anchor; blinding the extractor fails the vacuity guard *and* the control; loosening the range comparison fails the control alone, because the in-scope half has nothing out of range to notice. And the mutation that must **not** go red did not: putting `state-machine.ts:203` back to `:165` — the real defect — leaves all three green.

`tests/foundation/comment-stripping-contract.test.ts` guards the one helper almost every gate above depends on. Nearly all of them strip comments before scanning, so that a doc comment *discussing* a mechanism is not read as the mechanism, and they all share `stripComments` in `tests/helpers/canonical-iteration.ts` rather than each carrying a copy of that rule (#188). That made it a single point of silent failure, and #278 was it: the stripper removed block comments with one regex and then line comments with another, so a `//` comment containing the two adjacent characters `/` and `*` -- which is what any glob or path looks like -- opened a block comment that ran to the next terminator anywhere below. Measured on the tree that reported it, **197 lines of real code in 19 files were blanked before any gate saw them**, including 80 consecutive lines of `src/content/default-locale-en.ts`. No gate failed. Nine of them simply scanned less and stayed green, and three were demonstrated blind by injecting a violation into a blanked span and watching them pass: `canonical-iteration-contract`, `localization-key-completeness` and `ui-orchestration-boundaries`, the last being the gate for `AGENTS.md` boundary 1. Reordering the two passes is not a fix -- it mirrors the defect onto block comments containing `//` -- so the stripper now walks the text once and knows at every position whether it is in code, a line comment, a block comment, a string, a template literal (including the code inside `${...}`, at any depth) or a regular expression literal. It is deliberately not built on `typescript/unstable/ast/scanner`: that is a scanner without a parser, and measured against it, `const re = /https:\/\//;` comes back with its trailing `//;` reported as a line comment, because deciding that is `reScanSlashToken`, which the parser calls.

The gate has two halves, and the second is the one that would have caught #278. The first is fixtures in both directions -- a comment is removed; a delimiter inside a string, a template, a regular expression or a URL is not -- each with its expected output written out. The second strips **every `.ts` file under `src/` and `tests/`** and checks each line against a deliberately dumb oracle built on the line's first two characters rather than on the scanner it is checking, because an oracle sharing the scanner's idea of where a comment starts would agree with it about the lines it got wrong: a line the stripper blanks must look like a comment line, and a line that is a whole-line comment must be blanked. On the old stripper that assertion names 156 blanked code lines. A fixture suite cannot catch a stripper that is wrong about the file it is actually pointed at.

A second instance of the same defect lived on in `src/content/validate-catalog.ts` until #307: a `stripSourceComments` built the same two-pass way, and worse, in that it replaced a block comment with a single space and so destroyed line structure as well as content. Re-measured on the tree that fixed it, over the 141 files that scan reads: **81 lines of real code lost in two files** -- 80 consecutive locale lines of `src/content/default-locale-en.ts`, reached from a `//` comment naming `src/persistence/**` whose `/` `*` opened a block comment that closed 173 lines later, plus the line of `validate-catalog.ts` that declared the stripper itself. **116 of the 141 files** came back a different length, so every offset and line number derived from the output was wrong; against the line-aligned oracle that is 4,632 misreported lines in 112 files, and 346 whole-line comments left in.

The reason it was left out of #298 was that unifying it appeared to mean shipping a several-hundred-line lexer in the client bundle, since `validate-catalog.ts` is under `src/`. The tradeoff turned out not to exist. The four source-scanning exports had no importer anywhere in `src/`, and the module holding them was reachable only as `src/content/index.ts` <- `src/simulation/rooms/definition.ts`, whose only importer is a test -- so it contributed nothing to `dist/` in the first place, which `npx vite build` confirms: no `missing-object-reference`, no `stripSourceComments`, no `defaultCrossReferenceErrors` in either output chunk. The scanning rules therefore moved to `tests/helpers/simulation-enum-source.ts`, beside the `stripComments` they now share, and `src/content/validate-catalog.ts` keeps only `validateRoomObjectReferences`, the cross-catalog check that genuinely belongs to the shipped catalogs. Bundle size is unchanged to the byte.

Two of those three absences have since stopped being true, and #315 is why. The measurement above was correct about the *module*, and it was also the first record of a defect nobody read it as: a cross-catalog check that contributes nothing to `dist/` is a check that does not run in the shipped build, while `src/content/index.ts` and `docs/CONTENT.md` both said it failed fast at startup. #315 moved it to the bottom of `src/content/room-catalog.ts`, which every reader of `defaultRoomContentRegistry` imports, so `failed cross-reference validation` is now in both output chunks by design -- +327 bytes minified, +108 gzipped on the client chunk, and a cold first call measured at 0.12-0.18 ms. `missing-object-reference` had also come back independently: `src/simulation/construction/definition.ts` declares an error of that kind for its buildable-to-object check, so the string is in `dist/` whatever `src/content/` does, which is why the build-time gate in `vite.config.ts` matches on the throw text and not on the error kind. `stripSourceComments` is still absent, and that is the claim this paragraph was making.

The fix is verified the way #298's was rather than by inspection: `tests/unit/simulation-message-keys.test.ts` now asserts its **own** corpus in both directions against the same first-two-characters oracle -- no code line blanked, every whole-line comment blanked, no file's length changed, with floors under the file, comment-line and code-line counts so a walk that collected nothing cannot pass. "The shared helper is correct" and "this gate saw every file it says it scans" are different claims, and only the second one makes the enum discovery mean anything. Demonstrated by putting the two-pass stripper back into `stripComments` and running that file alone: five of its assertions fail, naming real code lines.

`tests/foundation/localization-key-completeness.test.ts` is the [ADR 0011](./adr/0011-localization-architecture.md) gate widened past the HUD. It scans every `.ts` file under `src/` (comments stripped) for a `<name>Key: '<literal>'` declaration and asserts each one resolves to real text in the bundled default locale, which is `defaultMessageCatalogEn` -- `src/content/default-locale-en.ts` merged under `src/services/localization/default-catalog.ts`'s service strings, so neither file alone is the whole default locale. A key field is typed as a well-formed identifier and never as "a key that exists", so a typo type-checks, passes schema validation and renders as the raw identifier on screen. It is scanned rather than assembled from imported catalogs on purpose: a list of catalog modules is a list that goes stale, which is how nine declared `input.action.*` descriptions had no entry anywhere while the suite was green. Every `*Key` field name must be classified as translatable or explicitly exempted with a reason, so a new key-shaped field cannot land in neither list. Comments are stripped with `canonical-iteration.ts`'s shared stripper rather than a local copy (#188). That stripper replaces every removed character with a space and keeps every newline, so an offset into the stripped text is an offset into the source and the failure message can name a line as well as a file; the local copy it replaced deleted block comments outright, which would have put the first declaration in `src/services/entitlements/products.ts` at line 32 instead of line 60. A separate assertion checks the property rather than pinning a line: every reported line, read back out of the real file, must contain the key it names.

The four module-boundary gates -- `tests/unit/navigation-no-phaser.test.ts`, `tests/unit/services-layer-boundaries.test.ts`, `tests/unit/rendering-module-boundaries.test.ts` and `tests/unit/ui-hud-messages.test.ts`'s architectural block -- were joined by two more in #206, and one of them was rewritten. `rendering-module-boundaries.test.ts` asserted that no rendering module matched `/new (SimulationRuntime|Kernel|SparseWorld|ConstructionSystem)\b/`. `SimulationRuntime` is an `export interface` (`src/simulation/runtime/new-session.ts`), so that alternative could never match anything — `tsc` rejects `new SimulationRuntime(...)` — and it was the one naming the thing the failure message was about; the exported factory that really builds a runtime, `createNewSimulationRuntime`, was matched by nothing. Measured before the fix: a rendering module constructing and exporting a live runtime at module scope left the whole suite green with `tsc -b` clean. The construction forms are now a typed catalog in `tests/helpers/module-boundaries.ts`, and `tests/unit/module-boundary-rules.test.ts` checks **every entry against the declarations `src/simulation/**` actually exports** — an entry naming an interface, a type alias, a module-private class or a renamed export fails with a message saying which. That check is the part that makes the defect unrepeatable rather than merely fixed once.

`tests/unit/input-module-boundaries.test.ts` and `tests/unit/ui-orchestration-boundaries.test.ts` cover the two trees under `src/` that no boundary test reached. `src/input/**` imports no package at all and depends on exactly one thing outside its own tree, the type-only `KeyValueStore` contract, which is `docs/INPUT.md`'s "renderer-agnostic, user-settings concern" made executable; it reaches for exactly one browser global, `resolveBrowserKeyValueStore`'s `globalThis.localStorage`, recorded with the reason rather than forbidden, because the placement is the argued decision `docs/INPUT.md` states and #199 landed. `src/ui/*.ts` — the top-level modules the HUD gate never sees, five when that gate was written and eighteen at the time of writing, read from the directory rather than counted here — gets a manifest of which layer each may know and **whether it may run that layer's code or only name its types**, since a module permitted to name `RestoredScope` gaining the ability to call `restoreSimulationRuntime` is one line of diff and is the step that turns a view into a second source of truth. A coverage assertion keeps the two UI gates exhaustive between them, so a new subtree under `src/ui/` cannot land inside neither. Every list fails in both directions, every scan reports the number of files it read so an empty result cannot pass for compliance, and the shared rules are fixture-pinned in both directions in `tests/unit/module-boundary-rules.test.ts` — comments stripped with `canonical-iteration.ts`'s shared stripper rather than a local copy of that rule.

`tests/unit/ui-hud-messages.test.ts` remains the narrower and stronger gate for the HUD specifically: it works from the `HUD_MESSAGE_KEYS` registry rather than from a scan, so it also checks placeholder filling, key spelling, that no HUD module hard-codes a `hud.*` literal outside `messages.ts`, and `AGENTS.md` boundary 1 (`src/ui/hud/**` may not import `src/simulation/**`). Its scope is still exactly `src/ui/hud/**` and `src/ui/primitives/**`; `tests/unit/ui-orchestration-boundaries.test.ts` covers the top level, and asserts that between them the two reach every `.ts` file under `src/ui/`.

The word "specifically" in that sentence was load-bearing, and issue #208 is what it cost: that gate's collection roots are `src/ui/hud` and `src/ui/primitives`, and `src/ui/save-panel.ts` is in neither — so about thirty English literals rendered from the one UI module outside every localization check, while the repository-wide gate above passed it trivially by asking only whether the keys it *declares* resolve. `tests/unit/ui-save-panel-status.test.ts` now carries both halves for the modules directly under `src/ui/`: the same registry check over `SAVE_PANEL_MESSAGE_KEYS` (resolution, placeholder filling, key spelling, one failure key per action), and a scan asserting that none of those eight modules writes a sentence-shaped literal into `textContent` or into a `message:` field. The module list is read from the directory and compared, so a module added to `src/ui/` fails until it is checked or excluded with a reason rather than inheriting the hole this one was in. #206 part 2 asked for the same widening for the *import* boundaries and landed it as `tests/unit/ui-orchestration-boundaries.test.ts`, quoted above; the two are deliberately separate files with separate lists, because one answers "which layers may this module know" and the other "may this module put a sentence on screen", and a single allow-list carrying both reasons would be read for neither. That literal scan covers **every `.ts` module directly under `src/ui/`**, and `tests/unit/ui-save-panel-status.test.ts:205-208` reads that directory and requires equality, so the number is the directory's and not this sentence's. **It said "eight" from `e5d54ed` (#283) onward while the directory grew 8 → 9 → 11 → 12 → 13 → 14 → 15 → 18** — a count in prose beside a gate that computes the same count.

`tests/unit/ui-brand-badge.test.ts` is the registry check for the third such registry, and it exists because the naming rule the repository-wide gate depends on does not reach it: `tests/foundation/localization-key-completeness.test.ts` scans for a `<name>Key: '<literal>'` declaration, and `BRAND_MESSAGE_KEY`'s fields are `region`, `wordmark`, `stage`, `build`, `description` — not one of them ends in `Key`. That is exactly the hole `SAVE_PANEL_MESSAGE_KEY` fell into, which is why a registry check is written per registry rather than assumed. It also asserts the build identity is a valid `identifierSchema` value, because that identity is written into `SaveEnvelope.gameVersion` and reported as the worker handshake's `workerBuildId`: a commit containing a character that schema rejects would give a page that boots, renders a correct-looking badge, and then fails to save, with the failure appearing nowhere near its cause. What the badge *renders* is not asserted there — that file runs in the `node` environment with no `document`, so `createBrandBadge` cannot be called at all, and rendered-output claims belong one layer up.

The one claim about the badge that **only** the browser layer can settle is that the build identity was injected at all. `src/shared/build-identity.ts` falls back to a visible `unknown` whenever the compile-time `define` is absent, and the default Vitest environment has no `define` — so every headless test necessarily exercises the fallback, and a build that shipped `lockstate-unknown-unknown` to every player would leave the whole headless suite green. `tests/browser/app-shell.spec.ts` asserts the injected value and that it is not `unknown`. That assertion is a statement about *production* only because `vite.config.ts` and `tests/browser/vite.config.ts` import one resolver module (`tooling/build-identity.mjs`) rather than each carrying a copy: with a copy in the test config, the suite would be proving the copy.

`tests/determinism/` is the executable form of `docs/DETERMINISM.md` and, through [ADR 0009](./adr/0009-challenge-verification-strategy.md), of the challenge-verification guarantee: same seed plus same command stream reproduces an identical state hash, `snapshot() → restore() → run N ticks` equals running those ticks straight through, named RNG streams cannot perturb each other, and system order is a property of the declarations rather than of registration order. `ambient-nondeterminism-contract.test.ts` is a static contract in the spirit of `navigation-no-phaser.test.ts`: it walks the real transitive import graph out of `src/simulation/` and rejects clock, locale, DOM, storage and randomness sources, with a single per-file allow-list that fails when an entry goes stale. `canonical-iteration-contract.test.ts` is the second static contract of that family and covers the one rule in `docs/DETERMINISM.md` that had no guard at all (#132): it scans `src/simulation/`, `src/content/` and `src/persistence/` for enumerations of a `Map`/`Set` that reach no sort, and every one it finds must be either sorted or recorded in its allow-list with the reason insertion order is safe there. Its scanning rules live in `tests/helpers/canonical-iteration.ts` and are exercised against fixtures in both directions, the same split `tests/unit/simulation-message-keys.test.ts` uses with `tests/helpers/simulation-enum-source.ts` — a static contract is only as good as its pattern, and a pattern that quietly stops matching leaves a green suite and no guard. Persistence was added by #177, which also had to make the scanner tell an array's `.entries()` from a `Map`'s — it does so from array-only usage of the same receiver expression in the same file, and both directions of that rule are fixture-pinned. Its scope is still a real limit: a `Map`-order walk in `src/rendering/` is not covered, deliberately, because rendering is not simulation and its sprite pools iterate insertion order by design. A determinism test that cannot fail is worse than none, so every test there is written against a break that was actually demonstrated — see that directory's table in `docs/DETERMINISM.md`.

`protocol-fault-recovery.test.ts` is the newest of them and is there because #187 changed what happens *after* a bad message rather than what a tick computes: the worker now keeps its session after a message it could not decode ([ADR 0024](./adr/0024-protocol-fault-recoverability.md)), so a run that used to stop is a run that continues, and the obligation that it continue identically is new. It drives the **real worker entry module** — `src/simulation/worker/worker.ts`, the module `src/main.ts` loads and the build emits as `dist/assets/worker-*.js` — rather than the state machine underneath, because the decision under test is one argument at one call site in that file and a harness that called `fault()` itself would be asserting against its own copy of the thing that could be wrong. Sixty ticks with undecodable messages of every classification arriving between wakes must end byte-identical to sixty ticks with none, and the heckled run is asserted to have actually been heckled so the comparison cannot pass by both runs doing nothing. Its main-thread mirror is headless and needs no worker: `tests/unit/simulation-worker-client.test.ts` stubs the `Worker` global so the real `SimulationClient` constructor runs under `environment: 'node'`, which is what lets the swallowed-message defect be asserted in `pnpm test` rather than only in a browser.
