# Input contract

Input is a renderer-agnostic, user-settings concern. Actions are identified by semantic id (`camera.up`), never by localized key character.

**How a consumer reads them today, stated because this line used to overstate it.** It said consumers *receive* semantic action IDs; none does. `KeyboardInputAdapter.keyDown`/`keyUp` return `readonly SemanticActionEvent[]` and the only production caller discards both return values (`src/rendering/scene/world-scene.ts`). The camera **polls** held-key state instead, through two `isActive` calls covering four of the nine declared action ids. So the `SemanticActionEvent` stream is produced and consumed nowhere: `grep -rn SemanticActionEvent src/` returns hits only inside `src/input/`. Which of the two survives — the event stream or the polling — is the decision in #200, and this file should follow it rather than pre-empt it (#203).

- Defaults bind physical `KeyboardEvent.code` positions (`KeyW`, `KeyA`, `KeyS`, `KeyD`), so the same movement cluster works on QWERTY and AZERTY keyboards.
- The four arrow keys are bound to the **same four action ids** as `KeyW`/`KeyA`/`KeyS`/`KeyD`, in the same contexts, so they are a second way to reach the camera rather than a second camera control. They exist because the Build panel already told the player they did: `hud.build.arm-hint` reads "Two fingers, the middle button or the arrow keys still move the camera", it is painted on screen whenever the map route is shown, and no `Arrow*` binding existed -- measured in a browser, each arrow held for 400 ms moved the camera by exactly zero while `KeyS` moved it 180.89 (#200). Of the two ways to make that sentence true, this is the one taken: the hint is the player-visible contract and matching the code to it is smaller than withdrawing a promise, and an advertised key that does nothing reads as a broken build where an unadvertised one is only a missing feature. Note what this does **not** fix: `hud.build.arm-hint` still names keys in a hard-coded English sentence, which sits awkwardly against the label bullet below -- `resolveKeyboardLabel` exists for exactly that and still has no caller (#141, #200).
- Five of the nine declared action ids have no reader anywhere in `src/` outside `src/input/` itself: `camera.zoom.in`, `camera.zoom.out`, `selection.primary`, `build.confirm`, `build.cancel`. All five are gated -- `tests/foundation/unconsumed-action-contract.test.ts` requires each to be recorded with what is verifiably true about it, and fails in both directions, so wiring one or deleting one has to pass through that list. Three of them are bound to keys a player can press and all three are dead: `Equal` and `Minus` left `camera.zoom` at 1 across ten presses, and `Escape` neither cleared a pending wall run nor stopped it committing. They stay dead deliberately for now, because they are `discrete` actions and a held-key poll cannot serve one at all -- the honest fix consumes the `SemanticActionEvent` array the bullet above says nothing consumes, which is #200's open decision and not an implementation choice.
- The key-label resolver uses the browser keyboard-layout map when available, with the physical-code label as its deterministic fallback; labels are display-only and never participate in action lookup. **Nothing displays one yet**, and this bullet was written in the present tense as though something did. `resolveKeyboardLabel` and `fallbackKeyboardLabel` have exactly three references in `src/`, all three inside `bindings.ts` itself — the two declarations and the fallback call. It is a correct, tested component (`tests/unit/input.test.ts`) with no consumer, which is a different thing from a shipped behaviour and worth saying rather than leaving a reader to assume a remapping UI exists (#141, #203).
- Bindings declare their active contexts. Collisions are rejected only when the same device/code is active in overlapping contexts; mutually exclusive contexts may share a binding.
- `text-entry` is deliberately absent from world action defaults, preventing game controls from firing while a text field owns input. **This sentence described a guard that was wired to nothing until #201:** the mechanism was real and unit-tested — `isActive` intersects a binding's contexts with the active set — but `WorldScene` supplied a literal `() => ['world']`, so `'text-entry'`, `'modal'` and `'construction'` were decorative and exactly one context was ever active, forever. Measured: a focused `<input>` received the character `"d"` **and** the camera panned 249.6 world units, both at once.
- The scene now answers from the document — `() => (isTextEntryFocused() ? ['text-entry'] : ['world'])` — so the sentence above is true. `isTextEntryFocused` (`src/input/focus.ts`) recognises `input`, `textarea` and `contenteditable` and deliberately nothing else: stopping the camera for a focused button or `<select>` would make the game feel broken after almost any click. Because `isActive` re-reads the context on every call, focus moving into a field **mid-hold** stops the camera too, without dropping the key — so releasing it after the field is blurred still behaves.
- A key held when the window loses focus is released. A `keyup` goes to whichever window has focus, so holding a camera key and alt-tabbing sent the release elsewhere and left the code held forever — 1,419 world units of panning over three seconds, continuing through refocus and through a click (#202). `WorldScene` listens for `window`'s `blur` and calls `KeyboardInputAdapter.releaseAll()`. `blur` rather than `visibilitychange`, because an unfocused-but-*visible* window is precisely the case that produces it and `visibilitychange` does not fire for one.
- Both of the above are guarded by `tests/browser/world-scene-input.spec.ts`, which is the first test in the repository to construct a `WorldScene` at all. That absence is why two player-visible defects survived every mutation the headless suite could apply: the adapter was covered and its one call site was not.
- **Keyboard and pointer** emit one `SemanticActionEvent` contract — those two and nothing else. This bullet used to include touch, which contradicted the gesture bullet two below it: `TouchGestureTracker.move` returns `Gesture | undefined`, a `{kind:'pan'|'pinch'}` union of screen-space deltas, and `src/input/gestures.ts` never mentions `SemanticActionEvent`. That is the right design and the right place to describe it; the contradiction was in this sentence (#203). The pointer adapter handles primary/select-or-confirm and cancellation only. Pinch, pan and gesture arbitration were deferred to Issue #11 and have since landed — see the bullets below. Drag/box selection has not.
- The touch gesture core now exposes pan deltas and cursor-centered pinch scale independently from Phaser. Phaser integration and gesture arbitration remain renderer-owned.
- A pinch carries the **translation of the midpoint** as well as the scale, because two fingers on a map mean "move and scale this". That stopped being cosmetic with #74's build tool: while a tool is armed the one-finger drag builds, so two fingers are the only way a touch player can pan, and a pinch that could not translate would leave them able to zoom and never to move.
- Gesture arbitration for building is **modal**, not threshold-based. Laying a wall run *is* a drag, so no travel threshold can tell it apart from a pan without guessing, and a wrong guess either scrolls the world or builds a wall. The HUD arms the tool explicitly; while it is off every gesture keeps its previous meaning, and the middle-drag, wheel, keyboard and two-finger gestures are camera controls at all times. See `docs/RENDERING.md`.
- Accessibility preferences are a separate versioned user-settings record. `reducedMotion` and `uiScale` are validated integration points; neither belongs in authoritative prison state.
- Input settings have their own versioned serialization and must not be embedded in a prison simulation snapshot.
- The pointer adapter (`src/input/pointer.ts`) emits that same action contract; **touch and accessibility do not**, and this bullet used to say all three did. `src/input/gestures.ts` emits `Gesture`, and `src/input/accessibility.ts` is not an adapter at all — its four exports are `ACCESSIBILITY_SETTINGS_VERSION`, the `AccessibilitySettings` interface, `DEFAULT_ACCESSIBILITY_SETTINGS` and `decodeAccessibilitySettings`. There is no event type, no method and no `SemanticActionEvent` reference in the file, which is exactly what the accessibility bullet below already says, so this sentence contradicted two others in its own document (#203). Camera consumers arrived with Issue #10 (`src/rendering/camera/`, read by `src/rendering/scene/world-scene.ts`).
- Settings persistence goes through an injectable `KeyValueStore` (`getItem`/`setItem`), not a hard-coded browser global, so tests stay headless. The browser `main.ts` entry point supplies the store, via `resolveBrowserKeyValueStore()`, and passes it to `WorldScene` as `keyValueStore`. **This sentence described the arrangement and the renderer had stopped honouring it:** `world-scene.ts` read `window.localStorage` itself, in a class field initializer, so a browser that blocks site data for the origin threw before `new Phaser.Game`, `mountInterface` or `bootPersistence` were reached and the player got an empty `<body>` — no canvas, no HUD, no save panel (issue #199). The seam existed and the one production caller did not use it.
- `resolveBrowserKeyValueStore()` never throws. Reaching for `window.localStorage` is itself a throwing operation — Chrome raises `SecurityError` from the **property getter**, not only from `getItem` — so it guards both the access and a first read, and returns an in-memory `Map`-backed store when either fails. Settings a player changes then keep working for the rest of the page load; they simply do not survive a reload, which is the honest consequence of a browser that will not store them. It lives in `src/input/` rather than beside the `KeyValueStore` interface in `src/shared/`, because nothing under `src/shared/` references a DOM global and `src/services/` consumes that interface under an asserted no-I/O rule (#121 item 1).
- This is a separate store from the IndexedDB prison-save path. Keys are `lockstate.settings.input` and `lockstate.settings.accessibility`. A corrupted entry, a **missing** entry and an **unreachable store** all fall back to defaults rather than failing boot — `readJson` reads *inside* its `try`, which it did not before #199, and a refused `setItem` is swallowed too: losing a settings write is recoverable, crashing a keyboard remap mid-session is not.
- `remapAndPersistKeyboardBinding` composes validation with persistence so a conflicting or invalid remap is never written to storage.
