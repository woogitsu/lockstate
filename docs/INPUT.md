# Input contract

Input is a renderer-agnostic, user-settings concern. Actions are identified by semantic id (`camera.up`), never by localized key character.

**How a consumer reads them, in both of the two ways there are.** This line once said consumers *receive* semantic action IDs when none did — `keyDown`/`keyUp` returned `readonly SemanticActionEvent[]` and the only production caller discarded both return values, so the stream was produced and consumed nowhere (#200, #203). #200 items 2 and 3 decided that it gains a consumer rather than being deleted, and `WorldScene` now reads both routes:

- **Polled**, for `continuous` actions. `WorldScene.update` calls `isActive` four times a frame for the camera-pan ids, because a held key should move the camera in proportion to the frame it was held for.
- **Received**, for `discrete` ones. `WorldScene.handleActionEvents` consumes the array `keyDown`/`keyUp` return and switches on `action` — keyboard zoom (`camera.zoom.in`, `camera.zoom.out`), cancelling a wall run (`build.cancel`) and undo/redo (`edit.undo`, `edit.redo`). It acts on the `'started'` phase only, so a press does its thing once and the release does not repeat it.

Which route an action may use is not a free choice, and `ActionDefinition.behavior` records it: `isActive` answers "is this key down right now", which cannot serve a discrete action at all — that mismatch is exactly why `Equal` and `Minus` did nothing for as long as they were bound. The pairing is asserted in `tests/foundation/unconsumed-action-contract.test.ts`, in both directions, which is also the field's only reader.

- Defaults bind physical `KeyboardEvent.code` positions (`KeyW`, `KeyA`, `KeyS`, `KeyD`), so the same movement cluster works on QWERTY and AZERTY keyboards.
- The four arrow keys are bound to the **same four action ids** as `KeyW`/`KeyA`/`KeyS`/`KeyD`, in the same contexts, so they are a second way to reach the camera rather than a second camera control. They exist because the Build panel already told the player they did: `hud.build.arm-hint` reads "Two fingers, the middle button or the arrow keys still move the camera", it is painted on screen whenever the map route is shown, and no `Arrow*` binding existed -- measured in a browser, each arrow held for 400 ms moved the camera by exactly zero while `KeyS` moved it 180.89 (#200). Of the two ways to make that sentence true, this is the one taken: the hint is the player-visible contract and matching the code to it is smaller than withdrawing a promise, and an advertised key that does nothing reads as a broken build where an unadvertised one is only a missing feature. Note what this does **not** fix: `hud.build.arm-hint` still names keys in a hard-coded English sentence, which sits awkwardly against the label bullet below -- `resolveKeyboardLabel` exists for exactly that and still has no caller (#141, #200). Nor is the sentence legible at every viewport any more: below 700px of viewport height `hud.css` clamps `.hud-build__note` to a single line, so the arrow-key clause is clipped on screen there while the string itself stays in the DOM in full. That was the price of getting the Build panel's last section above the fold at 900x600 (#174), and it makes the hint a promise the panel states in full only at taller windows -- another reason the binding, not the sentence, is what the player can rely on.
- Two of the eleven declared action ids have no reader anywhere in `src/` outside `src/input/` itself: `selection.primary` and `build.confirm`. Both are gated -- `tests/foundation/unconsumed-action-contract.test.ts` requires each to be recorded with what is verifiably true about it, and fails in both directions, so wiring one or deleting one has to pass through that list. Neither is bound to a key, so no player can press one and find nothing happening; both are emitted by `PointerInputAdapter`, whose returned events `WorldScene` still discards because placement and panning work through Phaser's own pointer handlers, which consult no action id. It was five, and the other three -- `camera.zoom.in`, `camera.zoom.out`, `build.cancel` -- were the ones bound to keys that did nothing: measured before the fix, `Equal` and `Minus` left `camera.zoom` at 1 across ten presses, and `Escape` neither cleared a pending wall run nor stopped it committing (#200).
- The key-label resolver uses the browser keyboard-layout map when available, with the physical-code label as its deterministic fallback; labels are display-only and never participate in action lookup. **Nothing displays one yet**, and this bullet was written in the present tense as though something did. `resolveKeyboardLabel` and `fallbackKeyboardLabel` have exactly three references in `src/`, all three inside `bindings.ts` itself — the two declarations and the fallback call. It is a correct, tested component (`tests/unit/input.test.ts`) with no consumer, which is a different thing from a shipped behaviour and worth saying rather than leaving a reader to assume a remapping UI exists (#141, #203).
- **`KeyZ` undoes and `KeyY` redoes** (#261). `ConstructionSystem` has maintained a transaction-grouped, snapshot-safe undo model since #108, `Undo` and `Redo` have been declared commands with handler branches calling it, and until #261 nothing in the application could produce one: there was no control, no binding and no intent, so the stack could be pushed and never popped. The key now reports through `EditHistoryPort` to `BuildTool`, which reports a direction to the HUD, which dispatches its own `undo`/`redo` intent — the same path `place-build-order` takes, and taken for the same reason: a refusal raised on the renderer's key handler reaches no control, no line and no player, which is the shape of the defect #225 removed from the build drag. The mechanism is complete and tested, and this is what makes it reachable. While it landed, what a player could undo was a *pending* order rather than a wall, because a placed order stalled in `materials-pending` for want of a buy surface; #89 added that surface, so an undo now takes back an order that would have become a wall.
- **No binding expresses a modifier, and that is an open question rather than a decision taken here.** `KeyboardBinding` is `{ device, code, action, contexts }` and `KeyboardEventLike` reads `code` and `repeat`, so the adapter cannot distinguish `Z` from `Ctrl`+`Z` from `Cmd`+`Z`: all three reach the `KeyZ` binding, which `tests/browser/world-scene-input.spec.ts` measures for `Control` in a real browser. What cannot be expressed is the other half of a chord scheme — undo on the chord *and nothing at all on the bare key*. That needs a modifier vocabulary in the binding record, which is persisted under a versioned settings format (`src/input/settings.ts`) and validated by the remapping path, so it is a schema decision for an owner rather than a line in `bindings.ts`; #261 raises it and deliberately invents nothing. macOS's `Command` is unmeasured here and this repository claims nothing about it.
- Bindings declare their active contexts. Collisions are rejected only when the same device/code is active in overlapping contexts; mutually exclusive contexts may share a binding.
- `text-entry` is deliberately absent from world action defaults, preventing game controls from firing while a text field owns input. **This sentence described a guard that was wired to nothing until #201:** the mechanism was real and unit-tested — `isActive` intersects a binding's contexts with the active set — but `WorldScene` supplied a literal `() => ['world']`, so `'text-entry'`, `'modal'` and `'construction'` were decorative and exactly one context was ever active, forever. Measured: a focused `<input>` received the character `"d"` **and** the camera panned 249.6 world units, both at once.
- The scene now answers from the document — `() => (isTextEntryFocused() ? ['text-entry'] : ['world'])` — so the sentence above is true. `isTextEntryFocused` (`src/input/focus.ts`) recognises `input`, `textarea` and `contenteditable` and deliberately nothing else: stopping the camera for a focused button or `<select>` would make the game feel broken after almost any click. Because `isActive` re-reads the context on every call, focus moving into a field **mid-hold** stops the camera too, without dropping the key — so releasing it after the field is blurred still behaves.
- A key held when the window loses focus is released. A `keyup` goes to whichever window has focus, so holding a camera key and alt-tabbing sent the release elsewhere and left the code held forever — 1,419 world units of panning over three seconds, continuing through refocus and through a click (#202). `WorldScene` listens for `window`'s `blur` and calls `KeyboardInputAdapter.releaseAll()`. `blur` rather than `visibilitychange`, because an unfocused-but-*visible* window is precisely the case that produces it and `visibilitychange` does not fire for one.
- Those two, and the discrete keys, are guarded by `tests/browser/world-scene-input.spec.ts`, which is the first test in the repository to construct a `WorldScene` at all. That absence is why two player-visible defects survived every mutation the headless suite could apply: the adapter was covered and its one call site was not.
- **Keyboard and pointer** emit one `SemanticActionEvent` contract — those two and nothing else. This bullet used to include touch, which contradicted the gesture bullet two below it: `TouchGestureTracker.move` returns `Gesture | undefined`, a `{kind:'pan'|'pinch'}` union of screen-space deltas, and `src/input/gestures.ts` never mentions `SemanticActionEvent`. That is the right design and the right place to describe it; the contradiction was in this sentence (#203). The pointer adapter handles primary/select-or-confirm and cancellation only. Pinch, pan and gesture arbitration were deferred to Issue #11 and have since landed — see the bullets below. Drag/box selection has not.
- The touch gesture core now exposes pan deltas and cursor-centered pinch scale independently from Phaser. Phaser integration and gesture arbitration remain renderer-owned.
- A pinch carries the **translation of the midpoint** as well as the scale, because two fingers on a map mean "move and scale this". That stopped being cosmetic with #74's build tool: while a tool is armed the one-finger drag builds, so two fingers are the only way a touch player can pan, and a pinch that could not translate would leave them able to zoom and never to move.
- Both two-finger gestures are executed against a real `WorldScene` by `tests/browser/world-scene-touch.spec.ts`, in a Chromium context with `hasTouch` driven through CDP `Input.dispatchTouchEvent` — a `page.touchscreen` tap places one finger and cannot express a second. Until #209's follow-up, no synthetic touch sequence had ever been dispatched at this project, so both halves of the sentence above rested on reading: measured now, two fingers travelling +120/+78 together move the camera by exactly −120/−78 at zoom 1 and leave the zoom untouched, and a symmetric separation from 100px apart to 220px apart multiplies the zoom by 2.2 while the world point under the midpoint stays put to within 3.0e-5 world units. What that spec settled about the **scroll** during a pinch is in `docs/CAMERA.md`, because it is a property of the anchored zoom rather than of the gesture.
- **Three touch pointers reach the scene, beside the mouse — measured, not inferred.** Phaser starts with one touch pointer (`inputActivePointers` defaults to `1`, and neither `src/main.ts` nor the browser harness sets it), which is why `WorldScene.create` calls `this.input.addPointer(2)`: without it a second finger is not delivered and `TouchGestureTracker` never sees a pinch. What that call actually produces was an inference from Phaser's source until #209 — the audit read four pointer entries and could not say which one was the mouse. Read live from `input.manager` in a real browser: four entries with ids `[0, 1, 2, 3]`, `pointersTotal` 3, and the manager's own `mousePointer` at index 0, i.e. one mouse and three touch pointers. `tests/browser/world-scene-input.spec.ts`'s pointer-inventory test is that reading, kept, and the default is measured too rather than taken from Phaser's source: deleting the `addPointer(2)` call takes the scene to one touch pointer and `addPointer(1)` takes it to two. Two of the three are what a gesture uses — `TouchGestureTracker.move` pairs the finger that moved with exactly one peer, so a third finger already down does not change the result (`tests/unit/input.test.ts`) — so the third is a spare.
- **A room is designated by a rectangle drag, and removed by one** (ADR 0022, amended). The Rooms tab arms a second world tool, and the gesture is the same shape as a wall run with one difference that is the whole reason it is a second tool: it keeps **both** axes. `edgeRunFromDrag` commits a drag to one axis because a wall is one-dimensional; `tileRectFromDrag` must not, because a rectangle is exactly the shape that has two. Press a tile, drag to the opposite corner, release — and the release **designates nothing**: it leaves a pending rectangle that the panel confirms, because a designation can cover 4,096 tiles and removal, while it now exists, is not free. **What it costs changed with #337 and this sentence used to say the old figure** — "it takes the whole connected same-type run", which meant a drag clipping one of two touching cells took both. Since `dea529c` a covered tile is resolved to the room instance whose rectangle contains it and *that room* is cleared (`src/simulation/rooms/zoning.ts:808`), so the cost is the whole of each room the rectangle touches and no neighbour beyond them — still not free, because clipping one corner of a 6×6 canteen clears all 36 tiles, and still worth confirming. The confirm step is also what makes removal usable on touch, where undo is a keyboard chord and there was previously no recovery of any kind from a stray drag. `Escape` abandons either gesture, the camera keeps every gesture it had, and at most one of the two tools is ever armed — they are armed from panels on different tabs and leaving a tab disarms its tool.
- **A room is also designated by four numbers, and that is not a convenience** (ADR 0039, #411). Until it existed, the drag above was the *only* producer of a rectangle anywhere in the application: the world canvas answers `tabIndex: -1` with no `role` and no `aria-label`, and `ACTION_IDS` names no area, rectangle or tile cursor — so a keyboard-only player could reach every control in the Rooms panel, arm the tool, and then have nothing to press. That is not an awkward game, it is an unfinishable one, because a prison with no room refuses every admission for the rest of the session. The Rooms panel now carries a folded "Enter coordinates" form — tile X, tile Y, width, height, and one control that produces the rectangle — at the foot of its catalogue list, and the rectangle it produces is the *same pending rectangle* the drag produces: the confirm control, the minimum-size warning and the refusals are reached unchanged, and `unzone-room` gained its keyboard route in the same stroke because the confirm row is driven by whether a rectangle is pending and never by who set it. The two sides are bounded at 64 tiles so the two routes reach the same set of rectangles; the tile coordinates are deliberately unbounded, because the panel does not know where the owned world is and a silent clamp would move a designation somewhere the player did not ask for. `tests/browser/app-shell.spec.ts` drives the whole loop — new prison, room type, coordinates, confirm, play, admit — with `page.keyboard` and a tripwire that fails the test if any trusted pointer press reaches the page. It was the first spec in this repository to press `Tab` at all, which is why the gap survived a ~190-test browser suite.
- **The room catalogue is one tab stop, not eighteen** (#411). The route above was *possible* from the day it shipped and was measured as such — every hop in the keyboard spec is bounded — but it was not *short*: the catalogue is eighteen rows, each one a `<button>` and therefore each one its own tab stop, and the coordinate form is the last child of the same scroller, so a keyboard player crossed the remainder of the list to reach it on every room they ever zoned. `room.cell`, the room the whole game is gated on, is drawn fifth. The rows are now a `radiogroup` with a **roving tab stop** (`src/ui/primitives/roving-focus.ts`): exactly one row carries `tabindex="0"` and it follows the selection, the arrows move focus inside the group with Home/End and a wrap at both ends, and `Enter`/`Space` chooses through the same `onActivate` a pointer press reaches. So the catalogue costs one `Tab` in and one `Tab` out, and the disclosure is the very next thing after the chosen room — asserted as an exact `1` in `tests/browser/app-shell.spec.ts`. The announced role is not decoration: a roving `tabindex` with nothing to say it was one would leave a sighted keyboard-only player unable to reach seventeen of the rows at all, so `role="radiogroup"`/`role="radio"` and `aria-checked` are what make the shorter route a fix rather than a regression, and `aria-checked` is now the machine-readable carrier of which room type is selected where only a badge said it before. Focus moves without selecting, deliberately: choosing a room type re-arms the world tool, so selection-follows-focus would fire that once per arrow press.
- **The Build catalogue is one tab stop too, and it is the longer list** (#411, the Build half). The bullet above landed on the Rooms catalogue and left this one exactly as it found it, although `BUILDABLE_REGISTRY` draws more rows than `room-catalog.ts` does — so the panel a player spends the most time in kept one native tab stop per row. Measured on the assembled application at 1280x800 with one prison saved: the forward `Tab` walk from the Build tab to the buy disclosure was **43** presses, of which **21** were the catalogue; the same walk is **23** now. The remaining 22 are not the catalogue's — sixteen of them are outside the Build panel altogether (the tab bar finishing its own buttons, the brand region, the metrics row, three transport controls, two panel toggles, the Alerts header and six save-panel buttons) and six are the panel's own header, its category filter, the catalogue, *Place on map*, *Remove* and *Buy*. So the Build panel's own share went from 26 presses to 6, and shortening the rest is a different piece of work with a different subject.
- **What the filter forced that the Rooms catalogue never had to answer.** These rows can be `hidden` (ADR 0035), and `hidden` takes an element out of sequential focus navigation — so a roving `tabindex="0"` left on a filtered-out row is a catalogue `Tab` cannot enter *at all*, which is strictly worse than the tab stops it removes, and an arrow key that named a hidden row would be a key that silently moves nothing, because `focus()` on one does nothing. Both halves are therefore read off the **visible** rows: `buildCatalogueFocusRing` in `src/ui/hud/build-panel.ts` answers with the ring and its one tab stop together, so the panel holds no second copy of the filter and the two can never disagree. It is pure and node-testable for the reason `visibleBuildableIds` beside it is; the wiring — a resolved `tabIndex`, a real `document.activeElement` after a real key press, and both under an active category — is in `tests/browser/app-shell.spec.ts`, which is the only place the real eight-group projection exists (`tests/browser/ui-harness.ts` draws one group and therefore no filter at all). The group is announced on the scroller itself rather than in a box of its own, because unlike the Rooms scroller this one holds the rows and nothing else — the Build panel's typed route is its own sibling section.
- **No catalogue row in this interface is ever disabled**, which is why neither catalogue has a rule for arrowing past one. `ListRow.element` is typed `HTMLElement` (`src/ui/primitives/list-row.ts:20`), `createListRow` takes no disabled option, and no panel casts to reach one; a buildable nothing sells is a row with no `material`, which hides the *buy control* and leaves the row itself selectable. A sentence asserting an absence rots first, so: the check is that `ListRow` still exposes no way to disable a row.
- **A command press gives the keyboard back to the control that issued it** (the accessibility playtest of 2026-08-29). Every control that issues a command — the status strip's transport, the Build panel's *Buy* and *Place order*, the Rooms panel's *Designate*, the Staff panel's *Hire*, the Intake panel's *Admit*, and the save panel's own buttons — is disabled for as long as that command is in flight, which is what stops two taps becoming two commands (issue #65, `src/ui/primitives/async-action.ts`). A disabled element cannot hold focus, so the browser blurs it, and re-enabling it does not undo that: measured keyboard-only on the assembled page with the pointer tripwire live, all six left `document.activeElement === document.body` with the command itself succeeding. For a player on a pointer that is invisible; for a player on the keyboard it is the loss of the only position they have, and it happened on **every command in the game**. The busy group now remembers which of its own controls held the keyboard when it disabled them and gives it back when it re-enables them — but only that control, only while nothing else has claimed it in the meantime (a player who tabbed away during the request keeps where they went), and only if it can still hold focus. Where it cannot, focus is left where the browser put it rather than forced somewhere arbitrary: a rebuilt row is matched by a `focusKey` naming what the control *does* rather than which node is doing it (the save panel re-renders its list from inside its own action), and a control that is really gone — a deleted prison's row — has no replacement to inherit it. The Rooms panel's *Designate* is the exception that proves the shape: it **hides itself** before it dispatches, so it is already blurred before the busy group sees it, and the keyboard is handed on by the panel to the *Arm* control that takes its place in the same 44px row. `tests/browser/app-shell.spec.ts` measures all six, keyboard-only, on commands it first proves were not refused.
- Gesture arbitration for building is **modal**, not threshold-based. Laying a wall run *is* a drag, so no travel threshold can tell it apart from a pan without guessing, and a wrong guess either scrolls the world or builds a wall. The HUD arms the tool explicitly; while it is off every gesture keeps its previous meaning, and the middle-drag, wheel, keyboard and two-finger gestures are camera controls at all times. See `docs/RENDERING.md`.
- Accessibility preferences are a separate versioned user-settings record. `reducedMotion` and `uiScale` are validated integration points; neither belongs in authoritative prison state.
- Input settings have their own versioned serialization and must not be embedded in a prison simulation snapshot.
- The pointer adapter (`src/input/pointer.ts`) emits that same action contract; **touch and accessibility do not**, and this bullet used to say all three did. `src/input/gestures.ts` emits `Gesture`, and `src/input/accessibility.ts` is not an adapter at all — its four exports are `ACCESSIBILITY_SETTINGS_VERSION`, the `AccessibilitySettings` interface, `DEFAULT_ACCESSIBILITY_SETTINGS` and `decodeAccessibilitySettings`. There is no event type, no method and no `SemanticActionEvent` reference in the file, which is exactly what the accessibility bullet below already says, so this sentence contradicted two others in its own document (#203). Camera consumers arrived with Issue #10 (`src/rendering/camera/`, read by `src/rendering/scene/world-scene.ts`).
- Settings persistence goes through an injectable `KeyValueStore` (`getItem`/`setItem`), not a hard-coded browser global, so tests stay headless. The browser `main.ts` entry point supplies the store, via `resolveBrowserKeyValueStore()`, and passes it to `WorldScene` as `keyValueStore`. **This sentence described the arrangement and the renderer had stopped honouring it:** `world-scene.ts` read `window.localStorage` itself, in a class field initializer, so a browser that blocks site data for the origin threw before `new Phaser.Game`, `mountInterface` or `bootPersistence` were reached and the player got an empty `<body>` — no canvas, no HUD, no save panel (issue #199). The seam existed and the one production caller did not use it.
- `resolveBrowserKeyValueStore()` never throws. Reaching for `window.localStorage` is itself a throwing operation — Chrome raises `SecurityError` from the **property getter**, not only from `getItem` — so it guards both the access and a first read, and returns an in-memory `Map`-backed store when either fails. Settings a player changes then keep working for the rest of the page load; they simply do not survive a reload, which is the honest consequence of a browser that will not store them. It lives in `src/input/` rather than beside the `KeyValueStore` interface in `src/shared/`, because nothing under `src/shared/` references a DOM global and `src/services/` consumes that interface under an asserted no-I/O rule (#121 item 1).
- This is a separate store from the IndexedDB prison-save path. Keys are `lockstate.settings.input` and `lockstate.settings.accessibility`. A corrupted entry, a **missing** entry and an **unreachable store** all fall back to defaults rather than failing boot — `readJson` reads *inside* its `try`, which it did not before #199, and a refused `setItem` is swallowed too: losing a settings write is recoverable, crashing a keyboard remap mid-session is not.
- `remapAndPersistKeyboardBinding` composes validation with persistence so a conflicting or invalid remap is never written to storage.
