# Yard exercise station: authored art draft

The existing `yard-basic` room plan is an 8×8 outdoor square with `objects: []`. All 19 object types in the other authored plans already resolve to oblique Blender catalogs; duplicating one would not add a missing asset. This draft supplies a new 2×1 outdoor exercise station for a later content change by the integrator. It is **not yet a buildable object** and is intentionally absent from the live oblique registry and object mapping until the Yard content path can place it.

The [twelve-pose contact sheet](poses.png) displays the actual Blender model at four yaws and three camera elevations. It has a tall pull-up bridge and a low parallel grip on four rubber anchored plates. The materials use the existing muted steel/rubber/warm accent palette. Evaluated Blender mesh bounds, including modifiers, are **X [0.05000003, 1.94999993], Y [0.05999999, 0.94], Z [0, 1.6975]** in minimum-corner tile coordinates: the visible geometry fits the full 2×1 occupied-square footprint. Model identity: `furniture.yard.exercise-station`; authored source: `assets/source/blender/furniture.yard.exercise-station.blend`.

`tooling/blender/create-yard-exercise-station.py` rebuilds the source in Blender 5.2.1. `tooling/blender/render-yard-exercise-station-oblique.py` exports 12 yaw × 6 elevation poses (72) at 256×256, nominal **64** px/tile, centered pivot `[128,128]`, camera target `[1,0.5,0.82]`. Source render camera and catalog target are the **same** `(1,0.5,0.82)` point. The runtime painter anchors the image at `(tileX+1,tileY+0.5,0.82)` and the sprite encodes each source vertex relative to that camera target, so its visible ground projection is `(tileX+sourceX,tileY+sourceY,sourceZ)`; there is no second offset. The renderer checks every transparent border, removes volatile Blender PNG time metadata and writes SHA-named PNGs plus `public/game-content/oblique-furniture.yard-exercise-station.v1.json`. The orthographic span is exactly **4 world tiles** across the 256 px render, so `256 / 4 = 64` rendered pixels per tile; the catalog test reads the exporter camera scale and checks that equation against its `nominalPixelsPerTile`. At yaw 0°/elevation 40°, the actual alpha width is 124 px across a 2-tile source, close to the expected 128 px footprint. `paintAsset` scales by `TILE_SIZE_PX / nominalPixelsPerTile = 64 / 64`, retaining that size. The catalog test also checks the source hash and all 72 frame hashes. Full runtime placement, collision, save/load and Full HD visual behavior still depend on the content definition and consumer mapping; this sheet is a source-art check, not gameplay acceptance.

Verification: all 72 Blender renders passed the border gate; the twelve inspected contact-sheet poses retain the same anchored feet, with alpha bounds fully inside the 256×256 image at yaw 0/90/180/270 and elevation 20/40/70. `python tooling/research/yard-exercise-contact-sheet.py` rebuilds the sheet from the 12 SHA-checked files. The focused catalog and research-index tests passed 6/6. Replacing exactly the first frame's stored SHA with zeroes made the catalog test fail 1/1 at that PNG; restoring the original manifest made it pass 1/1. Initially the raw Blender PNG bytes differed between identical preview runs because Blender wrote `Date` and `RenderTime` text chunks, although every RGBA pixel matched. Normalizing the PNG chunks made two independent preview rerenders byte-identical and two full 72-pose manifest rerenders SHA-identical. No browser test has been run because the asset is not yet placed by production content.

The final 4.0-tile camera scale was itself mutation-checked: changing only the exporter constant back to `3.7` made the catalog test red with `69.189189...` calculated px/tile against the manifest's `64`; restoration returned green. Two final full-catalog rerenders produced the same manifest SHA-256 `22079b7d941fef033d0f6f4fc3cd29e6ecaafd647f18556b5728b877cbc7cf3a`.
